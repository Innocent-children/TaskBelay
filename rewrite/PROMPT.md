# 按功能说明书实施 TaskBelay 重构

这份提示词供用户明确要求实施重构时使用。阅读或修改说明书本身，不代表开始删除代码、创建分支或执行安装。

## 1. 产品依据

先完整阅读 `rewrite/SPEC.md`。产品核心是防止 LLM 过度设计和过度测试；接力、存储和安装服务于这两个目标。

当前用户请求优先。实现、测试与文档必须表达同一份已确认说明书，不以既有代码证明某个设计必须保留。仓库工程要求发生冲突时，按当次用户实际确定的重构范围处理，不把本文件当作超出范围的操作许可。

不得把新算法替换为固定文件/行数预算、泛泛的提示词或任意模型评分。也不得把 Agent 提供的语义判断伪装成程序已经证明的事实。

## 2. 工作范围与数据保护

- 只在用户指定的仓库和重构范围内修改。Git 分支、commit 和其他写操作按当次实际授权执行；不自行 push、merge、打 tag、发布包或修改远端设置。
- 验证使用临时仓库和临时 `TASKBELAY_HOME`，不读取、修改或删除用户现有 TaskBelay 数据。
- 安装测试使用隔离的 Agent 配置目录。通过测试进程环境传入临时用户目录，不改真实全局配置，不把全局 HOME 或 USERPROFILE 改成任务变量。
- 清理前核对实际路径及 Git 跟踪状态；不删除未跟踪文件、ignored 文件或用户工作区改动。
- 先读取并保存需要的 Agent 格式、平台进程处理和打包来源，再替换对应实现。不要先删除后续实现仍需参考的材料。
- 说明书只描述目标产品。开发过程、尚未验证的结果和清理记录放在最终交付说明中。

## 3. 开始实现前形成具体方案

按贡献指南说明用户问题、真实可用信息、处理规则、验收和非目标。以当前用户请求为授权，不对已经确定的实施范围重复请求计划批准。

建立下面四条贯穿实现的对应关系：

1. 用户目标 → 必须实现或保持的行为。
2. 实际改动 → 当前职责 → 需要处理的新增复杂度。
3. 行为与失败原因 → 实际测试断言 → 必要检查集合。
4. 当前内容与运行结果 → 验证缺口 → 停止条件。

对明显改变用户行为的规格歧义，先给出具体问题和建议。普通实现方法自行选择；不要实现一个已知会错误复用结果或错误放行交付的解释，再把问题留到最后报告。

## 4. 实现职责

沿用说明书第 13.3 节的责任划分。`internal/service` 是 CLI、MCP 和 hook 共享的操作入口；规则在 `internal/task`，事实观察、分析、执行和存储分别由对应包负责。

按真实职责选择模块与直接调用。接口只用于当前调用方需要的边界，不因“只有一个实现”一律删除，也不为可能的未来扩展预建框架。

当前唯一 Task、实际运行、问题身份和累计记录不能在 Agent 或展示层复制成第二套状态。平台差异放在适当的平台文件和构建约束中，规则层不判断操作系统。

输入、输出和错误使用一份共同 Schema；先定义行为及对象关系，再实现消费者。源码位置、内容哈希、Agent 判断和真实进程结果保持来源区别。

## 5. 实施顺序与检查点

实施可以在同一完整重构中逐步进行，每一阶段都要有可检查的实际结果。阶段是开发安排，不是产品增加给用户的流程。

1. **Task 与观察**：不可变内容起点、行为清单、当前 Schema、修订和请求身份。通过涉及起点、目标变化、并发和状态保留的验收场景。
2. **设计算法**：实际改动覆盖、结构候选、直接方案比较、来源校验及增量失效。通过 A1–A9，明确哪些是程序事实、哪些是模拟 Agent 判断。
3. **测试算法**：测试情况与断言、重复候选、缺口、集合选择和停止。通过 A10–A19 及相关交付场景；保留必要边界测试和不同验证层次。
4. **实际执行**：输入与覆盖键、单 Task 运行协调、真实进程、结果保存、中断和复用。通过 A15–A28 中涉及执行的场景，不用假运行替代。
5. **接力与接口**：六个 MCP 工具、CLI、共享操作入口、交接、报告和占用。实现全部当前命令与错误，不保留另一套判断流程。
6. **Agent 接入和分发**：按可核对的真实格式接入四个 Agent，完成隔离安装测试及平台包完整性检查。源码模拟与真实会话分别标明。
7. **完整验收**：完成 A1–A37、受影响接口 Schema 校验、打包和性能检查，审查整个方案的责任和复杂度。

先做能验证核心算法的最小完整路径，再扩展已定义的接入；不要把交付停在只有统计报告、不能处理问题和阻止重复工作的原型。

## 6. 检查与测试

- 检查必须对应当前验收、具体失败或实际影响，不为每次编辑重复跑整个仓库。
- 对照说明书第 14 节使用实际入口测试；算法单元测试只补充无法清楚定位的规则差异。
- 使用有必要接口与无用接口、必要边界测试与重复测试等成对样本，不能只测试“应该拒绝”的例子。
- 运行成功不代替需求满足；Schema 通过不代替来源真实；模拟 Agent 输入不代替真实模型会话。
- 先检查作用域内的构建和测试。系统重构的最终检查点再做完整 `go test ./...`、`go vet ./...`、目标平台构建和安装产物检查。
- 不用降低断言、删除未解决场景或放宽未知输入来让测试通过。
- 清理被取代的实现和测试时，以当前责任与验收为依据，保持交付只有一套当前实现。

## 7. 文档与 Skill

README 说明用途、安装、完整例子和必要限制；产品说明描述真实行为；接口文档给出当前命令、Schema、错误和恢复方式；支持记录区分源码、模拟、原生平台和真实 Agent 会话。

目标产品维护中文与英文。实施中同步受影响的文档族及工程说明，避免当前用户入口继续指向不存在的实现。普通文档工作不修改产品版本或公开支持声明；功能实施时按实际版本约定更新机器可读元数据，不执行发布。

Skill 共同规则在一处维护，Agent 特有格式单独转换。生成或打包的副本不手工改写。最终安装包离开仓库也应包含所需文件。

使用普通中文与明确代码标识符。删除无助于理解的口号和重复说明，不靠禁词扫描代替准确表达，也不强制用行数上限压缩必要内容。

完整 MCP 请求示例紧邻同工具的具体错误示例，并能追溯到实际实现和验证。不能编造成功输出或未验证的 hook 能力。

## 8. 最终交付

用中文说明：

1. 核心算法实际实现了什么，哪些规则依赖 Agent 判断，哪些事实可以由程序核对。
2. A1–A37 的实际结果、必要的命令及未运行的检查。
3. 对绕过方式的处理：改名、删除检查、移动起点、过期理由、并发、响应丢失和旧通过结果。
4. 原生平台、真实 Agent 会话和隔离安装包分别验证了什么。
5. 冷/热性能、实际结构与体量，以及仍存在的限制。
6. 说明书第 16 节的对照是否真实执行；没有执行时，不能声称算法已经达到节省比例或质量目标。
7. 从当前真实需求重新设计，是否仍会选择这个结构；根因、职责和复杂度是否同时满足要求。

按用户要求的检查点结束，不以路线图替代完整实现，也不把完成本地工作扩大为发布操作。
