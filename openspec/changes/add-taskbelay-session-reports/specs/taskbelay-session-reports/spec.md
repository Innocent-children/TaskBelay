# Spec Delta

## Purpose

在 TaskBelay 执行实际工作时，将动作及当时可确认的结果保存为中文会话记录。用户直接查看用户目录中的文件即可了解 TaskBelay 做了什么，无需发起查询或要求 Agent 生成报告；记录只描述事实，不推断没有依据的收益。

## ADDED Requirements

### Requirement: 在动作发生时自动记录
系统 SHALL 在 TaskBelay 执行需要记录的动作时自动追加会话记录，不等待用户询问，也不依赖 debug 开关。没有相关动作的普通工具调用 MUST NOT 机械地产生工作记录。

#### Scenario: 正常开发中产生提示
- **WHEN** TaskBelay 成功向 Agent 输出了一项检查提示
- **THEN** 同次处理将该提示的简短事实写入会话文件，无需用户再发起请求

#### Scenario: 普通工具调用没有干预
- **WHEN** Agent 执行普通工具调用，TaskBelay 没有产生需要记录的动作
- **THEN** 不为该调用追加表示“提供了帮助”的记录

### Requirement: 用户直接查看会话文件
系统 SHALL 将记录保存到 TaskBelay 用户数据目录的 `session-records/`，使用 UTF-8 Markdown。用户 SHALL 可以直接打开文件查看。系统 MUST NOT 为此新增 MCP 查询工具、查询命令、汇总报告入口或对话中的自动播报。

#### Scenario: 用户查看记录
- **WHEN** 用户打开 `~/.taskbelay/session-records/` 或 Windows 下对应的用户目录
- **THEN** 可以直接阅读已生成的会话记录，无需调用 Agent 或其他查询入口

### Requirement: 按工作区与会话隔离文件
系统 SHALL 使用当前事件或调用中可核对的工作区、Agent 和 session 确定文件。同一组合 SHALL 持续追加到同一文件，即使会话跨天或切换任务；不同组合 SHALL 使用不同文件。没有任务编号不影响已核对会话的记录，身份无法核对时 MUST NOT 归入其他会话。

#### Scenario: 两个 session 共享任务
- **WHEN** 两个 session 同时处理同一任务
- **THEN** 两个 session 的动作分别写入各自文件，不混入一个任务文件

#### Scenario: 同一会话切换任务
- **WHEN** 当前会话从任务 A 切换到任务 B，或跨天继续运行
- **THEN** 继续追加原会话文件，每条保留适用的任务编号

#### Scenario: 无当前任务
- **WHEN** TaskBelay 输出接续信息时尚未创建任务，但会话身份可核对
- **THEN** 记录写入当前会话文件，任务显示为未关联，不新建任务

### Requirement: 记录具体动作及必要依据
每条记录 SHALL 包含带时区的发生时间、工作区、Agent、session、适用的任务、动作对象、简短说明及当时可取得的来源编号。记录范围 SHALL 包括需求和决定保存、接续信息提供、检查反馈、验证拒绝、过期编辑拒绝，以及已观察到的检查或验证结果。

#### Scenario: 保存需求
- **WHEN** Agent 通过现有 MCP 工具成功保存一项需求
- **THEN** 文件追加需求编号、修订、简述和“已保存”事实，不声称该需求已经实现

#### Scenario: 拦截验证
- **WHEN** TaskBelay 已成功输出对一条重复验证命令的拒绝
- **THEN** 文件追加命令的脱敏简述、拒绝依据和可取得的验证或问题编号

### Requirement: 只写当时可确认的事实
记录 SHALL 区分已经发生的动作、未完成或未知结果。生成决定不等于成功输出，检查复用不等于新执行，提交交付请求不等于任务完成。系统 MUST NOT 推断节省的时间、token 或避免的缺陷，也 MUST NOT 主动追踪后续效果来改写记录。

#### Scenario: 输出没有完成
- **WHEN** TaskBelay 形成提示或拒绝决定，但未确认输出完成
- **THEN** 如记录该事件，明确写为未确认完成，不记作成功提示或成功拦截

#### Scenario: 后续验证取得结果
- **WHEN** 之前启动的验证随后返回可核对的结果
- **THEN** 在结果到达时追加一条新记录，不回写先前条目，也不为完善记录另行运行验证

#### Scenario: 复用检查
- **WHEN** TaskBelay 采用已有的检查结果
- **THEN** 记录写为复用结果，并保留可取得的原检查编号，不写成新执行了一次检查

### Requirement: 文件持续追加并保持已有内容
系统 SHALL 在首次有记录时创建文件，后续以完整条目追加，不重建或覆盖已有内容。多个进程同时写入同一会话文件时 SHALL 保持各条记录完整，不交错拆分。文件 SHALL 由用户自行保留或删除，程序更新、卸载及账本清理 MUST NOT 自动删除这些文件。

#### Scenario: 多进程追加
- **WHEN** 同一会话的 hook 和 MCP 进程同时产生记录
- **THEN** 两条记录均完整追加，已有正文保持不变；发生时间以各条时间字段为准

#### Scenario: 用户修改已有文件
- **WHEN** 用户编辑过记录文件，随后同一会话产生新动作
- **THEN** 系统只追加新条目，不恢复或覆盖用户修改的已有内容

### Requirement: 仅记录新动作并控制记录内容
系统 SHALL 直接使用动作处理时已取得的信息，只记录功能运行后新发生的事件。系统 MUST NOT 查询或补写历史数据，不提供旧格式兼容和迁移逻辑，也 MUST NOT 复制完整会话、原始工具输出、凭据或完整调试快照。命令信息 SHALL 沿用既有脱敏结果。

#### Scenario: 开始使用记录功能
- **WHEN** 新功能开始运行并产生一项新动作
- **THEN** 直接写入这项动作，不扫描账本或工作区来补齐先前过程

### Requirement: 记录不改变正常开发
写入记录 SHALL 不改变任务、需求、授权、检查输入或既有拦截决定，不启动检查、测试、构建、工作区扫描或网络请求。记录无法写入时 SHALL 沿用现有错误日志报告原因，并让原业务流程按原结果继续，不阻断 Agent 开发。

#### Scenario: 记录文件无法写入
- **WHEN** 当前动作已按原流程处理，但追加记录失败
- **THEN** 原动作结果不变，记录错误进入现有日志，不因此增加拦截或重跑业务动作
