# Design

## Context

动机见 `proposal.md`，行为见 `specs/taskbelay-session-reports/spec.md`。目标代码仓库为 `/Users/innocent-children/GoLandProjects/TaskBelay`。规划阶段仅编写规划文档；实际实施状态见 `tasks.md`。

现有代码已经掌握需要记录的信息：

- `internal/hook/dispatch.go` 的 `HandleOutput` 串联事件处理、协议输出和完成状态，可区分形成决定与成功输出。
- 需求、笔记、任务及检查服务在处理完成时已有记录编号、Actor 和结果；无需为写会话文件重新查询整份账本。
- `internal/ledger/debug.go` 的 `DebugTrace.append` 已采用用户数据目录、受限文件权限、追加打开和每条一次写入，可参考其文件处理方式。debug 本身仍是独立的详细诊断功能。

## Goals / Non-Goals

**Goals:**

- 在动作发生时直接留下简短中文记录，用户打开文件即可理解。
- 按当前工作区、Agent 和 session 保持文件归属，支持多个短进程持续追加。
- 使用处理过程中已取得的事实，不改变原业务结果。

**Non-Goals:**

- 不增加查询工具、查询命令、汇总接口、统计面板或对话播报。
- 不生成会话总结，不计算收益，不主动追踪后续效果。
- 不读取、兼容、转换或回填历史数据，不增加报告查询表、索引或迁移逻辑。
- 不为记录启动检查、测试、构建、工作区扫描、外部模型或网络请求。

## Decisions

### 1. 在现有动作完成位置记录

不设置“用户询问后生成”流程。既有处理路径在取得实际事实时，将少量记录字段交给文件写入器：

| 原有动作 | 写入时机与内容 |
| --- | --- |
| 保存需求、决定、下一步或方案 | 确认实际保存后，记录编号、修订、任务及简述；仅返回模式提示而没有保存时不写“已保存” |
| 开始或恢复任务、申请交付 | 记录实际状态动作；`task_finish` 只申请交付时写“已申请交付”，不写“任务已完成” |
| 向 Agent 提供接续信息 | 成功输出后，记录提供了哪些需求、决定或下一步的简述 |
| 输出检查提示或拒绝 | 成功输出后，记录对象、规则、实际决定及可取得的检查或问题编号 |
| 执行检查或采用检查结果 | 按返回结果写明新执行、复用、部分完成或未知；不将复用写成新执行 |
| 观察到验证结果 | 结果事件到达时写入已知运行状态和退出结果；尚在运行或未知时如实记录 |
| 拒绝过期编辑 | 成功输出拒绝后，记录文件和拒绝原因，不推断避免了多少损失 |

纯读取、普通工具经过和没有实际干预的放行不机械记录。正常记录只在原动作产生事实时调用；不会为完善文件再检查一次代码或轮询验证结果。之后有新的正常结果事件时，再追加一条即可。

业务事实与输出事实分开处理：数据库操作实际完成可以记录“已保存”；准备好的提示只有输出成功才记录“已提示”。失败或未完成事件如果记录，必须保留当时状态。

### 2. 每个会话持续追加一个 Markdown 文件

位置为：

```text
<用户数据目录>/session-records/<workspace-key>/<agent>-<session-key>.md
```

用户数据目录复用 `Store.DataDir()`。macOS、Linux 为 `~/.taskbelay`，Windows 为 `%USERPROFILE%\.taskbelay`。工作区和 session 的 key 根据各自完整身份生成固定的安全路径片段，采用 SHA-256 前 32 个十六进制字符；Agent 使用已有固定标识。文件路径不带任务编号或日期，同一会话跨天、提交代码或切换任务后仍追加同一文件。

文件在第一条有效记录到达时创建，不创建空报告。每条记录是独立的 Markdown 小节，写清工作区、Agent、session 和适用任务，不依赖全局文件头、索引文件或格式元数据。例如，以下仅为格式示例：

```markdown
## 2026-10-31T14:30:00+08:00 · 需求已保存

- 工作区：/path/to/project
- 会话：Codex / <session-id>；任务：t17
- 动作：保存需求 R2 第 1 版，增加 CSV 导出。
- 依据：requirement:R2@1；工具调用：<call-id>
```

每条保留必要的来源编号及简述，不复制完整原话、全部检查正文或工具输出。结果尚未知时直接写明，不补充猜测。记录中不包含累计统计和效果评分。

选择 Markdown 是为了让用户直接阅读；单条独立成节避免首次写文件头时的额外协调。文件追加顺序表示实际写入顺序，跨进程事件先后以每条发生时间和来源身份为准，不为了排序回读或重写整个文件。

### 3. 使用已有文件写入方式，保持操作简单

文件写入器沿用现有用户数据根目录和 `os.OpenRoot` 的处理方式，以 `O_CREATE | O_APPEND | O_WRONLY` 打开文件。一次条目先在内存中形成完整短文本，再一次追加写入，核对实际写入长度；不分多次输出一条内容。新建目录使用 `0700`，文件使用 `0600`，Windows 的实际权限沿用用户目录控制。

不读取目标文件来合并、重新生成或校验正文，不增加每次请求的报告副本、文件摘要、复用缓存或后续修补流程。用户改过的现有正文继续保留，后续只追加；用户删除文件后，新的动作按正常创建路径继续记录，不恢复已经删除的内容。

多个进程追加沿用现有“一条一次写入”的方式，实施时用本次必要的临时验证确认目标环境中条目不交错。无需新增常驻写入服务或跨会话调度器。

写入失败通过现有错误日志报告，不改变原动作结果或决定，不为了保存记录重跑原业务。记录本身的成功或失败不再生成一条会话工作记录。

### 4. 数据来源直接来自当前处理过程

记录条目只需要事件时间、工作区、Actor、任务编号、动作类别、简短文字、当时结果和来源引用。身份沿用现有适配器和服务取得的信息；无法核对 session 时不猜测归属。

hook 决定涉及的记录内容可以先作为内部瞬时数据随处理结果返回，在协议输出完成后追加；它不需要写成供以后查询的新账本字段。MCP 处理路径直接使用已返回的类型化业务结果组织记录，不把任意成功调用都解释成“提供了帮助”。

不改造 `CheckRecord` 保存会话调用列表，不建立新的 `report_evidence` 持久化结构，也不从提示文字反向解析规则。缺少某个编号时写已有事实及其可取得的来源，不能编造引用。命令内容只使用已有脱敏信息。

### 5. 落点遵循现有模块职责

| 位置 | 计划职责 |
| --- | --- |
| `internal/ledger/session_records.go`（新增） | 根据当前身份定位文件，负责目录创建和完整条目的追加；不提供读取与汇总接口 |
| `internal/summary/session_record.go`（新增） | 将当前动作事实格式化为中文 Markdown 条目，不查询账本 |
| `internal/event/event.go`（按需） | 定义 hook 处理期间传递的最小记录事实，不新增外部事件或协议字段 |
| `internal/hook/` 的既有动作和输出路径 | 提供当前动作事实，严格按实际结果及输出状态触发写入 |
| `internal/mcpserver/` 或其调用的既有业务服务 | 为实际发生的需求、笔记、任务、方案及检查动作写记录，不注册新工具 |

使用上述小范围数据传递和写入函数，不建立通用审计框架。无需修改 `task_get`、新增响应预算或向接续提示添加查询引导。

产品文档分别说明功能用途、哪些动作有记录、实际落盘时机、目录与保留方式。会话文件是产品运行数据，位于用户目录；不在代码仓库新增过程台账或验证归档。

## Risks / Trade-offs

- 每个有效动作增加一次本地文件追加 → 只写当前动作的简短事实，不附完整快照、不增加数据扫描。
- 开始记录不代表动作成功完成 → 使用实际处理状态；输出未完成和结果未知明确写出。
- 多进程追加顺序不一定等于事件发生顺序 → 保留带时区时间和来源身份，不重排文件。
- 文件随使用增长 → 由用户自行保留或删除；不附带自动轮转、清理或归档功能。
- Windows、macOS、Linux 的真实运行证据不同 → 只报告当次实际验证的平台和 Agent；构造事件不能代替真实接入结果。
