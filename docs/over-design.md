# 过度设计判定

过度设计是：在当前需求、已有行为、明确授权和用户修改都得到满足的条件下，仍存在可以避免的实现负担。接口只有一个实现、文件较多或代码较长，只能作为检查线索，不能独立证明过度设计。

本文定义新算法。共享事实、证据超图、增量失效、问题身份和预算见 [算法设计](algorithm.md)。当前程序的 D1 至 D8、E1 及其阈值属于旧实现，不再作为本设计的判定依据；旧报告仍按生成它的版本解释。

## 检查范围

检查从任务起点到当前内容的累计改动，以及受其影响的既有行为。可核对的 Agent 编辑用于确定行为责任，工作区更新用于确定当前事实。不可拆分的用户修改不得作为自动删除候选。

需求位置、引用、调用和文件相邻关系用于发现候选机制；是否支持需求必须另有语义依据。新增参数、接口、配置、依赖或兼容路径均按同一方法判断，不设语言规则分支。

有效依据包括用户明确要求的结果、直接相关的既有不变量，以及当下确实存在的复用、隔离、资源管理、可维护性或性能要求。不得凭空加入未来兼容、多后端或插件扩展需求。已有架构的存在也不自动证明它必要。

## 约束建模

对每个机制 Mᵢ 建立有限域变量 Xᵢ，取值包括保留、删除，以及已经具体描述的简化替代。替代必须说明改什么、影响什么、保留什么行为；“重写得更简单”不是一个可求解的候选。候选未列全时，只讨论当前候选集，不能宣称找到所有可能设计中的最优解。

约束 Φ(X) 包含：

| 约束 | 表达的事实 |
| --- | --- |
| 需求满足 | 哪些机制或替代共同实现一项结果，哪些是可选实现路径 |
| 行为保持 | 这次修改直接、间接影响的既有行为和当前工程约束 |
| 依赖与互斥 | 保留 A 是否必须保留 B；两个替代能否同时存在 |
| 范围与授权 | 当前需求、有效方案、新入口与依赖的明确边界 |
| 用户内容 | 用户修改及无法拆分的混合片段必须保留 |
| 明确保留 | 用户决定精确约束到的对象、范围和有效期限 |

同一结果可能要求多个机制同时存在，也可能有不同实现路径。例：

```text
R1 = (A ∧ B) ∨ C
R2 = B ∨ D
cost(A,B,C,D) = (1,2,2,5)
```

只看 R1 会选成本为 2 的 C；一起满足 R1、R2 时，A+B 的成本为 3，低于 C+B 的 4。逐条规则分别删除或保留机制，无法可靠处理这种共享关系。

用户没有要求的行为不能通过 Agent 新增一条“推断需求”变为硬约束。某条语义约束尚未核对时，记录待核对条件；求解器不能把模型假设转换成事实。

## 成本模型

求解目标为：

```text
min C(X)
subject to Φ(X)
```

成本首先保存可解释的向量：需要维护的独立状态、配置选择、外部依赖、间接调用与维护操作。按当前任务约定的权重得到非负标量 C，仅用于候选搜索和排序。代码行数、接口数和测试数不能单独决定成本；成本项、权重、来源与不确定范围写入结果。

精简结论优先使用支配关系：替代满足相同的已核对约束，所有已识别成本维度不增加，至少一项降低。如果减少代码却增加运行成本或改变隔离边界，则报告具体取舍，不把较低总分当作必须采纳的理由。成本未知时保留未知，不能默认为零。

成本并不等于业务收益。保留某个机制能满足什么要求，由约束和证据表达，不能靠任意“价值分”抵消未授权功能。

## 求解流程与复杂度

1. 把约束与成本项转为有限域因子图；共享变量、全局约束和交叉成本必须连在同一分量，不能为了提速将它们当作独立分量。
2. 对连通分量分别求解。先检查当前设计在模型内是否可行，再寻找具体替代。若约束之间互相冲突，使任何设计都不可行，报告模型冲突及来源，不把它直接归责为 Agent 过度设计。
3. 在预算内使用启发式构造树分解，不要求先算最小树宽。低树宽分量通过动态规划求精确解。树分解中的每个节点保存一个变量集合，称为袋（bag）；各袋记录边界变量每种赋值下的最小成本和回溯选择。
4. 高树宽分量使用有界分支定界：保存已核对可行解作为上界，使用可靠松弛下界剪枝，先搜索受本次改动影响的局部替代。
5. 输入变化后只重算受影响因子及相关消息。分解结构、成本或边界变化时相应失效；最坏情况下仍需重算整个分量。

每个约束或成本因子只分配给一个包含其全部变量的袋，避免重复计费。违反硬约束的赋值成本为正无穷。袋 b 向父袋 p 传递边界消息，局部因子之和为 φᵦ，分隔集为 S=b∩p：

```text
m[b→p](s) = min { φᵦ(x) + Σ m[c→b](x restricted to c∩b) }
             x 遍历袋 b 的赋值，且 x restricted to S = s
             c 遍历 b 的子袋
```

根袋取最小值并回溯选择；所有赋值均为正无穷时，才得到该完整模型不可行的结论。树分解必须满足每个因子的变量同袋、包含同一变量的袋连通，不能只对普通依赖图求宽度后忽略高阶约束。

假设已经取得有效树分解，每个因子的求值成本至多为 `poly(w)`，袋数为 g、因子数为 f、树宽为 w，布尔变量的动态规划时间为 `O((g+f) · poly(w) · 2^(w+1))`。每袋因子数有界时可简写为 `O(g · poly(w) · 2^(w+1))`。有限域最大大小为 d 时，对应指数项为 `d^(w+1)`；布尔编码后的树宽可能变化，不能忽略。空间也随袋表大小指数增长。

增量更新仅在分解不变、缓存消息仍有效时，以实际重算的袋数 gΔ、因子数 fΔ 代替对应规模。构造分解、语义提取、候选生成的成本另计。高树宽问题最坏仍为指数级；不承诺任意项目快速得到精确最优。

## 求解结果与依据

| 结果 | 需要展示的内容 | 处理 |
| --- | --- | --- |
| 当前改动违反已核对硬约束 | 具体改动、来源、约束与成立前提 | 能归责于 Agent 时按产品规则有限拦截 |
| 找到更简单的可行替代 | 替代内容、满足的约束、成本差与适用条件 | 作为工程建议，由 Agent 复核后决定 |
| 删除或替换会破坏约束 | 模型内冲突的约束子集和来源 | 说明该机制在当前模型与候选集中的作用 |
| 候选之间存在取舍 | 各自收益、增加的负担与未知项 | 提示，不强制删除 |
| 预算到期或证据不足 | 可行解、上下界、未搜索范围或缺失证据 | 未知，不拦截，不写成没有过度设计 |

冲突子集不要求是最小不可满足核，也不能由一次失败搜索推出“没有替代”。只有完整求解或有效证明，才能报告模型内不可行或最优。存在一个成本更低的可行解，不需要先证明它全局最优，就可以提交精简建议。

可行性证书用于核对方案是否满足模型中的全部约束，至少包含输入版本、变量选择、约束及来源、各约束满足情况、成本变化。证书证明有限模型中的结论，不证明任意程序语义等价。修改依赖语义假设时，必须保留这些条件和待核对处；不能用求解器替代代码理解。

## 常见场景

| 场景 | 判断方式 |
| --- | --- |
| 只有一个实现的接口 | 比较改为直接调用的方案；核对当前隔离、复用和测试边界，不能按实现数量删除 |
| 当前看不到调用的代码 | 核对外部入口、动态注册与完整使用范围；范围不明时不判定未使用 |
| 新增配置或兼容分支 | 找到它实现的当前结果；没有依据先提示，明确违反需求或方案才拦截 |
| 新依赖 | 比较具体已有能力与新增依赖方案，展示维护和运行取舍 |
| 大段重复代码 | 提出当前可用的共享机制，比较耦合与维护成本；不以重复率强制抽象 |
| 用户改过的机制 | 保留当前内容，建议只针对可核对且可分离的 Agent 部分 |
| 用户明确要求保留 | 将精确对象加入有效约束，其他对象继续正常分析 |

## 反馈与接续

反馈先说明事实，再说明可选替代和影响。例如：

```text
[精简建议] CSV 导出的分隔符配置
当前需求只要求固定格式导出。可移除新增配置，并在导出位置使用既定分隔符。
该替代保留当前已核对的输出和错误处理，减少一项配置及对应分支。
动态调用范围尚未完整核对，本次仅提出候选，不作删除结论。
```

同一建议没有新证据时不反复要求解释。用户采纳后，重新核对改变的约束与证据；无需因为“进行了精简”就自动补跑测试。明确保留、问题修复和暂时未知分别记录，接续时使用当前事实。
