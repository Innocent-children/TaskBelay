# 过度设计判定

本文定义 TaskBelay 怎样判断一个任务的改动里有没有过度设计。检查对象是本次任务的 diff，包括各种语言的代码，以及改动过的其他文件。检查在 Agent 准备结束时运行，Agent 也可以随时主动要求检查。结论分三档：放行、提示、拦截，结论怎样影响 Agent 见 [产品需求](product.md) 的默认行为。本文用到的任务、需求、实现位置和归属，定义见 [任务和需求](requirements.md)；规则里说到的声明、接口、错误类型、对外入口在各种语言里对应什么写法，以及一个文件能做哪些检查，见 [语言支持](languages.md)。

## 过度设计是什么样子

本文说的过度设计，是改动里不为用户这次的要求服务的部分，包括：用户没要的功能和对外入口，眼下只有一种用法却做成可替换的抽象，值永远不变的参数，为旧调用方保留的兼容代码，以及和任务无关的顺手修改。它们有一个共同点：删掉之后，用户要的行为一点不少。

用户说：“给 export 命令加一个导出 CSV 的选项。”Agent 交回的改动节选如下：

```go
// internal/export/exporter.go
type Exporter interface {
	Export(w io.Writer, rows []Row) error
}

type csvExporter struct{ delimiter rune }

func (e *csvExporter) Export(w io.Writer, rows []Row) error {
	cw := csv.NewWriter(w)
	cw.Comma = e.delimiter
	// ……写表头和每一行
}

func NewExporter(format string, delimiter rune) (Exporter, error) {
	switch format {
	case "csv":
		return &csvExporter{delimiter: delimiter}, nil
	}
	return nil, fmt.Errorf("unknown format %q", format)
}

// cmd/export.go
format := fs.String("format", "table", "output format: table or csv")
delimiter := fs.String("delimiter", ",", "CSV field delimiter")
```

用户要的行为只需要这么多：

```go
// internal/export/csv.go
func writeCSV(w io.Writer, rows []Row) error {
	cw := csv.NewWriter(w)
	// ……写表头和每一行
}

// cmd/export.go
format := fs.String("format", "table", "output format: table or csv")
```

多出来的是 `Exporter` 接口、只有一个分支的 `NewExporter`，以及用户没提过的 `--delimiter`。Agent 的理由通常是“方便以后加 JSON”“分隔符可能有人要改”，这些都是对将来的猜测。

## 核心做法

每一处改动都要能回答两个问题：它为哪条需求服务？它现在就有用吗？

第一个问题看归属。Agent 为每条需求列出实现位置，TaskBelay 从这些位置出发，沿着代码之间的引用关系，找出每处改动归属哪条需求（方法见 [任务和需求](requirements.md)）。没有归属的，或者只归属到推断需求的，就是和需求无关的改动。新增的对外入口还要多一步，必须拿出对应的用户原话。

第二个问题看现在的用法。接口、泛型、函数参数这类抽象，只有当前代码里已经有两种以上用法才算有用；新增的错误类型要有地方区分它；参数和字段只有值会变才有必要；新增的声明要有人用。“以后可能用到”不算用法。

两类判断只看代码里数得出来的事实，不请另一个模型来评判，所以同样的代码和需求每次得出同样的结论。项目里已经普遍采用的写法，按项目惯例放行。一处命中要算作合理，唯一的办法是拿出用户的原话。

## 检查用到的输入

- **diff 和改动声明**：本次任务的 diff，以及其中的改动声明和改动过的其他文件。生成的代码、依赖目录下的文件和锁文件不检查；测试代码和测试数据由 [过度测试判定](over-testing.md) 检查。这几类文件怎样认出来，见 [语言支持](languages.md)。
- **需求、实现位置和归属**：每处改动归属哪条需求。
- **当前代码**：工作区里 TaskBelay 能解析语法的全部源文件，从中得到每个声明引用了哪些声明，以及下文各条规则要数的用法。
- **已有代码**：当前代码去掉本次任务新增的声明，用来统计项目惯例。

下文反复用到三个说法：

- **引用**：定义见 [任务和需求](requirements.md)。D1 判断“有没有人用”用的就是它；D4 数用法时用的是各种抽象自己的数法，见 D4。
- **非测试代码**：不属于测试代码的代码。数“有几种用法”时只数非测试代码，测试里的用法不算，因为“为了方便测试”加的抽象，正是本文要找的过度设计之一。
- **库的公开声明**：可能被工作区之外的代码使用的声明，比如 Go 里不在 `internal/` 目录下的包导出的声明。各种语言怎样认定，见 [语言支持](languages.md)。几条规则对它们放宽，下文逐条说明。

## 规则

每条规则都按同一个格式写：判断什么，怎么判断，有例外时写例外，为什么这样定。档位写在规则标题里，参数集中在后面的参数表中。一条规则要用到的写法，某种语言没有规定时，这条规则不检查这种语言的文件，见 [语言支持](languages.md) 的“三级支持”。

### D1 没人用的代码（拦截）

**判断什么**：新增的声明有没有被用到。

**怎么判断**：一个新增的声明同时满足下面三条，就命中：非测试代码里没有任何声明引用它；它的名字没有作为一个完整的单词出现在非测试代码的字符串里；也没有出现在工作区的其他文件里，比如配置文件和依赖清单。

后两条是为按名字调用留的余地：反射、插件注册、配置文件里写的入口函数，都是用字符串写出名字来调用的。

**例外**：隐式调用的声明，也就是程序入口，以及运行时或框架按约定调用的函数和方法，比如 Go 的 `main`、`init` 和 `String()`，Python 的 `__str__` 和带路由装饰器的函数，Java 带注解的方法。各种语言的清单见 [语言支持](languages.md)。

**为什么这样定**：没人用的代码是最直接的多余。常见的是“以后可能用到”的辅助函数，以及改到一半被替换掉、却没删干净的旧实现。只有测试在用的声明同样命中：为了测试而留着的功能代码，不属于用户要的行为。新增的库的公开声明在工作区里没人用，也同样命中，这里没有给它放宽：它要么是用户要的新 API，这时用户的原话里会提到它，可以凭原话放行；要么就是多余的。

### D2 和需求无关的改动（拦截）

**判断什么**：每个改动声明、每个改动过的其他文件，是不是为某条原话需求服务。

**怎么判断**：按 [任务和需求](requirements.md) 的方法，确定每个改动声明、每个改动过的其他文件归属哪条需求。没有归属的命中；只归属到推断需求的也命中，说明里写明它归属哪条推断需求。以那份文档里的例子来说，`log.Debugf` 没有归属，命中 D2。

任务里还没有任何原话需求时，所有改动都会命中。这时 TaskBelay 只给出一条合并的说明：先记录需求，改完后列出实现位置。

**例外**：依赖清单由 D8 检查。被删除的声明不检查。

**为什么这样定**：顺手修改是 Agent 最常见的多做，比如“看到旁边的函数写得不好，一起改了”。判断依据是归属而不是改动行数，因为一处改动多不多余，和它的大小无关。

### D3 没有原话依据的对外入口（拦截）

**判断什么**：新增的对外入口是不是用户要的。

**怎么判断**：对外入口有命令行参数、子命令、环境变量、HTTP 路由和配置字段五种，按 [语言支持](languages.md) 里各种语言的写法找出来。每个新增的对外入口，都必须出现在某条原话需求的实现位置里，并且附有匹配上的原话引用，否则命中。

**为什么这样定**：对外入口一旦交出去，用户和其他程序就会依赖它，以后删掉的代价最高；它也是 Agent 最爱“顺便”加的东西，比如多一个开关、多一个环境变量。要求每个入口单独附上原话，任务完成时 TaskBelay 会把“入口 ← 原话”逐条列给用户，用户一眼就能看出某个参数是不是自己要的。

### D4 只有一种用法的抽象（拦截）

**判断什么**：新增的抽象现在是不是真的有多种用法。

**怎么判断**：按抽象的种类数用法，用法少于参数表里的“抽象至少要有的用法数”（2）就命中。错误类型例外，只要有 1 处区分就不命中。

| 新增的抽象 | 一种用法指什么 |
| --- | --- |
| 接口类：接口、trait、protocol、抽象类 | 非测试代码里实现它的一种具体类型 |
| 泛型声明 | 非测试代码里写明的一组类型实参。有一处用法靠推断、看不出类型实参时，这个声明不检查 |
| 函数参数，以及类型是函数的字段 | 非测试代码里传进来、赋进去的一个不同的函数。同一个具名函数算一个，每个匿名函数各算一个 |
| 错误类型，包括 Go 的哨兵错误 | 非测试代码里一处区分它的地方，比如 Go 的 `errors.Is`、Python 的 `except`、Java 的 `catch` |

各种语言里这几种抽象怎样认出来，“实现”和“区分”指哪些写法，见 [语言支持](languages.md)。

**例外**：
- 库的公开声明里的接口、泛型和错误类型，因为工作区之外的代码可能实现或区分它们。
- 符合项目惯例的，见 E1。

**为什么这样定**：抽象的价值在于让多种实现、多种情况共用一段代码。只有一种的时候，它只会多出一层跳转和一个名字。“为了以后扩展”不算用法：以后真需要时，把一种实现改成接口是一次机械的重构，代价很小。“为了方便测试”也不算：测试里的替身不计入用法，项目如果一贯这样写，会按 E1 放行。没有任何地方区分的错误类型，调用方拿到它也只能当普通错误处理，直接用普通的错误就够了。

### D5 用不上的参数和字段（拦截）

**判断什么**：新增的参数和字段，值会不会变。

**怎么判断**：
- **新增的参数**，包括给已有函数加的参数，满足下面任一条就命中：函数体里没用到；非测试代码里所有调用处传的都是同一个常量；或者所有调用处都没有传它，总是用默认值。什么算常量，见 [语言支持](languages.md)。
- **新增的字段**，满足下面任一条就命中：非测试代码里从来没被赋值；或者每次赋值都是同一个常量。

**例外**：
- 签名由别处决定的函数：实现接口或覆盖父类的方法，以及作为值传出去、要符合某种函数签名的函数。
- 库的公开声明的参数。
- 从外部数据写入的字段，比如 Go 带结构体标签的字段、pydantic 模型的字段。它们的值在解码外部数据时写入，代码里看不到赋值，按“从来没被赋值”判断会误拦。其中的配置字段由 D3 判断。

**为什么这样定**：一个永远传同一个值的参数，等于一个藏在调用处的常量；一个从不赋值的字段，等于一个零值常量。Agent 常把“可配置”当作好设计，加了参数，调用处却只传默认值。

### D6 只转发的函数（提示）

**判断什么**：新增的函数是不是只把调用原样转给另一个函数。

**怎么判断**：新增的函数或方法，函数体只有一条语句，这条语句调用另一个函数（或者返回它的结果），参数按原来的顺序原样传入，没有任何其他处理，就命中。

**例外**：实现接口或覆盖父类的方法；库的公开声明。

**为什么这样定**：Agent 加的转发层多数只是多了一次跳转，比如 Service 套一层 Manager。转发有时也合理，比如给第三方包换一个本项目惯用的名字，所以这条只提示，由 Agent 自己判断，不阻止结束。

### D7 保留旧写法（拦截）

**判断什么**：改动有没有为旧的调用方式保留兼容代码。

**怎么判断**：出现下面任何一种就命中：
- 新增了弃用标记，比如 Go 的 `// Deprecated:` 注释、Java 的 `@Deprecated` 注解。
- 新增了一个别名，别名用的旧名字是起点快照里已有的名字，比如 Go 的 `type Old = New`，也就是改了名却留下旧名字。为其他目的新增的别名不命中。
- 起点快照里已有的函数，改动之后函数体变成了对一个新增函数的原样转发，也就是改了名却留下旧名字。

各种语言的弃用标记和别名写法见 [语言支持](languages.md)。

**为什么这样定**：兼容代码是为已经存在的外部调用方准备的。仓库内部的改名，所有调用方都在同一次改动里改掉了，留下旧名字只会让代码里并存两套写法。库已经发布、确实需要兼容时，用户会明确提出，这时按原话放行。

### D8 新增依赖（提示）

**判断什么**：改动有没有引入新的第三方依赖。

**怎么判断**：依赖清单里新增了直接依赖，就命中。有哪些依赖清单、什么算直接依赖，见 [语言支持](languages.md) 的“依赖清单”。

**为什么这样定**：引入依赖有时是正确的选择，比如解析一种复杂格式；但 Agent 也常为了几行代码就引入一个包。是否值得，由 Agent 自己掂量，所以只提示。

### E1 项目惯例（放行）

**判断什么**：一处 D4 命中的写法，是不是这个项目一贯的写法。

**怎么判断**：在已有代码里，按 D4 的同一种抽象、同一种数法统计：已有多少个这种抽象，其中有多少个如果是新增的就会命中 D4。比如统计接口：已有代码里有多少个接口，其中有多少个在非测试代码里只有一种具体类型实现；统计错误类型：已有多少个错误类型，其中有多少个没有任何地方区分它。会命中的数量达到参数表里的“已有数量”（3 个），并且占同种抽象的比例达到“所占比例”（50%），就认为项目惯例如此，本次新增的同种抽象全部放行。统计范围是工作区里和这处改动同一种语言的已有代码。

放行的地方会写进检查结果的放行记录，并附上统计数字，比如“按项目惯例放行：已有 8 个接口，其中 6 个只有一种具体类型实现”。

**为什么这样定**：项目的写法是用户或团队已经做出的选择，TaskBelay 不和它对着干。同一个仓库里并存两种风格，比多一层抽象更难维护。惯例是从代码里数出来的，Agent 自己说“项目都这么写”不算数。E1 只用于 D4，因为其他规则查的是无用、无关、不变的东西，项目惯例改变不了它们是多余的这个事实。

### 凭用户原话放行

按 [任务和需求](requirements.md) 的“凭用户原话放行”，一处改动出现在某条原话需求的实现位置里、并且附有匹配上的原话引用，就不再受 D1、D4、D5、D6、D7、D8 约束，D3 也以此为满足条件。检查结果里会写明“按原话放行”和对应的原话。

## 结论和参数

一次检查的结论取所有命中里最高的档位：没有命中是放行；只有提示档的命中是提示；有任何一处拦截档的命中就是拦截。按 E1 或用户原话放行的地方不算命中，只记进放行记录。因为语言支持不到而没检查的部分，写进检查结果的“未完成的部分”，不影响结论。

| 参数 | 值 | 用在哪里 |
| --- | --- | --- |
| D1、D2、D3、D4、D5、D7 的档位 | 拦截 | 结论 |
| D6、D8 的档位 | 提示 | 结论 |
| 抽象至少要有的用法数 | 2 | D4 |
| 错误类型至少要有的区分处数 | 1 | D4 |
| 项目惯例的已有数量 | 3 个 | E1 |
| 项目惯例的所占比例 | 50% | E1 |
| 各种语言里声明、抽象、对外入口、依赖的写法 | 见 [语言支持](languages.md) | 各条规则 |

## 事前提示

session 开始时，TaskBelay 把下面这几条交给 Agent，让它一开始就按规矩做，而不是等被拦下再改：

- 只做原话需求里的事。需求之外想到的改进，告诉用户，不要直接做。
- 新增接口、泛型、函数参数、错误类型之前，先确认现在就有两种以上用法。
- 新增参数和字段之前，先确认它的值会变。
- 不要加用户没提过的命令行参数、子命令、环境变量、HTTP 路由和配置字段。
- 改名就改彻底，不保留旧名字。
- 改完后，在每条需求的实现位置里列出关键的声明、改过的其他文件，以及新增的对外入口。对外入口要附上用户原话。

## 给 Agent 的反馈

拦截时，Agent 收到的说明是这样的：

```text
TaskBelay 检查结论：拦截（2 处拦截，1 处提示）

[D4 拦截] internal/export/exporter.go:12 接口 Exporter
  非测试代码里实现 Exporter 的只有 *csvExporter 一种类型。
  建议：去掉接口，直接调用 CSV 的写出函数。
[D3 拦截] cmd/export.go:41 命令行参数 --delimiter
  实现位置里没有附原话引用的 flag:--delimiter。
  建议：删掉这个参数；如果你认为用户需要它，先问用户。
[D6 提示] internal/export/service.go:20 函数 Service.Export
  只把调用原样转给 s.exporter.Export。

处理方式：直接修改；或者向用户说明为什么要保留并询问。用户同意后，
用 requirement_save 把用户的原话填成这一处实现位置的引用。
不处理就结束时，这些问题会显示给用户。
```

每处命中都写明规则编号、档位、位置、原因和建议的改法。规则编号在文档、反馈、评估数据和代码里保持一致。用过的编号不会再分给别的规则。

## 会在哪里判错

归属和凭原话放行本身会在哪里判错，见 [任务和需求](requirements.md)，那些地方同样影响 D1 和 D2。下面是本文规则自己的问题。

**会漏判的地方：**

- **库的公开声明不受 D4、D5、D6 约束**，在以库为主的仓库里会漏掉一部分。
- **从外部数据写入的字段不检查。** 一个没人读写的 JSON 字段看不出来。
- **D1 只按名字找用法。** 新增的声明和别处的声明同名时，别处的用法也会被当成它的用法；`run`、`get` 这类常见的名字几乎总能找到“用法”。
- **语言支持不到的规则不检查**，比如没写对外入口写法的语言不做 D3，见 [语言支持](languages.md)。

**会误判的地方：**

- **Agent 改到一半就停下来**，比如中途停下来问用户问题，新函数可能还没接上调用方，D1 会报出来。按 [产品需求](product.md) 的默认行为，拦过一次之后 Agent 照样可以停下来，这处命中等 Agent 接上调用方后自然消失。
- **框架按约定调用、又不在隐式调用清单里的声明**，D1 会报出来。Agent 向用户说明之后，凭用户的原话放行。
- **用户在 Agent 工作期间自己改了文件**，这些改动也算进 diff，可能命中 D2。
- **接口确实是为下一个任务准备的**，比如下一步就要加第二种实现，按规则仍会被拦。用户说一句“保留接口，下一个任务要加 JSON”，就能凭原话放行。

## 例子

例子用 Go 写，规则对各种语言都一样。例子里的代码只保留和判断有关的部分。

### OD-01 只有一种实现的接口

- **用户原话**：给 export 命令加一个导出 CSV 的选项。
- **改动**：本文开头的 `Exporter` 接口和 `csvExporter`。
- **实现位置**：R1（原话需求）列了 `flag:--format`（附引用）、`cmd/export.go:runExport`、`internal/export/exporter.go:NewExporter`。
- **结论**：拦截。D4 命中 `Exporter`：非测试代码里实现 `Exporter` 的只有 `*csvExporter` 一种。D3 命中 `--delimiter`：没有附原话引用。

### OD-02 项目惯例放行

- **用户原话**：加一个按日期查询报表的接口。

- **已有代码**：工作区的 Go 代码里已有 8 个接口，其中 6 个在非测试代码里只有一种具体类型实现。
- **结论**：放行。E1 生效，放行记录写明“已有 8 个接口，其中 6 个只有一种具体类型实现”。

### OD-03 值不变的参数

- **改动**：

  ```go
  func writeCSV(w io.Writer, rows []Row, delimiter rune) error

  writeCSV(os.Stdout, rows, ',')
  ```
- **结论**：拦截。D5 命中参数 `delimiter`：所有调用处都传常量 `','`。

### OD-04 对外入口经用户确认后放行

- **用户原话**：先是“给 export 命令加一个导出 CSV 的选项”；被问到分隔符后，用户回复“加个分隔符参数吧，有人要用分号”。

- **第一次检查**：实现位置里没有 `flag:--delimiter`，D3 命中，拦截。
- **第二次检查**：Agent 把 `flag:--delimiter` 加进 R1 的实现位置，引用“加个分隔符参数吧”。代码没变，但需求版本变了，所以重新检查，结论是放行。任务完成时，报告列出“--delimiter ← 加个分隔符参数吧”。

### OD-05 顺手修改

- **用户原话**：给 export 命令加一个导出 CSV 的选项。

### OD-10 没人区分的哨兵错误

- **用户原话**：导出时没有数据要给出明确的报错。
