# 过度测试判定

TaskBelay 分别检查测试代码和验证过程。测试代码检查帮助 Agent 精简用例；验证过程检查帮助它选择合适的范围和时机。最终保留哪些测试，要看行为、断言和运行条件。

## 检查怎样运行

静态检查先列出新增和修改用例、需求关系、风险和 mock 断言。动态检查逐条运行用例、采集覆盖率，再按需要做有限变异。动态检查由项目设置开启，或者通过 `check_run(depth="tests")` 主动请求；普通停顿不启动测试。

用户已配置的项目环境、工具版本、命令前缀和测试选择规则由语言 Runner 使用。运行环境、准备步骤和是否可并行按项目配置确定。没有配置动态检查时，TaskBelay 使用已有验证记录和静态分析反馈。

## 用例与风险建议

一条可单独运行的测试是一条用例，参数组和子测试分别计数。只有新增用例是精简建议的对象；修改用例参与比较，已有未改用例可在项目支持时作为比较基准。

需求代码见 [任务和需求](requirements.md)。风险统计中，改动声明看改变行为的行，未改动但被点名补测试的声明看整个声明。只改名字、文案或简单取值的需求，通常不额外增加测试；其他需求建议一条主路径，并考虑下列加项：

| 风险 | 建议增加的用例 |
| --- | --- |
| 并发、写文件或数据库、解析外部输入 | 每类两条 |
| 执行外部命令 | 一条 |
| 每四个分支点 | 一条 |

每类风险计一次，建议总数最多八条。这个数字用于提醒 Agent 复核测试投入；配置、安全默认值和删除旧行为等需求，仍可有需要保留的回归测试。

## 测试代码规则

### T1 没观察到需求代码覆盖（提示）

有效覆盖数据中，新用例未执行需求代码时，提醒 Agent 核对用途。先区分确实在测其他行为，还是测试通过子进程、外部进程、配置或“旧入口已不存在”来验证需求。覆盖采集失败不等于覆盖为空；无法定位时列为未检查。

### T2 可能重复的用例（提示）

1. 按需求代码的行覆盖集合分组。同组只表示行覆盖相同，尚不能说明执行条件或断言相同。
2. 仅在有效覆盖涉及的行为变化范围内做变异：比较运算符互换、条件取反、整数加减一、加减互换、去掉逻辑非。去重后每组最多二十个。
3. 先在固定快照的临时副本里运行基线。基线通过，且执行的是副本代码后，再逐个变异。编译失败、工具错误和基础设施失败不算用例发现错误；有效变异引发测试断言失败才算发现。
4. 比较各用例发现的变异集合，用贪心方法给出能保留同等发现集合的一组候选。数量相同时优先修改用例，再按源码位置。最多运行四十次变异用例组合，达到次数或时间预算就保存已有证据。
5. 反馈候选及其共同覆盖、各自断言和发现集合，Agent 核对后决定是否合并。

没有有效变异、没有用例发现变异或检查未完成时，只记录观察，不提出删除清单。不同输出、输入契约、权限、幂等、副作用、时序和共享状态由各自断言守护，不能由相同的行覆盖替代。

### T3 超出风险建议（提示）

一条需求的新增用例超过建议数时，展示数量和风险来源。已经按用户要求保留的用例单独计数，不把建议数当作上限。

### T4 只覆盖简单声明（提示）

用例只覆盖 getter、setter 或只填字段的构造函数时，提醒 Agent 查看是否已有行为测试覆盖它，以及默认值、公开约定是否值得单独守护。

### T5 只检查 mock 调用（提示）

断言只有 mock 调用次数、顺序或参数时，提醒核对行为结果。若调用约束本身就是需求，例如不能重复扣款，说明用途后保留。

### T6 缺少需求验证（提示）

有实际逻辑的需求没有新增或修改用例覆盖时，提醒核对已有用例、黑盒测试或其他验收方式。已有验证已守住新行为时，可以直接说明，不要求为消除提示另写测试。

用户明确要求某些用例时，将用例或测试函数列入实现位置并记录来源。用户直接修改过的测试按当前内容分析，混合修改的用例不列入删除候选。

## 验证命令

命令按 Agent 实际 shell 解析，复合命令按语法树分段。POSIX 变量赋值、`env` 和常见运行前缀只影响执行环境，不改变后面的命令类别。

| 类别 | 默认识别 |
| --- | --- |
| Go 验证 | `go test/build/vet`、`golangci-lint`、`staticcheck` |
| JavaScript、TypeScript 验证 | npm、pnpm、yarn、bun 的 test/build/lint/typecheck；tsc、jest、vitest、eslint、deno test |
| Python 验证 | pytest、unittest、tox、nox、ruff check、mypy、pyright |
| Rust 验证 | cargo test/build/check/clippy、cargo nextest run |
| Java、Kotlin 验证 | Maven、Gradle 及其 wrapper 的 test/verify/package/install/compile/build/check/assemble |
| 其他验证 | dotnet test/build、rspec、rake test、rails test、phpunit、swift test/build、ctest、cmake --build；make 的 test/check/lint/build/ci 目标 |
| 只读 | 读取和检索文件、查询位置、查看 git 状态或差异等无写入用法 |
| 其他 | 安装、启动服务、修改环境或文件，以及未识别的命令 |

只读类别按参数和重定向核对，命令名本身不代表只读。`sed -i`、`find -delete` 或输出重定向按实际写入处理。`npx`、`pnpm exec`、`bunx`、`uv run`、`poetry run`、`pipenv run`、`bundle exec`、`vendor/bin/`、`./` 和 Python 的 `-m` 前缀按后续命令分类。

一条工具调用里有验证段，计一次验证；混有其他命令时照常记录，但不做重复拦截。记录实际工作目录、参数和环境标识。比较命令时按解析后的参数和执行目录比较，只规整语法层面的空白，保留引号内的空格和字面值。

## 验证过程规则

### V1 重复且可复用的验证（满足条件时拦截一次）

同一 session 上一次相同验证已完成并通过，且执行目录、参数、输入状态、工具与环境标识相同，Runner 又能确认这类命令的输入范围时，可以复用结果，拦截一次重复运行。带自动修复、生成文件或其他动作的命令不复用。

下列情况直接允许运行：用户明确要求重跑；上次失败、中断或结果未知；正在确认不稳定结果；工作区、工具、依赖或外部环境变化。无法核对环境的测试只提示上次运行情况。

Agent 用 `note_add` 记录本次重跑的原因，目标指向上一条验证记录；有用户要求时附消息引用。这条决定只用于接下来相同目标的一次运行，重跑前内容变化则重新判断。无需用户修改全局设置或换一种命令写法。

### V2 运行范围较大（提示）

按语言 Runner 的项目依赖关系给出受影响范围和较小的运行命令。项目有全量验收约定、改动涉及共享配置或分析无法覆盖的动态依赖时，Agent 采用对应范围并记录原因。

### V3 本轮验证较多（提示）

本轮实际运行第七次验证时提示一次，列出次数和最近结果，建议按一组相关改动验证。之后有新失败或用户要求才更新提示，不在每条命令前重复。

## 执行预算与结果

| 参数 | 值 |
| --- | --- |
| T1 至 T6 | 提示 |
| V1 | 满足条件时拦截一次 |
| V2、V3 | 提示 |
| 动态检查默认值 | 关闭，项目或当前任务可开启 |
| 单次动态检查预算 | 120 秒，包含准备、编译、基线和变异 |
| 每组变异数 | 最多二十个 |
| 每组变异用例运行次数 | 最多四十次 |
| 默认并行数 | 一；项目声明可独立运行后最多 min(CPU 核数, 4) |
| 风险用例数 | 主路径一条，加风险建议，最多八条 |

测试在固定快照的临时副本中运行，覆盖和构建产物写入临时目录。副本可复用项目工具和依赖；外部数据库、端口等仍按项目环境配置使用。默认串行，避免相互干扰。项目可以选择只做静态检查，或由 Agent 按已有流程运行集成测试。

预算到期时终止本次启动的进程组，释放临时资源，保存已完成的观察。用户继续修改时，本次结果标记为旧版本，不用于当前交付判断，也不立刻反复启动测试。

## 反馈示例

```text
[T2 提示] TestParseRange/1-3、5-5
  两条用例的需求代码行覆盖相同。
  有效变异中，5-5 额外发现了把 > 改为 >= 的问题。
  建议核对两条断言后，考虑保留 5-5；其他输入契约需要的用例仍然保留。
[V1 提示] 上次 pytest 结果未知
  当前无法复用通过结果，这次照常运行。
```
