# 过度测试判定

过度测试包括两种情况：一些测试用例没有检查其他用例未覆盖的行为；一些验证运行没有提供新信息。前者用等价类和变异结果判断，后者用验证输入记录判断。是否保留一条测试，以及本次是否运行它，是两个独立的决定。

验收依据、分组检验、合并信号和问题标识见 [算法核心](algorithm.md)，测试内容识别、命令记录和副本运行见 [输入与执行协议](languages.md)。

## 1. 用例与表格行

按 [输入与执行协议](languages.md) 学到的测试内容特征识别测试单元。一条可以单独运行的测试是一条用例。识别表格测试时，把同一个列表字面量中结构相同的元素分别作为一行：将元素的词序列规整（把字面量换成类别）后，哈希相同就视为结构相同。

在括号配对的布局中，测试可以在每个操作后写同样的 `must(err)` 或 `if err != nil { t.Fatal(err) }`，每次检查刚返回的错误。比较大括号内以圆括号或大括号结束的节点时，只收集后面紧跟逗号的项，以及前有逗号、后接容器结束大括号的末项。其余调用和分支留在所属用例内检查。编辑前比较和交付检查共用这项判断。

词汇分类不能证明单元是可运行用例。静态用例建议还要求单元具备完整的首行参数括号和实际主体；不能核对该形状的顶层测试单元记为用例结构未知，不据此提示补断言或合并。函数体内的条件、局部赋值等子节点不作为独立用例，也不逐个记录为未知；嵌套函数与闭包的限制见[过度设计判定](over-design.md)。表格行仍从已识别用例内部提取。该限制不证明其他写法没有测试，也不自动补跑验证。

同文件其他测试声明的主体直接调用某个声明时，仅凭它位于测试文件或含测试侧调用，不能确认它是独立用例。静态分析将这类声明作为辅助逻辑略过，不生成用途、相近测试或数量建议，也不参加用例计数；自身递归不算其他声明调用。调用按当前已读取内容中的名字核对，不补读调用链。该限制不能证明被调用声明不可独立运行，也不判断辅助逻辑是否多余。

只有本次新增、且全部来自 Agent 编辑的用例可以成为删除或合并候选。以下用例预先放入**保留集合**：起点已有的用例、作为验收依据的用例、用户点名的用例，以及含工作区更新的用例。

## 2. 等价类与边界值

用例正文中，名字后跟配对的圆括号，才按直接调用查找被测单元。只取生产文件中有完整参数和主体的同名声明。局部变量、类型注解和下标中的名字本身不能引入分段点。例如，调用 `EditAdvice(...)` 可以引入这个函数里的比较，给局部变量 `path` 赋值不能引入其他文件中同名节点里的比较。名字相同仍不能确定接收者或实际执行路径。只传递函数值、通过测试辅助函数间接执行等情形，可能无法定位被测行为。

被测声明中与比较运算符（`<`、`<=`、`==`、`!=`、`>`、`>=`）相邻的常量用于划分输入。数值常量把输入分成区间，字符串常量把输入分成“等于某个常量”和“都不等于”。

按词法识别出的类型比较每条用例、每一行的输入字面量。数值按区间分类，并标出它是否落在分段点 c 或 c±1 上。字符串按是否等于被测单元中的字符串常量分类，`"9"` 也按字符串处理。

- **重复候选**：比较同一被测单元、输入等价类和断言形状相同的用例或行。按字面量在代码中出现的顺序逐个比较输入。某个位置命中数值边界点时，另一处的相同位置也须命中同一个点。例如，代码判断 `n < 10` 时，`4` 和 `9` 都小于 `10`，但只有 `9` 能发现分界错移到 `9`。相近测试提醒会略过这对用例。
- **测试预算**：等价类数加边界点数。数值区间与常量相等分别计类，字符串分为各常量与其他值，重复边界点去重。新增用例超过预算时，展示超出的部分及其等价类；预算不是上限，超出的部分只是复核对象。

排序和二分查找使这一步的复杂度为 O(用例数 × log 常量数)。被测单元的结构置信度低、提取不到比较常量时，这一项为未知。

**断言。** 用例中没有出现任何学到的断言词时，提示它可能没有检查执行结果。正文词汇只反映词与测试样本的关联，回调参数、类型、夹具读写和失败处理也可能匹配；某个表达式的参数全是测试偏向词，不能说明它承担断言、只检查 mock 或缺少独特作用。编辑前和修改后的静态检查均不再据此单独生成用途提醒。调用约束本身就是需求时（例如不能重复扣款），仍须保留对应检查。

比较相近用例时，另外核对已识别测试侧调用的名称和完整实参，保留字面量。实际表达式不同，反馈指出差异并建议保留相应检查。表达式相同，只能确认这部分断言写法重复，还要核对输入、执行环境和副作用。表格行保留实际值供比较。Agent 可引用两处断言或明确的行为要求，说明删去用例会漏掉什么错误。已核对的独立副作用应保留；仅检查内部调用顺序时，应先确认顺序是否属于约定。依据范围见[用途核对](algorithm.md#用途核对)。

断言表达式从测试侧调用名读取到匹配的圆括号或方括号末尾，保留实参中的大小比较、嵌套表达式和连续的调用或下标。这里沿用词汇和括号形状定位，可能包含类型、回调和夹具表达式，不能据此确认调用语义或断言职责。仅有尖括号开头的形状无法确认调用边界，括号错配或没有闭合时也不能确认完整实参。任一用例含有未读全的测试侧调用时，这一次比较记为未知，只提示核对。比较表格行也带上所属用例的断言及其已知范围。

先登记既有和必须保留的用例，使它们即使排在新文件之后，也可作为比较对象。仅从后置参照发现的建议、断言差异以及未知断言只供核对，不增加撤回候选，也不根据 Agent 随后的删除动作给这些提示打分。

### 编辑前提醒

编辑请求能够核对出预期内容时，复用上述等价类和完整断言比较，在写入前提醒 Agent 核对本次新增用例，包括其中的表格行。目标文件以这次编辑前读取的实际内容为基线，已存在的测试作为参照，不因它们晚于任务起点而重新提醒；等价类与数量比较仍将既有用例内追加的行视为保留项。用户点名、验收要求及当前任务有效保留决定覆盖的用例继续保留。保留决定沿用现有用例编号、声明位置及 `test:` 位置匹配，不扩大到同文件的其他用例；决定撤销或随关联需求失效后重新按当前输入核对。保留的新增项继续参加数量计算，全部新增用例均已保留时不准备比较参照。

同一目标文件内，两个已识别用例属于同一层的同一个容器，且声明范围内只有用例名不同，写入前就可以指出具体副本。比较使用拟写入的原文，保留参数、字面量、注释、缩进和执行顺序。优先以已有或明确保留的用例为参照；若全部是本次新增，则以第一条为参照。只有其余未被保留的新增用例可以收到建议。名称、声明外的标注或夹具可能使相同正文承担不同检查。确认执行条件和验收职责也相同时，可以省去新副本及其单独运行。这项用途核对只依赖目标文件，即使跨文件参照随后失效或超时，仍可展示；跨文件的等价类和数量比较继续按其实际完成情况报告。

成对括号能定位同一张表时，预览比较独占一行、以逗号结尾的数据行。每列可以直接写数字或引号括起的字面量，也可以用一层具名字段组织这些值，例如 `Query{TaskID: "t101", Limit: 1}`。类型名和字段名均须为单个标识符，字段值含变量、调用或其他表达式时跳过整行。比较使用去掉行首尾空白后的原文，类型、字段名、值和排列都须一致。

新增用例中，以第一条相同的行为参照。已有用例仅在本次改动全部为整行插入时参与比较。同表有未改动的相同行时，优先以它为参照，即使它排在新行之后。如果同一份数据是这次才加进表里的，就保留第一条新行作参照，只提示后续相同的新行。用例内同时删改了原文、差异识别到移动，或用例已被点名保留时，跳过这项核对。提醒给出用例名、新行和参照行的行号，供 Agent 判断省去新行会失去哪项检查。行的位置、次数、顺序或共享状态有意义时应保留。此项只读取目标文件，跨文件比较未完成时仍可展示。

有些用例直接调用辅助函数来检查一组输入。若用例主体中连续几行都是同一个名字加圆括号的调用，每行原文和缩进一致，且实参符合上述字面量规则，预览也会指出拟新增的副本。只比较直接位于用例主体、独占一行的调用，两次之间出现其他操作、注释或空行就分开处理。每段连续调用优先以已有行作参照，沿用同表比较的插入和保留规则。若调用会推进状态、检查幂等性或依赖执行次数，仍需保留重复调用。

检查跨行匹配的首末片段时，如果输入只包含两个预期片段，中间仅有一个换行，这组数据就无法检验实现是否错误地附带了中间一行。预览沿用上面的调用、插入和保留规则，核对形如 `check("A\nB1\nA\nB2", "A\nB", "A\nB1", "A\nB2")` 的四个双引号文本实参。后两段必须不同，都含有第二项的跨行文本，且以一个换行连接后恰好等于第一项。只识别普通文本和显式的换行转义，每个用例只指出首处。若要检验中间内容被排除，可直接在原输入的两段之间放一行不匹配的文字，保留原预期。若要检验两段紧邻时的行为，保留这组数据。该提示只读拟写入的调用，实参各自的用途由 Agent 核对。

一个新用例可能需要检查同一段输出中是否分别出现两个名字。若长名字本身就含有短名字，只查这两段子串会漏掉“只出现长名字”的错误。编辑预览检查未被保留的新用例，定位形如 `if !obj.Contains(text, "LongName") || !obj.Contains(text, "Name") {` 的条件。条件可以有多项，须用同一个对象、方法和文本变量逐项查找，查找值为不含转义或插值的普通双引号文本。相邻两项中一个片段完整包含另一个较短片段时，每条用例只提示首处，并指出两项在条件中的位置。方法名按 `contains` 忽略大小写匹配，实际语义仍由 Agent 核对。若确实按子串查找且没有副作用，可用分隔符或上下文单独定位短名字。若只要求长片段出现，可省去短片段检查。该提醒只依赖拟写入的用例，跨文件比较未完成时仍可展示。

新增用例中，没有识别到断言词时，也在写入前提示核对用途。这不能证明用例没有检查结果，测试运行器和其他写法也可能承担检查。Agent 应核对用例承担的当前需求、实际输入、期望结果或副作用，以及删去会漏掉哪种错误；调用次数或顺序属于约定时保留。只有确认没有独特检查后，才考虑省去本次拟新增用例；依据不足时保留必要检查，不因此追加断言、辅助设施或验证。提醒复用已有词汇和完整调用识别，不要求存在可比较的等价类；测试身份未稳定、声明形状无法核对、用例已存在或属于保留集合时不提示。参数仅含测试偏向词不再触发独立提醒；是否只检查内部调用或缺少独特行为，需结合具体断言、相近用例或用途说明核对。

本批新增用例或表格行超过按等价类与边界点计算的建议数量时，也在写入前展示超出部分的位置、被测单元、等价类和建议数量，提示核对它承担的当前需求、不同输入、期望结果或副作用，以及省去会失去的独特检查。计数沿用上述算法，含已明确保留的新增项；数量只用于选择复核对象，不是上限，超过也不能证明用例多余或断言重复。只有确认没有独特检查后，才考虑省去本次拟新增项；依据不足时保留必要检查，不因此追加断言、辅助设施或验证。已有和明确保留的项不作为提醒对象；没有可计算的等价类与边界点时不补猜数量。

参照范围由已发布索引中的直接被测声明和引用这些声明的测试确定，不扫描全仓库。请求内的目标使用拟写入内容。请求外的测试文件须与索引一致，因为断言和调用的名字都可能影响比较范围。生产参照若只是修改了普通文件的内容，则按起点约定重新判断文件角色。仍属生产文件且可调用声明的名字集合相同时，用当前声明提取比较常量；角色、声明名集合或文件模式改变时，测试比较记为未完成。同一请求含删除或无法完整核对的目标时，略过可选预览，避免引用这批操作后可能已失效的参照。分类未稳定时不生成测试提醒。没有可比较的等价类时，仍可核对同文件的声明原文及新增用例的用途。尚未进入索引的新文件可能不在参照范围内。

准备直接参照时，名字和词的倒排成员已经包含文件路径，按该路径核对文件角色，不为取得路径逐条读取完整单元记录。同一名字的被测文件集合在本次准备中复用，重复出现的名字或同文件中的多个同名单元不增加读取。补齐其他直接目标时，只从既有测试文件读取词流。选中的参照都须核对当前内容，参照较多时仍可能耗尽预算。

编辑前先合并同一请求中已识别用例正文里的调用名，从已发布索引分批查找对应的声明。若每条待比较的新用例都调用同一个请求外生产声明名，既有测试也须提到它，才可能具有相同的被测目标。文件中缺少任一这样的名字时，仍核对该测试文件的内容和模式，但省去仅由它引出的其他声明。其余相关测试文件合并查询第一轮尚未查过的调用名。查找在这些直接目标处结束。批量读取沿用逐键读取的覆盖和删除规则，成功后才缓存空结果。读取失败或取消时，仍不发布不完整的比较。

查找哪些既有测试引用了被测名字时，编辑预览按名字批量查询包含这个词的测试文件。同一个文件有多个单元用到这个词，只取一次路径。旧索引没有保存这组路径时，仍从词倒排中筛选测试文件。两种读法都按上述条件补齐其他直接目标，并逐一核对参照的当前内容和模式。任何一批读取失败或取消时，只保留此前完成的提醒。

判断倒排成员所属文件是否为测试时，编辑预览直接使用发布该索引时已判为测试的路径集合。旧索引没有这份集合时，仍按成员路径分批读取文件元数据。两种方式都逐一核对最终参照的实际内容和模式，读取失败或取消时不发布部分比较。

编辑前先确定上述完整邻域的路径，保留已经按实际当前和拟写入内容计算的目标视图。请求外参照的当前内容和模式核对一致后，直接沿用发布索引中的文件分析、角色、测试身份和种子，加入两份视图；不为这些未变化的参照重新分类，不覆盖同批目标的实际内容或分类。参照失效、读取失败、取消或超时时，仍只保留此前完成的提醒，不能用不完整的邻域生成相近测试或数量结论。修改后的静态检查继续装配原有的完整前后视图。

在原有编辑前预算内，先用目标的实际当前与拟写入内容、已发布索引的测试分类和断言词完成新增测试用途核对，再完成目标内容上的设计核对；每步完成后核验索引仍有效。设计核对沿用已有入口、依赖、抽象、恢复和重复实现等规则，不把为测试比较补齐的文件加入设计分析范围。只有用途核对识别到本批新增、属于拟编辑内容且未被保留的用例时，才补齐参照并比较测试。仅编辑已有用例，或全部新增用例均已保留时，直接展示已核验的设计建议和目标文件内可确认的副本。数据行和连续调用均沿用所属用例的保留决定。只要有一条用例需要比较，仍为整批拟编辑内容补齐直接目标，保留项照常计入新增数量。这里复用已有身份和保留判断，不增加另一套用例识别。

目标设计核对失败或来不及时，只保留此前已完成的测试用途提醒，并说明其余核对未完成。目标设计核对完成并核验索引后，再比较重复实现；这一步读取失败、取消或超时时，保留已完成的目标设计和测试用途提醒，说明重复实现与测试比较未完成，不采用不完整的重复候选。设计核对全部完成后，参照核对失败或测试分析未完成时，保留已完成的设计和测试用途提醒，说明测试比较未完成；没有完成的比较不产生相近测试或数量建议。索引未就绪、用途核对本身未完成时略过提示；编辑证据仍然保存，交付检查仍按当前快照分析。完整预览成功时按原有候选顺序合并设计和测试分析结果，同文件副本的建议优先展示，同一用例不再重复占用反馈预算。提醒按完整条目放入字符预算，放不下的条目略过，仍可选取后续较短的候选；不截断事实或保留条件，也不指向没有保存的预览正文。

相近测试反馈展示两处位置、被测单元、等价类以及已知的断言相同、不同或未知。测试提醒只通过编辑前附加上下文提供，不拒绝编辑、不保存为运行结论、不启动动态检查，也不因没有提示而要求补测试。已识别测试不再同时收到通用的近似代码复用提醒，避免绕过断言比较给出重复建议。

## 3. 变异与保留集合

动态检查开启时，通过变异判断每条候选用例是否检查了其他用例未覆盖的行为。

### 变异算子

所有变异算子都在词流上操作：关系运算互换、算术运算互换、`&&` 与 `||` 互换、整数加减一、布尔字面量互换、删除改动块中的一整行。这些替换不保证在每种语言里都合法，是否能构建成功由项目自身的构建过程判断。无法应用到固定内容的变异记为无效；能够确认运行结果时，才将结果计入发现矩阵。如果无法从失败输出中区分构建失败与用例失败，结果保留为未知，不计入有效发现。按扩展名记录各算子生成的有效、无效和结果未知的变异数量，再对无效比例做二项检验；某个算子的无效比例显著偏高时，停止用它生成变异。

### 范围与抽样

只在需要保留的变更簇上生成变异：有撤回试验时，取试验确认需要保留的簇；没有撤回试验时，取精简建议可信度低的簇。按变更簇和算子分成若干层，依各层大小按比例随机抽样，逐个加入变异。

用 Good–Turing 估计决定何时停止抽样。每个变异都有一个**发现集合**，包含发现该变异的所有用例；没有用例发现时，集合为空。将发现集合作为变异的类别：已抽样 N 个有效变异，其中 N₁ 个发现集合在样本中只出现过一次，下一个变异带来新发现集合的概率约为 N₁/N。发现集合相同的变异对约简没有区别，只有新的发现集合可能改变需要保留的用例。估计概率低于精度参数，或预算用完时，停止抽样。

### 发现矩阵

每次只将一个变异应用到副本，再运行一次验证。能从输出中解析出单条用例的结果时（见 [输入与执行协议](languages.md#运行结果)），一次运行就能记录所有用例是否发现了该变异，形成发现矩阵的一行；解析不出时，只记录整条命令的结果。运行次数等于抽到的变异数，由上面的停止规则和预算控制。

不能把多个变异放在一起运行，因为它们的效果可能互相抵消。例如，一个让结果加一，另一个让结果减一；同时启用时，检查两者之和的用例仍然通过，两个变异都会被误记为未发现。这样得到的错误矩阵会把有用的用例列为删除候选，还会报出不存在的测试缺口。

### 约简

1. **去掉冗余变异**：凡是发现 m₁ 的用例都发现 m₂ 时，m₂ 冗余（Ammann、Delamaro、Offutt，2014）。用位集计算。
2. **选出保留的用例**：从保留集合出发，用贪心集合覆盖补入能发现剩余变异的候选用例：每次选能额外发现最多变异的一条；数量相同时，按稳定顺序选择。近似比为 ln Δ + 1，Δ 是单条用例发现的最大变异数。
3. **确认**：未被选中的候选用例是删除或合并候选。把它们去掉后，在不含变异的副本中运行一次保留的用例，确认全部通过，排除用例之间的依赖；发现关系以逐个变异运行的结果为准。

不执行需求相关代码的用例、只测简单取值的用例、只断言 mock 调用的用例，都表现为没有发现任何有效变异，会在约简中成为候选。

发现集合相同，只说明对这批变异的检测能力相同。不同用例的断言还会检查输出约定、权限、幂等性、副作用、时序和共享状态。合并前，Agent 应核对这些检查是否仍被保留。

无法取得单条运行结果的用例仍留在保留集合中。删除范围重叠，或确认运行没有覆盖全部保留用例时，不发布精简集合。无效或结果未知的运行，不计入发现矩阵中的有效发现。如果整条命令运行成功，但无法取得每条用例的结果，只能记录“这组用例未发现该变异”，不能据此删除其中某条用例。

### 测试缺口

在需要保留的变更簇中，如果某个有效变异没有被任何用例发现，就有依据提示这里存在测试缺口。只有这种情况才提示补测试，并写明未被发现的变异位置。没有变异结果时，不因“有逻辑却没有新用例”提示补测试。

## 4. 验证输入记录

### 验证输入

一次验证的结果由以下内容决定，它们的哈希称为**验证输入**：

- 仓库内容，但去掉同时满足两个条件的文件：按词法统计属于文档（自然语言比例高）；没有被任何代码或配置引用。引用核对用 Aho–Corasick 一次扫描代码和配置的全部文本，包括注释，因为 Go 的 `//go:embed` 就写在注释中。文件路径、所在目录的任一级（仓库根目录除外）、文件名，或能匹配它的通配符出现在其中，都算引用。测试用 `filepath.Join("testdata", name)` 拼出路径时，`testdata` 目录下的文件因此仍计入验证输入。
- 实际目录、参数、标准输入内容、命令中的环境变量和工具标识。

非只读命令开始前先保存工作区观察，并用这次观察计算验证输入。每个工作区状态的内容摘要只确定一次。新出现的状态先按已发布的索引去掉未被引用的文档。索引尚未就绪或在时限内算不完时，改用该状态自身的标识，仍能比较内容完全相同的两次运行。

### 重复验证

Agent 准备重跑时，可以先按命令里的用例名或路径找回本任务的记录。即使命令只运行过一次、尚未归为验证，也能核对当时的命令、执行状态和输出。命令文本里引用一段测试命令也会匹配，阅读时要确认实际执行了什么。同一命令先失败、后通过时，可以用两次运行各自稳定的工作区快照核对中间的修改。如果一次运行前后的快照不同，可以比较这两个快照，查看当时改的是被测实现、用例还是其他文件。这份差异供 Agent 判断已有输出是否回答了当前问题，不能据此自动拦截重跑。查询方法见[任务账本](requirements-ledger.md)。

例如，交付时若只想确认即将提交的补丁没有引入 Git 报告的空白错误，可以先暂存要提交的改动，再运行一次 `git diff --cached --check`。若还要在开发中检查未暂存的改动，`git diff --check` 检查的是工作区与暂存区之间的差异。只暂存了部分修改、补丁后来又有变化，或者两次检查采用的空白规则不同时，前一次结果无法回答后一次的问题。工作区快照本身不能说明哪些改动已暂存。

比较修改前后的结果时，如果以前的任务已测过旧版，可以用 `task_get` 指定那项任务的 `task_id`，按命令或输出片段找到原始结果。例如，比较提示长度时，先核对被测文本、设置组合和计数方法。三者一致，旧输出也列出了所需的长度和限额，就可以直接引用旧值。如果还需要确认新脚本能复现已知结果，在旧版上运行它也有独立用途。查找和核对记录比重新计算更费时时，可以一次测完新旧两版。

如果只需确认新提示能否完整显示，可以先看余量最小的设置。各组采用同一限额、改动的文字在每组中都只拼入一次，而且计数和截断方式都没变时，可以从旧版未截断的最大长度推算新版上限。核对最终补丁，按取整前的单位计算增量，再向上取整。例如，旧版最长的一组占 319 个 token，公共文案恰好增加 1 个 token，各组就都能放进 321 个 token 的限额，可以省去为遍历设置而另写的脚本。若某个分支也改了拼接方式，或要确认 Agent 客户端实际显示了什么，就要针对相应入口另行核对。

只有单段命令可以拦截。同一命令最近一次运行已通过、本次验证输入与那次完全相同，且这条命令从未在相同输入上得到不同结果时，拦截一次，并附上那次输出。如果最近一次运行尚未结束，或在轮次结束时仍无结果，下一次请求照常运行。被拦截且未执行的请求不算一次运行。长输出保留开头和结尾。环境变量或外部服务有变化时，可用 `note_add` 写明理由后重跑。记录跨 session、跨 Agent 有效。

拦截前复核当前工作区状态。如果内容已变化，本次照常运行。上次验证通过后，只要账本记录了另一条可能改变外部状态的命令已经启动，即使还没有收到结果，或轮次结束时结果仍未知，也只提示上次输出，允许重跑。例如，另一个 session 已开始更新测试数据，验证读到的数据可能已经变化。被拒绝且未执行的请求不计入。命令没有调整环境变量时，只读查看和已报告用例名的单段验证可以排除。多段命令即使有测试输出，也可能包含写入数据库或调用服务的操作。中间的命令记录超出回看范围时也只提示。

多段命令按整条记录。即使 `go vet && go test` 与上次输入相同，也只给提示和上次输出，照常执行。分号、换行连接的命令（包括花括号和子 shell 内部）及前段不是只读查看的管道，最终退出状态无法证明各段都通过。用户要求重跑、有一次性重跑理由、上次未通过或结果未知，以及会写入或结果不稳定的命令，也都照常运行。

验证输入无法反映 TaskBelay 未观察到的外部变化。例如，用户在其他终端修改了环境变量、数据库或服务，TaskBelay 无法观察到这些变化；Agent 可按拦截提示写明理由后重跑。

试改前后分别运行同一条单段验证并通过，随后撤回试改时，最近一次输出对应的是试改后的内容。查找可引用的近期成功时，若遇到这条命令在当前完整验证输入上通过的记录，可以展示那次输出，供 Agent 判断原问题是否已经得到回答。本次请求照常放行。只在其间这条命令的每次运行都已通过、输入完整且运行前后工作区未变时引用。遇到可能改变外部状态的操作就停止回看。本次命令调整了环境变量时也略过这项提醒。

只改注释或空白，验证输入照常改变，因为 doctest、构建标签、lint 和格式检查都可能读取注释或空白。判断是否值得重跑时，先从同一命令的执行记录中选出工具标识和环境都与本次相同的记录，再依次比较。例如，检查工具升级后可能开始检查注释，旧版的通过或失败都不能说明新版会怎样处理。只有在当前工具和环境下，只改注释或空白的前后多次结果一致、从无反例，且按 Beta 分布估计的不一致概率低于精度参数时，才把这条命令视为对注释不敏感。最近一次运行也在相同条件下通过、本次只改了注释或空白时，提示重跑可能没有新信息，列出前后结果一致的比较次数并附上那次输出。命令照常执行。

这一复用条件比“整个工作区相同”更宽松，也有现成先例：`go help test` 说明，Go 的测试缓存要求测试二进制、可缓存的参数、测试打开过的模块内文件，以及读取过的环境变量保持不变，不核对数据库或网络等外部状态。

### 范围包含与通过规律

接手任务时，Agent 可以先从[任务接续摘要](handoff.md#摘要内容与长度)找到本任务最近一次验证请求，查看状态和已保存的输出，再决定是否需要重跑。

重复判断先读取同一命令的历史和其后的近期操作。对已识别的验证，需要比较其他命令时，再读取工作区的运行记录。按范围包含或通过规律给出提示时，每条来源命令只看最近一次实际启动或执行的记录。例如，整组测试先通过、随后重跑失败或尚未结束，运行其中一项前就不再引用第一次的成功输出。被拦截而没有执行的请求不算一次运行，其他命令仍可提供依据。选定要引用的记录后，才从账本中读取那次输出。

引用另一条命令的成功结果前，按[重复验证](#重复验证)的规则核对两次命令之间的操作。例如，整组测试通过后，另一条命令开始更新仓库外的测试数据。此时首次请求子包测试，或再次请求已识别的验证，都不能用更新前的成功结果提示本次运行可以省去。更新后若有新的成功验证，可以引用新结果。判断两条命令是否有稳定的通过规律时，仍使用历次可配对的已知结果。

首次请求某条命令、尚未按运行事实归为验证时，也可从上述已读取的近期记录核对范围包含。每条历史命令只考虑近期最后一次已启动或执行的记录，不跳过较新的失败、未知或未结束记录去复用旧成功。只采用已识别为验证、输入完整、运行前后工作区不变且已通过的单段记录；本次也须输入完整、单段、可完整解析且没有已识别的写入，内容、环境、工具、目录和 shell 必须一致。程序和其他参数仍按下述原规则比较。只提示已有较大范围的结果和记录编号，不拦截，不把尚未运行的本次命令归为验证，也不为这项提醒查询全历史。同一命令只要已经启动或执行过，后续请求就不再适用首次请求的提示，即使上一次还没有结果。

子包测试失败后，开发者修改代码并运行整组测试。再次请求子包测试时，如果整组在当前验证内容、工具和环境下已经通过，并且其输出报告了子包上次运行时识别出的全部用例名，TaskBelay 会附上整组的记录和输出，供 Agent 核对原先失败的检查。整组验证须在子包上次运行结束后启动。程序只查找近期记录，并沿用上述范围和外部状态规则。上次失败须发生在不同的验证内容上，有完整输入和可识别的用例。本次输入已有失败记录、同命令结果不稳定或本次调整了环境变量时，均略过提醒。用例名不能说明每个断言的结果，本次请求始终放行。

历史命令和本次命令都只有一段，且程序、子命令和其余参数都相同时，按显式路径判断范围包含。例如，`go test ./...` 的路径范围包含 `go test ./internal/x/...`。如果在相同验证输入下较大范围已经通过，TaskBelay 会在运行较小范围前提示，并附上那次的输出。

在同一目录先运行 `go test ./...`，再请求 `go test .` 时，可以先从上次输出里确认当前包的用例是否已经运行。两条命令须只在同一个参数位置分别写了 `./...` 和 `.`，且这个位置在第一个以 `-` 开头的参数之前。例如，`go test ./... -v` 和 `go test . -v` 可以比较。选项之后的点可能是 `-run` 的匹配表达式，也可能是传给被测程序的数据，程序不推断它的含义。递归命令的成功只说明它实际选中的目标通过，本次请求仍可照常运行。

每遇到一个非路径参数，就分开核对它前后的路径。以 `go test ./... -args -fixture ./pass.txt` 为例，只把包范围缩到 `./edge` 时，可以提示上次结果。如果同时把 `-fixture` 后的数据文件换成 `./fail.txt`，上次结果只对应 `./pass.txt`，就不提示范围已覆盖。如果某个位置只有一条命令给出了路径，也不提示覆盖。

组合命令中，每个路径只属于使用它的那一段。例如，`go test ./core && go test -run TestSmoke ./...` 只在 `./core` 运行了全部测试，其他包只运行了名称匹配 `TestSmoke` 的测试。整条命令通过，不能据此省去另一个包的完整测试。只要有一方是组合命令，就不按路径推断覆盖。整条命令的重复运行和历史通过规律仍分别按各自的条件判断。

递归范围按目录逐级比较。例如，在一个包里运行 `go test ./...` 可以覆盖 `./child`，其结果无法说明同级包 `../sibling` 是否通过。比较时保留路径开头的斜杠，以区分相对路径和以 `/`、`//` 开头的路径。忽略目录之间的空段和 `.`，保留 `..`。只有目标的开头与递归目录一致，且剩余部分不含 `..`，才提示范围包含。这样无需访问文件系统来判断经过 `..` 后实际落在哪个目录。

省略路径时，默认运行范围由程序决定。例如，`go test` 只测试当前目录的包。历史命令和本次命令只有一方带有可识别的路径参数时，TaskBelay 不根据路径推断覆盖关系。两次命令完全相同时，仍按同命令的验证输入和运行记录判断是否重复。

此外，从本仓库的运行记录中统计“A 通过时 B 也通过”的规律，例如“测试通过时构建也通过”。每组可配对的输入只计一次。A 在该输入上曾通过且 B 曾失败，就计为一个反例，即使后来 A 重跑失败或 B 重跑通过。A 和 B 都有成功记录、B 没有失败记录时，才计为一次一致。历史中从无反例，且按 Beta 分布估计的反例概率低于精度参数时，才采用这条规律。A 已在当前验证输入下通过时，请求运行 B 会收到可能没有新信息的提示，并附上 A 的输出。这些判断都不需要预先了解具体工具。范围包含和通过规律都由运行记录推断，不作为拦截依据。

## 5. 停止与报告

相近用例和表格行的静态反馈列出比较对象的位置、被测单元及等价类，并明确结构相同不代表行为检查重复。合并前核对输出约定、副作用、权限、时序和共享状态；存在独特检查时保留。动态约简也须保留抽样变异以外的行为检查，不能只因确认运行通过就直接删除。

是否保留测试，以及本次是否运行它，需要分别判断：本次没有运行某条用例，不表示它应该删除；历史测试也不会因为当前任务没有涉及，就成为删除或合并候选。

报告分别列出：重复候选和测试预算、发现矩阵的规模和确认结果、保留集合、测试缺口、拦截的重复验证与复用的结果、可能没有新信息的提示，以及未运行或未完成的部分。实际运行次数、拦截次数和复用次数分别计数；TaskBelay 自己在副本中的运行计入总成本，不靠减少 Agent 的命令数掩盖新增的开销。
