# TaskBelay 自进化维护机制

TaskBelay 以真实业务需求重演驱动改进：从已授权的 Git 历史中选取可还原的需求，在独立业务副本中从实现之前的基线重新开发，观察固定运行版 TaskBelay 的 hook + MCP 如何影响 Agent。根据具体过度设计、过度测试、误报、漏报及额外负担形成改进问题，有限复现、开发候选、独立复盘并决定是否采用；采用后继续真实任务。

主持 Agent 在授权范围内负责选题、还原需求、隔离历史参考、收集记录、安排独立复盘和作出采用决定；开发 Agent 只取得需求、基线和必要依赖，在固定运行版约束下自主实现。用户照常使用产品，提供方向和体验反馈；日常使用的可核对问题也进入同一改进流程。

## 三类长期资料

| 资料 | 维护内容 |
| --- | --- |
| [产品需求](product.md) | 长期目标、已约定的产品行为、成功标准 |
| [需求与问题池](backlog.md) | 统一选题入口，分别索引真实需求池（业务重演样本）和 TaskBelay 改进问题池，保存状态、证据缺口及结果关联 |
| `docs/iterations/NNN.md` | 每个实际启动的重演、调查或候选改进的一份记录，保存冻结的任务约定、当前步骤、证据索引、复盘和结论 |

本文件定义规则，backlog 保存两类池的入口和当前状态，迭代记录保存一次决定的依据。开工时建立记录，使用固定编号；调查、失败、部分完成和未采用的结果都按原编号保留。沿用文档、独立副本和现有记录即可，不为重演另建任务平台。

## 真实需求池与改进问题池

真实需求池保存可供重新实现的业务任务；改进问题池保存有证据或明确证据缺口的 TaskBelay 问题。一个重演样本可以关联多个问题，一个问题也可以引用多个样本；没有发现问题的重演仍是有效观察，不必制造修复项。

优先处理已经定界且影响核心判断的产品问题。现有 backlog 没有合适问题时，主持 Agent 继续从已授权的真实需求池选题，通过重演取得新证据。缺少可安全执行的真实任务时才因样本不足暂停，写明缺少的授权、需求信息或依赖；预算、运行接入和用户暂停等停止条件另按本文执行。

### 从历史还原任务

主持 Agent 在独立历史参考副本中只读查看授权范围内的提交、提交说明、相关文档和上下文，确认需求目标、相应实现提交之前的基线、验收条件和必要依赖。跨多个提交的需求须明确提交范围与依赖顺序；不能从现有信息区分需求和偶然实现细节时，先补齐资料或跳过。

任务启动前形成两份资料：主持和复盘使用的来源映射，以及开发会话使用的任务说明。后者只包含完整业务目标、可观察的验收、基线已有约定、允许使用的依赖与安全执行方式。开发会话看不到参考提交标识、参考 diff、后续代码或预期实现，也不能通过 Git 对象、日志、共享目录、上下文或其他会话取得答案。

历史实现用于核实需求与比较取舍，不是唯一正确答案。验收以业务目标和必要行为为准，允许不同的合理实现；参考实现中的顺手改动、旧缺陷和技术选择不自动成为任务要求。只选需求信息足够、依赖可隔离、能在授权预算内安全执行的任务。

### 业务副本的边界

- 原业务仓库始终只读。历史参考副本与开发工作副本分开保存、隔离访问，不共用可暴露后续提交的 Git 对象或 worktree；开发副本仅保留基线及任务所需内容，并单独建立本地历史。
- 工作副本不关联业务远端，不推送或回写原仓库，不触达真实业务系统。启动前核对远端、子模块、依赖下载地址、运行脚本与配置，确保命令只使用允许的本地或隔离依赖；不能安全替代的外部依赖记为阻塞。
- 不复制凭据或真实敏感数据，包括基线文件、Git 历史和本地配置中的秘密；需要的数据使用脱敏或合成的最小数据。必要依赖、已知缺口及受影响验收在任务说明中写清。
- 业务源码、历史参考与完整过程资料留在受保护的本机位置。公开的 TaskBelay 仓库只保存脱敏结论和最小可公开复现，公开资料中的样本与来源用本机映射关联。

## 从目标形成任务

“改进防止过度设计和过度测试的算法”是长期目标。主持 Agent 将真实使用中的现象转成范围有限的问题，依据调查结果确定修复方向。

没有有效反馈时，按这条链定位：

```text
有可判断的输入 → 检查触发 → 判断完成 → 反馈送达
                                      ↓
实际减少多余工作 ← 最终实现或运行发生变化 ← Agent 处理反馈
```

先定位证据缺失或行为不符的环节，区分触发、记录、判断和反馈处理问题。调查按证据得出结论：确认缺陷、解释正常行为，或列明仍需补充的资料。

每次复盘同时抽看与本轮问题有关的提示和放行情形，寻找误报、漏报及额外负担。以具体行为及其后果形成改进问题，关联需求样本、输入链和证据位置，不把提示数量作为收益。

## 改进问题状态与选题

```text
候选 → 待办 → 进行中 → 完成
进行中 → 暂缓 → 待办（补齐证据或提出可验证的新假设后重新定界）
候选 / 待办 / 进行中 → 关闭
```

- **候选**：有现象或疑问，尚待确定执行范围；原因未知时可先形成调查任务。
- **待办**：问题、来源、有限范围、验收和预算齐全。调查验收是能区分假设的证据；修复验收是可观察的行为变化。
- **进行中**：由一个迭代记录承接。具体执行、复盘和验证状态只写在该记录中。
- **完成**：满足该条目验收，分别记录调查结论、行为修复和核心效果。
- **暂缓**：写明阻塞原因和恢复条件。**关闭**：已证伪、重复或收益不足，写明理由。

一次只执行一个已定界任务。产品问题顺序是：阻断核心检查的断点 → 无法观察效果的缺口 → 已有样本的误报、漏报和重复负担。相同优先级按任务编号；前项等待外部证据时可以跳过。没有待办时，主持 Agent 最多对一个候选做有限定界；仍无可执行产品问题就选择真实需求重演，不反复挖掘旧现象凑轮次。

## 迭代状态机

```text
待机 → 定界 → 执行 → 独立复盘 → 验证 → 决策 → 收尾 → 待机
              ↑          │
              └─ 一次有明确范围的返工
任一步骤遇到阻塞、总预算用尽或收到暂停要求 → 暂停
暂停 → 核对现场和已保存结果 → 继续原步骤，或以无法判定收尾
```

| 状态 | 要完成的事 | 转移条件 |
| --- | --- | --- |
| 待机 | 读取两类池和最近结论，确认授权，选择产品问题或真实需求 | 有任务进入定界；无合适真实任务时说明恢复条件 |
| 定界 | 还原目标、基线、验收及依赖，固定隔离方式、比较方式、预算和停止条件 | 信息充分、可安全执行且能区分成功、失败与未知才进入执行 |
| 执行 | 新会话做业务重演、调查或候选实现，完整保存需求、diff、执行记录和工具反馈 | 达到交付点或开发预算即停止开发，进入独立复盘 |
| 独立复盘 | 另开会话先核对原始需求和产物，再对照工具反馈、Agent 回应及最终处置 | 已有证据足够则直接决策；缺一个可回答的问题则验证；明确实现缺陷可返工一次 |
| 验证 | 只执行定界或复盘已说明的验证，必要时对比新旧版 | 取得结果或用尽预算后进入决策 |
| 决策 | 分别判断业务验收、环境阻塞、检测有效性；有候选时再决定采用 | 记录证据、成本和未知，进入收尾 |
| 收尾 | 保存结论，更新两类池，完成已授权的提交、评审、合并与安全切换 | 采用版进入后续任务；满足继续条件才选下一项 |

### 定界时固定什么

每轮先记录：

1. **任务约定**：原始问题、要回答的假设、当轮范围、必要行为、验收、采用所需的改善及可接受代价、明确不做的事。
2. **代码基线**：仓库、分支、提交标识和起点未提交内容；业务任务另保存需求来源、历史参考范围、开发基线及依赖映射，参考信息仅主持与复盘可读。候选在独立分支或副本中开发，比较范围限定为本轮改动。
3. **运行基线**：实际二进制路径、版本与校验值，Agent、模型、思考强度、审核方式，hook / MCP 接入和关键设置。
4. **接入证据**：以每个目标会话实际发生的 hook 事件与 MCP 调用确认接入，记录二者实际使用的程序及独立数据位置；开始和结束核对版本与校验值，期间发生切换或接入缺失须单独说明，不能作为固定版本下的有效比较。
5. **投入上限**：每个业务任务填写开发时限、必要验收命令及次数上限；每个产品问题填写复现样本数、验证命令及次数、开发与复盘时限。默认一条相关输入链、一版候选加至多一次定向返工，验证优先一个复现和一个最接近的必要行为对照。各任务与独立复盘使用新会话，实际会话及返工投入均计入总预算。开工前将上限填成数值，并从总预算中预留独立复盘与收尾投入；开发预算用尽即转复盘，总预算用尽则保存状态，未完成复盘的候选不采用。追加投入需符合本次授权。

启动一段连续工作时，一次写清允许读取的业务历史、允许操作的副本、提交/评审/合并及新分支范围、安装与数据操作范围、模型/思考强度/审核方式和总投入上限。具体配置按本次授权固定并记录，不固化为永久产品规则。主持 Agent 自主完成范围内的常规选择；需要扩大授权时，保存准备结果并请求相应决定。

### 执行与复盘的分工

运行版 vN 在一个任务期间保持固定，用 hook + MCP 约束业务重演与 TaskBelay 候选开发；候选源码 vN+1 单独开发。每个任务和每次独立复盘均使用新会话，按本次授权保持模型、思考强度及审核方式一致。各任务、候选及对照组使用独立 TaskBelay 数据；需要比较已有缓存状态时，从同一份一致快照分别开始，不借用用户活动账本。安装后通过新会话核验统一版本的 hook 和 MCP。

开发 Agent 自主处理任务说明与工具反馈，主持 Agent 观察并完整保存原始需求、起点与最终 diff、命令及结果、会话执行记录和 TaskBelay 反馈。人工介入的原因及影响单独记录，按受干预样本复盘。复盘材料先提供需求、产物和执行事实，遮蔽工具判定及其处置理由；独立判断保存后再开放完整反馈，避免先按工具结论寻找理由。

独立复盘先看原始需求、最终 diff 和执行记录，判断完成、部分完成和未完成的验收项，区分环境阻塞与实现缺陷，并指出具体多余工作及必要行为；再看 TaskBelay 反馈，核对提示与放行中的误报、漏报、及时性和额外负担。业务完成程度、环境可执行范围、检测有效性分别记录：环境阻塞不等于检测失败，部分交付也不抹去已能核对的误报或漏报。Agent 的保留理由是待核对依据；有争议的样本保留分歧及所缺资料。

判定重复验证时核对前后代码、命令和环境输入。代码修改后针对受影响行为复测可以提供新信息，不能只因命令重复就认定过测。提示数、拦截数和建议采纳数只描述过程；实际减少了什么多余工作、保留了什么必要行为及付出了什么成本，才支持收益判断。

发现明确缺陷后，在预算内沿用同一任务及冻结约定定向返工，完整保留各次结果；返工后仍须另开新会话独立复盘。业务重演发现的 TaskBelay 问题关联到改进问题池，另行定界后修复，保持业务任务期间运行版不变。无关新问题进入候选，不扩入当前实现。

## 验证与采用

验证方法见 [算法评估](product-evaluation.md)。具体问题先有限复现，确认期望行为和维护成本后开发候选，再独立复盘并做能改变判断的必要验证。算法修改使用真实需求、事件、内容、账本状态到反馈的输入链和最小反例；合成用例可以补充边界，不能独自证明真实问题已解决。受影响的旧缓存、检查记录及规则版本失效行为也纳入检查，避免新实现正确却继续消费旧判断。

- **旧版与新版比较**回答这次修改是否改善了问题。固定需求、起点、模型、设置和初始数据状态，只改变 TaskBelay 版本。
- **关闭与开启比较**回答工具本身是否带来净收益，仅在已有记录不足以判断时使用。各组使用新会话和独立数据，从同一基线分别执行。
- 开始前规定样本、运行次数与停止条件；接入失败、超时和无改善也计入结果。调过算法的样本用于回归，采用后继续选择不同真实需求检查适用性；不要求每次都做完整开关对照。

| 决策 | 条件与处理 |
| --- | --- |
| 采用 | 本轮验收满足，必要行为和用户修改保留，目标问题有明确改善，新增负担可接受；记录适用条件 |
| 保留旧版 | 未改善、误伤必要行为或成本超过收益；保存候选、证据与拒绝理由，下一轮继续使用已采用版本 |
| 无法判定 | 接入、原始证据或比较条件不足；保留旧版，写明缺什么及再次进入任务池的条件 |

调查和业务重演以证据及结论交付，不要求每轮都有候选版。接入与记录修复按自身验收采用；核心效果单独依据多余工作、必要行为和使用成本的变化判定，收益未知如实记录。修好一个误报只支持该问题改善，不能宣称整体算法有效。

收尾时按实际结果更新改进问题池：验收满足则完成；问题被证伪或已确认不值得继续则关闭；证据不足、方案失败且暂无新办法则暂缓，写明恢复条件。补齐证据或形成可验证的新假设后，原条目重新定界为待办，沿用编号并关联失败迭代。业务样本状态按 [真实需求池](backlog.md#真实需求池) 回填。

采用版本包含两个步骤：先保存被接受的源码与可复现构建标识，再在已授权的安全时点切换运行程序、核对实际接入并开启新会话。共享安装仍被用户任务使用时，迭代停在“收尾：运行版待切换”，记录已采用的代码和切换条件；完成切换后，以采用版开展后续真实任务。未采用或无法判定时继续使用旧版。任务是否完成按冻结验收判断，安装状态单独记录。切换前保留可恢复程序和一致的数据备份；涉及数据格式变更时，确定程序与数据配套恢复的办法。

主持 Agent 在任务启动、发现关键证据或阻塞、采用决策、切换等待及本轮收尾时主动汇报，说明已完成、未知和下一步。提交、评审、推送、合并及建立后续分支按本次授权分别推进；约定合并 main 后继续的，先完成评审和合并，确认更新后的 main，再从该基线建立下一工作分支。不能用“继续迭代”代替安装或合并授权；尚未授权的步骤记录为接续事项。

## 证据、样本与恢复

每轮完整保存原始需求、起点与最终 diff、会话与命令执行记录、TaskBelay 输入输出、独立复盘及验证结果。将 Agent 执行记录、实际产物和 TaskBelay 账本相互核对，记录证据缺口；本机保存完整过程，公开记录只摘取脱敏依据。

- **仓库内**：迭代记录保存脱敏结论、关键事件、版本与证据索引；允许保留最小可公开复现、正确性反例和回归测试。每个已确认的失败模式保留能够解释问题的最小样本。
- **本机**：原始资料放在受保护且不进入 Git 的目录，可使用 `.taskbelay-evolution/NNN/` 或独立受保护目录，记录来源、会话/任务标识、时间范围及文件校验值。启动前核实忽略与访问限制，参考资料不能置于开发会话可读范围；不收集凭据或真实敏感数据。
- **数据隔离**：任务和对照实验各用独立数据；需要旧状态时从同一份脱敏一致快照分别开始。启动前核验当前版本实际使用目标数据目录；不能隔离时暂停该实验，保持用户活动数据完整。
- **保留与清理**：回归用例按当前需求持续维护；临时探针、重复输出和无后续价值的材料可清理。活动迭代和仍被结论引用的证据保留；删除失效原始资料前先在记录中注明哪些结论将不能重放。

中断前保存当前步骤、最后有效输出、已用预算、返工次数、阻塞和恢复条件。恢复时读取活动记录，核对工作区、历史隔离、二进制、数据和已存在的输出；新会话接续原任务并计入剩余预算。复用已完成且来源可核对的结果，来源不明的结果记为未知。条件变化导致原比较失效时，以无法判定收尾，并明确下一次要固定什么。

## 何时继续，何时停止

收尾后只有同时满足“授权有效、预算有余、运行基线与接入明确、存在可执行产品问题或真实需求”才继续。

- 没有可执行产品问题：转向已授权真实需求重演；没有信息充分且可安全执行的真实需求才因样本不足待机，写明恢复条件。
- 历史隔离、安全依赖、实际接入或固定版本无法保证：暂停受影响任务，保存已取得证据，不带着失效比较继续。
- 连续两轮产品改进既没有新增可靠证据，也没有明确改善：暂停候选实现，复查假设和观察方法，可从不同真实需求取得证据后再定界，不机械重复失败方案。
- 真实任务中已看到设计和验证两方面的具体收益，必要行为保持且反馈负担可接受：按授权继续后续真实任务；日常反馈仍可形成改进问题。
- 用户要求停止或本次总预算用尽：保存当前状态，进入待机。

“本轮修好了什么”和“核心算法整体是否好用”分别汇报。一个样本能证明该样本改善，持续使用的新样本才支持更广的判断。

## 单轮记录格式

实际启动时按下面内容建立 `docs/iterations/NNN.md`。公开记录只填脱敏摘要和证据编号，完整需求、业务基线、来源映射、敏感路径及原始附件留在受保护的本机目录：

```markdown
# NNN：任务标题
- 任务：真实需求样本编号 / TB-xxx；类型：业务重演 / 调查 / 修复 / 效果验证
- 关联样本、改进问题及历史参考的受保护索引：
- 当前状态、更新时间、负责会话、下一步：
- 授权范围、总预算与已用预算：

## 冻结的任务约定
原始需求与来源；目标和假设；范围；必要行为；逐项验收；依赖和安全边界；验证、返工次数与停止条件。
## 基线与执行
开发基线及历史隔离；代码/运行版标识与首尾校验；模型/强度/审核及环境设置；独立数据与实际 hook/MCP 接入；起点、候选和最终产物；各新会话标识与受干预情况。
## 证据索引
关键事件、原始记录位置与校验值；复现/反例；失败、缺失与未知。
## 独立复盘与必要验证
先保存独立验收与多余工作判断，再核对反馈、Agent 回应和实际变化；所做验证及结果；真实输入链、最小反例及受影响旧缓存/规则版本。
## 结论与接续
逐项完成/部分完成/未完成；环境阻塞；检测有效性及收益未知项；采用/保留/无法判定的证据与成本；源码与安装状态；两类池更新；提交/评审/合并/后续分支接续。
中断时另记当前步骤、已用预算、已返工次数、最后有效输出、恢复条件和下一步。
```
