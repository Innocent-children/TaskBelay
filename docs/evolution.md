# TaskBelay 自进化维护机制

TaskBelay 通过真实任务发现自身不足，用可复核的改动改善判断，持续减少 Agent 的过度设计和过度测试。每次迭代围绕一个具体问题，验证改进是否保留必要行为、节省工作并降低使用负担。

主持 Agent 在授权范围内负责选题、准备、收集记录、安排独立复盘和作出采用决定；开发 Agent 在固定运行版 TaskBelay 的约束下完成任务。用户照常使用产品，提供方向和体验反馈；问题定位、任务拆分与逐轮验收由主持 Agent 完成。

## 三类长期资料

| 资料 | 维护内容 |
| --- | --- |
| [产品需求](product.md) | 长期目标、已约定的产品行为、成功标准 |
| [需求池](backlog.md) | 当前问题、证据缺口、优先次序、状态和结果索引；唯一选题入口 |
| `docs/iterations/NNN.md` | 每个实际启动的迭代的一份记录，保存冻结的任务约定、当前步骤、证据索引、复盘和采用结论 |

本文件定义规则，任务池保存当前事实，迭代记录保存一次决定的依据。开工时建立记录，每次迭代使用固定编号；调查、失败和未采用的结果都按原编号保留。

## 从目标形成任务

“改进防止过度设计和过度测试的算法”是长期目标。主持 Agent 将真实使用中的现象转成范围有限的问题，依据调查结果确定修复方向。

没有有效反馈时，按这条链定位：

```text
有可判断的输入 → 检查触发 → 判断完成 → 反馈送达
                                      ↓
实际减少多余工作 ← 最终实现或运行发生变化 ← Agent 处理反馈
```

先定位证据缺失或行为不符的环节，区分触发、记录、判断和反馈处理问题。调查按证据得出结论：确认缺陷、解释正常行为，或列明仍需补充的资料。

每次复盘同时抽看与本轮问题有关的提示和放行情形，寻找误报、漏报及额外负担。以具体行为及其后果形成任务。

## 任务池状态与选题

```text
候选 → 待办 → 进行中 → 完成
进行中 → 暂缓 → 待办（补齐证据或提出可验证的新假设后重新定界）
候选 / 待办 / 进行中 → 关闭
```

- **候选**：有现象或疑问，尚待确定执行范围；原因未知时可先形成调查任务。
- **待办**：问题、来源、有限范围、验收和预算齐全。调查验收是能区分假设的证据；修复验收是可观察的行为变化。
- **进行中**：由一个迭代记录承接。具体执行、复盘和验证状态只写在该记录中。
- **完成**：满足该条目验收，分别记录调查结论、行为修复和核心效果。
- **暂缓**：写明阻塞原因和恢复条件。**关闭**：已证伪、重复或收益不足，写明理由。

一次只选一个可执行条目。顺序是：阻断核心检查的断点 → 无法观察效果的缺口 → 已有样本的误报、漏报和重复负担。相同优先级按任务编号；前项等待外部证据时可以跳过。没有待办时，主持 Agent 最多对一个候选做定界；形成有价值的问题后开工，其余情况待机并等待新证据。

## 迭代状态机

```text
待机 → 定界 → 执行 → 独立复盘 → 验证 → 决策 → 收尾 → 待机
              ↑          │
              └─ 一次有明确范围的返工
任一步骤遇到阻塞、达到预算或收到暂停要求 → 暂停
暂停 → 核对现场和已保存结果 → 继续原步骤，或以无法判定收尾
```

| 状态 | 要完成的事 | 转移条件 |
| --- | --- | --- |
| 待机 | 读取任务池和最近结论，确认本次工作授权与可执行任务 | 有任务进入定界；否则说明等待什么反馈 |
| 定界 | 固定需求、基线、验收、假设、比较方式、预算及停止条件 | 能区分成功、失败与未知才进入执行 |
| 执行 | 新会话做调查或候选实现，保留原始输入、diff、运行记录和工具反馈 | 达到交付点即停止开发，进入独立复盘 |
| 独立复盘 | 另开会话先核对原始需求和产物，再对照工具反馈、Agent 回应及最终处置 | 已有证据足够则直接决策；缺一个可回答的问题则验证；明确实现缺陷可返工一次 |
| 验证 | 只执行定界或复盘已说明的验证，必要时对比新旧版 | 取得结果或用尽预算后进入决策 |
| 决策 | 分别判断任务是否完成、候选是否采用、核心效果是否得到支持 | 采用、保留旧版或无法判定，都进入收尾 |
| 收尾 | 保存结论与证据，更新任务池，完成已授权的版本切换 | 满足继续条件才选择下一项，否则待机 |

### 定界时固定什么

每轮先记录：

1. **任务约定**：原始问题、要回答的假设、当轮范围、必要行为、验收、采用所需的改善及可接受代价、明确不做的事。
2. **代码基线**：仓库、分支、提交标识和起点未提交内容；候选在独立分支或副本中开发，比较范围限定为本轮改动。
3. **运行基线**：实际二进制路径、版本与校验值，Agent、模型、思考强度、审核方式，hook / MCP 接入和关键设置。
4. **接入证据**：以目标会话实际发生的 hook 事件与 MCP 调用确认接入情况，保存对应记录。
5. **投入上限**：检查哪些样本、运行哪些验证、最多返工几次，以及耗时或调用预算。默认只追一条相关调用链、最多两个相关会话、一版候选加一次定向返工；实现验证优先选择一个复现和一个最接近的正常反例。主持 Agent 根据问题在开工前调整并写明理由，执行中达到上限就收尾。

启动一段连续工作时，一次写清允许操作的电脑与仓库、提交与合并范围、安装与数据操作范围、总投入上限。主持 Agent 自主完成范围内的常规选择；需要扩大授权时，保存准备结果并请求相应决定。

### 执行与复盘的分工

运行版 vN 在本轮保持固定，用 hook + MCP 约束开发 Agent；候选源码 vN+1 单独开发。每个开发任务使用新会话，安装后通过新会话加载统一版本的 hook 和 MCP。开发 Agent 自主处理原始需求与工具反馈，主持 Agent 在过程中负责观察和记录。人工介入的原因及影响单独记录，按受干预样本复盘。

独立复盘先看原始需求、最终 diff 和执行记录，判断任务完成情况、具体多余工作及必要行为；再看 TaskBelay 的反馈，检查是否及时、正确、有用。Agent 的保留理由作为待核对依据；有争议的样本保留分歧和需要补充的资料。

发现缺陷后沿用同一任务定向返工，完整保留修复过程和各次结果。新发现但不阻断本轮验收的问题进入候选，下一轮再选。

## 验证与采用

验证方法见 [算法评估](product-evaluation.md)。小修先用具体样本证明行为改变；当要判断“工具是否使 Agent 少做多余工作”时，才在独立副本中比较自然开发结果。

- **旧版与新版比较**回答这次修改是否改善了问题。固定需求、起点、模型、设置和初始数据状态，只改变 TaskBelay 版本。
- **关闭与开启比较**回答工具本身是否带来净收益，仅在已有记录不足以判断时使用。各组使用新会话和独立数据，从同一基线分别执行。
- 开始前规定样本、运行次数与停止条件；接入失败、超时和无改善也计入结果。调过算法的样本用于回归，后续自然出现的新任务用于检查改进的适用性。

| 决策 | 条件与处理 |
| --- | --- |
| 采用 | 本轮验收满足，必要行为和用户修改保留，目标问题有明确改善，新增负担可接受；记录适用条件 |
| 保留旧版 | 未改善、误伤必要行为或成本超过收益；保存候选与拒绝理由，下一轮继续使用已采用版本 |
| 无法判定 | 接入、原始证据或比较条件不足；保留旧版，写明缺什么及再次进入任务池的条件 |

调查以证据和结论交付。接入与记录修复按自身验收采用；核心效果单独依据多余工作、必要行为和使用成本的变化判定，证据不足时记为未知。

收尾时按实际结果更新任务池：验收满足则完成；问题被证伪或已确认不值得继续则关闭；证据不足、方案失败且暂无新办法则暂缓，写明恢复条件。补齐证据或形成可验证的新假设后，原条目重新定界为待办，沿用编号并关联失败迭代。

采用版本包含两个步骤：先保存被接受的源码与可复现构建标识，再在安全时点切换运行程序、核对实际接入并开启新会话。共享安装仍被用户任务使用时，迭代停在“收尾：运行版待切换”，记录已采用的代码和切换条件；完成切换后，再启动依赖新运行版的下一轮。任务是否完成按冻结的验收判断，安装状态单独记录。切换前保留可恢复的程序和一致的数据备份；涉及数据格式变更时，提前确定程序与数据配套恢复的办法。

## 证据、样本与恢复

每轮只保留支持本轮判断的资料：原始需求、起点与最终 diff、会话与命令记录、TaskBelay 输入输出、独立复盘及验证结果。将 Agent 执行记录、实际产物和 TaskBelay 账本相互核对，记录证据缺口。

- **仓库内**：迭代记录保存脱敏结论、关键事件、版本与证据索引；允许保留最小可公开复现、正确性反例和回归测试。每个已确认的失败模式保留能够解释问题的最小样本。
- **本机**：原始资料放在项目内被 Git 忽略的 `.taskbelay-evolution/NNN/`，记录来源、会话/任务标识、时间范围及文件校验值。收集时创建目录并限制访问；提交资料先脱敏，凭据按秘密信息管理。
- **数据隔离**：对照实验各用独立数据；需要旧数据时从同一份一致快照分别开始。只有已验证当前版本支持目标隔离方式后才启动。需要共用用户数据目录时，在空闲窗口内按授权完成备份和切换，保持正在运行的用户任务数据完整。
- **保留与清理**：回归用例按当前需求持续维护；临时探针、重复输出和无后续价值的材料可清理。活动迭代和仍被结论引用的证据保留；删除失效原始资料前先在记录中注明哪些结论将不能重放。

中断后读取活动迭代记录，再核对工作区、二进制和已存在的输出。复用已完成且来源可核对的结果，继续尚未完成的步骤；来源不明的结果记为未知。条件变化导致原比较失效时，以无法判定收尾，并明确下一次要固定什么。

## 何时继续，何时停止

收尾后只有同时满足“授权有效、预算有余、运行基线明确、存在值得解决的可执行条目”才继续。

- 没有可执行问题，或证据依赖正在进行的用户任务：待机，写明恢复条件。
- 连续两轮既没有新增可靠证据，也没有明确改善：暂停实现，复查选题、假设和观察方法，取得新的可验证方向后恢复。
- 真实任务中已看到设计和验证两方面的具体收益，必要行为保持，反馈负担可接受，且没有优先问题：进入日常使用。后续反馈可以重新开启迭代。
- 用户要求停止或本次总预算用尽：保存当前状态，进入待机。

“本轮修好了什么”和“核心算法整体是否好用”分别汇报。一个样本能证明该样本改善，持续使用的新样本才支持更广的判断。

## 单轮记录格式

实际启动时按下面内容建立 `docs/iterations/NNN.md`，原始附件留在本机：

```markdown
# NNN：任务标题
- 任务：TB-xxx；类型：调查 / 修复 / 效果验证
- 当前状态、更新时间、负责会话、下一步：
- 授权范围、总预算与已用预算：

## 冻结的任务约定
原始问题与来源；假设；范围；必要行为；验收；验证与停止条件。
## 基线与执行
代码/运行版标识；环境与设置；实际接入；起点、候选和最终产物；受干预情况。
## 证据索引
关键事件、原始记录位置与校验值；复现/反例；失败、缺失与未知。
## 独立复盘与必要验证
先验收任务，再核对反馈、Agent 回应和实际变化；所做验证及结果。
## 结论与接续
任务验收；核心效果；采用/保留/无法判定及理由；源码与安装状态；任务池更新。
```
