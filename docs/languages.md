# 语言无关的输入与执行协议

本文件定义算法统一使用的输入：怎样将文件转换为词、单元和统计结果，怎样记录命令及运行结果，以及 TaskBelay 怎样在副本里运行项目已有的命令。算法不按语言分级，也不为各个语言分别维护规则表或专用执行器；所需约定从仓库内容中学习。

纯计算分别由 `units`、`repostats`、`changes`、`signals`、`validation` 完成，副本运行由 `dynamic` 完成；`check` 负责将这些处理与账本、Agent 接入流程衔接起来。

## 内容与改动

处理文件时，先读取它的字节内容、路径和版本。记录包括工作区标识、文件标识、blob 标识、范围、变更类型和来源。

- 新增和修改记录指向当前内容；删除记录保留编辑前的内容和来源。
- 移动和改名优先根据可核对的编辑记录更新位置；没有编辑记录时，使用 [变更簇](algorithm.md) 中的移动检测，只有前后内容能唯一对应时才更新位置。
- 对子模块与嵌套仓库，只记录其边界和引用的版本，不展开为普通目录；不能因为没有观察到某些内容，就假定它们不存在。
- 二进制内容不分词，按整体记录变化。

## 统一词法

一个确定有限自动机单遍扫描文件，复杂度 O(字节数)，把文本切成标识符、数字、字符串、符号和空白。字符串再分为两种：

- **短键**：形如标识符、不含空格的字符串，例如 `"delimiter"`。
- **自然语言句子**：含空格、常用词比例高的字符串，例如 `"field delimiter"`。

哪些引号用于划定字符串、哪些记号表示注释开始，都不预先规定，而是按下文的方法从仓库内容中统计得出。

## 版面树与单元

用栈对括号进行配对，得到一棵树；再按缩进层级得到另一棵树，选择更符合该文件结构的一棵：括号配对失败少，且缩进与括号层级吻合时，使用括号树；否则使用缩进树。树的节点叫**单元**；在大多数语言里，顶层单元就是函数、类型或配置段。单元的第一行叫**首行**，首行中低频的词是单元的名字。

配置文件同样建立版面树，每一层键是一个单元。

单元标识由内容、父级首行和同层重复首行的出现次序确定，不使用行号。空白或兄弟单元的内容变化不重置标识；内容相同但位于不同文件的单元分别记录。移动前后的内容能唯一对应时，才沿用原来的问题标识。

缩进树不把跨行词内部的续行另建为节点；例如多行字符串中的 SQL 缩进不能结束外层函数。续行上的代码仍归入原单元。名字的首行频率按实际行去重，不重复计算同一行形成的多个括号节点。首行存在多个顶层的“名字加圆括号”形状时，选取首行频率最低的名字，同频时取先出现者；不从参数括号内部取名，避免将接收者前的高频声明词当作方法名。

## 从起点学习的约定

以下约定按文件扩展名分组，从起点快照统计。词法计数与词流按 blob 缓存，起点 tree 变化时复用未变化的内容，再合并仓库计数和约定；约定变化时重新确定单元名字和置信度：

| 约定 | 统计方法 |
| --- | --- |
| 字符串定界符 | 在同一行内大多成对出现的引号字符 |
| 注释记号 | 常出现在行首、其后自然语言词比例高的符号序列 |
| 关键字与名字 | 在单元首行中文档频率很高的词是关键字（如 `func`、`def`、`pub`），低频词是名字 |
| 调用写法 | 标识符后紧跟左括号（含方括号、尖括号）的比例；比例低的文件不做实参分析 |
| 返回与抛出写法 | 单元最后一行最常见的开头词 |
| 测试内容 | 测试词汇、路径模式和运行输出中出现的用例名，见下文 |
| 约定入口 | 起点中定义后再没出现过的名字的模式，见下文 |
| 生成内容、锁文件和清单 | 文件开头说明生成来源的文字；几乎每个单元都含名字、版本号和哈希的文件是锁文件；很多单元含名字和版本号、不含哈希的文件是清单 |
| 依赖目录 | 自带清单和许可证文件的子目录 |

**测试内容。** 路径中含 test、spec 一类词的文件是初始样本；运行输出中报告的用例名所在的单元也是初始样本。运行输出指执行项目代码或工具得到的输出，只读命令显示的文件内容和状态不算在内。输出里出现一个名字，还要满足两个条件才算报告了用例：名字连同同一行里左侧或右侧的相邻文字不能在起点内容中原样找到，否则这段输出是照抄源码，例如经容器或脚本转发的读文件命令；同一条输出里至少有两个名字以相同的行格式出现，日志和报错中偶然提到的函数名没有这种成组的格式。只有含初始测试样本的扩展名参与测试分类，不把从代码学到的测试词汇直接推广到没有测试样本的文档或其他格式；扩展名只作为仓库内分组标识，不使用语言规则表。

分类以版面树的顶层单元为样本，子节点沿用所属顶层单元的分类，避免同一段正文被多层节点重复计入。分类特征为文件名词和首行标识符拆词，分别保存来源；不用正文中常见的调用和错误处理词判断测试身份。运行输出命中子节点名字时，将所属顶层单元作为初始样本。

固定词表和初始样本，采用词是否出现的 Bernoulli 模型，重复出现同一词不重复计权。交替执行以下两步：按当前划分，用 Beta(`Prior+1`, `Prior+1`) 估计两类中每个特征出现的概率，并用同样的先验估计类别比例；再按包含出现与未出现特征的对数后验比较分类，相等时保持原分类。初始样本始终属于测试。

非初始样本的单元被划为测试，还要求文件名里至少有一个词在测试样本中出现得更频繁。首行里的 `import`、`function` 一类词在测试和产品代码中都大量出现，只凭它们扩展，划分会逐轮扩大到整个仓库。两类样本数量悬殊时，平滑项会让从未在测试样本中出现的文件名词也得到正权重，这类词不作为正向证据。新建文件的路径含 test、spec 一类词时，同样按测试内容处理。

划分改变时，目标函数值严格增加；反复迭代，直到划分不再变化。计算预算用尽或计算被取消时，结果记为未知，不根据尚未完成的划分提出建议。分析当前内容时，沿用从起点内容中学到的模型及扩展名范围，不用新增内容重新训练；新出现的词也不加入起点词表。分类收敛后，另按顶层单元的正文标识符出现情况计算平滑对数几率比及其标准化值，用于定位测试侧表达式；这些正文统计不反过来决定测试身份，也不能区分断言、mock、回调、类型和夹具。其参数全部匹配测试偏向词，不作为独立的测试用途提醒依据，见[过度测试判定](over-testing.md#2-等价类与边界值)。

**约定入口。** 起点中定义后再没出现过的名字，要么对应死代码，要么由框架按约定调用。对这些名字的前缀、后缀、首行关键字和所在路径计数。如果某个模式中“只出现一次”的比例，经二项检验显著高于全仓库的平均比例，就将符合该模式的名字视为约定入口，例如 `Test*`、`main`。

## 结构置信度

每个文件有一个结构置信度，由版面树的一致性、该扩展名的统计样本量和调用写法比例组成。结构置信度作为一项信号参与 [合并信号](algorithm.md)：初始权重会降低结构信息少的文件所对应建议的可信度，之后再根据反馈拟合权重，不会因为信息不足反而得出更强的结论。

## 命令与运行记录

每次运行命令时，记录以下信息：

| 字段 | 内容 |
| --- | --- |
| 命令信息 | 程序、参数、实际目录、命令中的环境变量和 shell 写法 |
| 工具标识 | 程序的实际路径，以及它的内容哈希或版本输出 |
| 结果 | 是否启动、退出状态、输出、开始和结束时间 |
| 工作区 | 运行前后的工作区状态 |

复杂命令仍由原 shell 执行，TaskBelay 只记录解析结果，不改写命令。环境摘要只保存比较用的哈希，不保存凭据原文。

命令标识包含各段的程序、参数、目录、标准输入以及输出是否交给下一段管道。`python3 - <<EOF` 的脚本不同，或把管道改成 `&&`，都会改变标识。多段命令整体比较，重复时只作提示。合并输出流、丢弃输出和读取输入的重定向不算写入。管道前面各段都是只读查看时才算完整解析。分号或换行连接的多条命令只返回最后一条的状态，这也适用于花括号和子 shell 内的语句。

是否将命令归为验证，按实际运行情况判断，不使用命令名白名单。已完整解析且各段都只读的命令只是查看内容，不归为验证。其余命令的前提是运行前后工作区不变；在此前提下，输出中出现已识别的用例名，或者该命令在不同代码快照上反复运行，都可以归为验证。记录不足以判断时，按普通命令记录，不判断它是否属于重复验证。

首次请求的命令可以收到近期成功验证的范围包含提示，具体条件见[过度测试判定](over-testing.md#范围包含与通过规律)。这只说明历史路径参数包含本次范围，不是本次已经运行或通过的证据，也不改变上述验证分类。

## 运行结果

退出状态取自 Agent 提供的结构化结果；拿不到时为未知，不从输出文字猜测。

后续运行结束后，可根据结果更新对起点测试内容的识别，内容缓存保持不变。单条用例的结果从输出中解析：用例名来自测试单元；通过比较退出状态为零和非零的输出，学习表示“通过”和“失败”的词。某个词只在失败输出中出现在用例名附近时，将它视为失败标记。解析不出单条用例结果时，只记录整条命令的结果；输出没有正常结束时，也不能仅凭其中的成功标记认定通过。

## 副本中的运行

动态检查由项目设置开启，或通过 `check_run(depth="tests")` 请求。开启后，撤回试验、变异和探针按以下方式运行：

1. **只运行可信命令**：只使用 Agent 在本任务中已经在真实工作区运行成功的验证命令。
2. **写时复制的副本**：从固定快照导出副本，文件系统支持时用写时复制（APFS 的 clonefile、Linux 的 reflink），否则普通复制。
3. **确认命令读的是副本**：先在副本上运行一次命令，取得当前快照的运行结果；再故意破坏文件的字节内容，以这种哨兵改动核对命令是否读取该文件。命令仍然通过时，说明它不读这些文件或不在副本中运行，不能用它验收这些文件。结果按命令和文件缓存。
4. **不影响真实工作区**：运行前后核对真实工作区状态；发生变化时停止动态部分并报告。
5. **资源**：默认串行，项目设置声明命令可以独立运行时并行。以较低优先级运行，Agent 开始自己的验证时暂停。
6. **预算**：每次副本运行使用动态检查的剩余预算；进入搜索阶段前，先扣除为确认运行保留的部分。启动前，将该可信命令在真实工作区最近一次成功运行的实测耗时，与当前阶段的剩余预算比较。如果预算不足以运行一次，或实测耗时未知，就不启动，结果记为未知，并说明剩余预算和实测耗时。等待结束、准备好副本后，再次核对剩余预算。历史耗时只用于判断是否启动，实际运行仍受当前阶段的截止时间限制。预算到期或运行被取消时，终止本次启动的进程组，清理副本，保存已完成的确认结果。

涉及数据库、服务、端口等外部状态时沿用项目已有的约定。Agent 自己的日常命令照常在真实工作区运行，TaskBelay 只记录。

## 普适性的验收

把整个仓库中的某个扩展名一致地换成另一个，或把工具名一致地改名，统计按新的扩展名重新分组，命令仍按行为归类，结果应与原来相同（同分时按稳定规则排序）。这检验算法没有语言分支。

不同语言的差异只体现在统计结果和结构置信度上：版面规整、样本多的文件得到更强的结论，结构信息少的文件结论更少。添加新的项目或工具，不需要新增规则。

## 输入不足时的处理

自然语言文件只有在存在完整句子、没有执行结构且不属于清单或配置时，才作为文档候选；无法确定的文件仍计入验证输入。通过注释、目录名或 glob 引用的文档，也计入验证输入。

无法区分构建失败与行为失败时，发现矩阵按 [过度测试判定](over-testing.md#发现矩阵) 保留未知。

在副本中运行前，核对工具文件的内容摘要、环境摘要和目录；不重复执行混合命令、包含写入操作的命令或无法完整解析的命令。macOS 使用文件 clone，Linux 使用文件系统 reflink；不支持时逐字节复制，Windows 使用逐字节复制。每次运行使用独立目录；通过 POSIX 进程组或 Windows Job 暂停、恢复和清理后代进程。
