# TaskBelay 终极形态与进化路线图

本文件规定 TaskBelay 的长期方向、各阶段目标和完成条件，后续调整和开发进展统一在本文件中维护。具体产品行为与实现设计见[文档说明](README.md)，开发要求见项目根目录的 [AGENTS.md](../AGENTS.md)。

TaskBelay 最终应成为一个融入 Agent 日常开发的工具：**帮助 Agent 用简单、可靠的方式完成当前需求，少做多余设计，少写和少跑无价值的测试，并去掉没有必要的防御处理。实现应当够用、可靠，也容易维护。**

项目始终围绕过度设计、过度测试和不必要的防御性编程展开。任务记录、改动与需求的对应关系，以及会话恢复，用于保存判断所需的信息，避免换一个 Agent 或会话后，又重复做已经决定省去的工作。这些配套功能是否继续扩展，也应看它们能不能减少多余工作。

长期目标分为五个阶段：**准确指出已经多做的部分 → 分清哪些实现有必要 → 在动手前提醒 → 给出可以一起执行的精简方案 → 减少反复提醒，让 Agent 及时停止多余工作。** 各阶段都以减少多余工作为目标，产品可以始终保持小型本地工具的形式，也不必证明每份实现都是理论上的最优方案。

## 从当前项目出发

当前产品定义已经把“Agent 容易做多”和“Agent 容易测多”列为主要问题。设计检查要指出具体可以省去或简化的部分；测试检查要分别回答：这条用例检查了什么行为，这次运行能提供什么新信息。后续应继续把这些判断做好。[产品目标与现有功能](https://github.com/Innocent-children/TaskBelay/blob/550ed29e7b68345288198891c33960607ed2d563/docs/product.md#L9-L61)

| 主要问题 | 当前已有能力 | 还需要改进什么 |
| --- | --- | --- |
| 过度设计 | 分析改动与需求的关系，检查对外新增项、间接层、重复和闲置代码；按需进行撤回试验 | 分清“与需求有关”和“实现需求所必需”，提出更简单的实现 |
| 过度测试 | 按等价类和边界寻找相近用例；按需进行变异分析；识别重复验证并复用结果 | 说明每条测试检查什么、每次运行要解决什么疑问，尽量在写测试或运行前提醒 |
| 过度防御 | 通用检查可能发现部分无关改动和新增项；撤回试验会保留疑似防御性分支 | 判断故障假设有没有依据，是否存在重复校验，以及重试、降级或补偿是否有必要 |
| 配套功能 | 保存用户要求、决定、当前内容、编辑来源和验证记录，生成会话恢复摘要 | 尽量自动提供前三类判断需要的信息，减少记录负担，避免 Agent 根据旧信息重复多做 |

当前能力的说明见：[过度设计定义](https://github.com/Innocent-children/TaskBelay/blob/550ed29e7b68345288198891c33960607ed2d563/docs/over-design.md)、[测试代码与验证过程](https://github.com/Innocent-children/TaskBelay/blob/550ed29e7b68345288198891c33960607ed2d563/docs/over-testing.md)、[当前检查编排](https://github.com/Innocent-children/TaskBelay/blob/550ed29e7b68345288198891c33960607ed2d563/internal/check/run.go#L96-L168)。这里描述的是 2026 年 11 月 5 日 main 提交 550ed29e7b68345288198891c33960607ed2d563 的状态；后文提出的是未来目标。

**当前还没有完整判断防御处理是否过度。** 文档规定，符合特定结构的短错误分支不参加撤回试验。代码根据排版结构和标识符识别这些分支，却没有判断相关错误能否发生、上游是否已经保证条件成立，也没有判断恢复操作是否必要。目前这些规则主要用于避免误删错误处理。[文档中的保护规则](https://github.com/Innocent-children/TaskBelay/blob/550ed29e7b68345288198891c33960607ed2d563/docs/over-design.md#L72-L82)、[当前形状识别](https://github.com/Innocent-children/TaskBelay/blob/550ed29e7b68345288198891c33960607ed2d563/internal/signals/analyze.go#L255-L289)、[动态候选排除](https://github.com/Innocent-children/TaskBelay/blob/550ed29e7b68345288198891c33960607ed2d563/internal/dynamic/run.go#L270-L296)

## 怎样判断一项工作是否有必要

三类检查都需要回答：**新增这些代码和测试，是为了满足哪项当前要求、解决什么实际问题？有没有更直接的做法？** 完成需求所需的调用连接、错误处理和合理的代码拆分，都可以由 Agent 判断，不要求用户事先逐项提出。

| 检查对象 | 应当回答的问题 | 仅凭什么还不能下结论 |
| --- | --- | --- |
| 功能、配置、依赖 | 当前使用者需要什么行为？已有功能为什么不够？ | 名字与需求相似，或 Agent 已登记实现位置 |
| 抽象与间接层 | 它隔离了哪种实际变化或依赖？直接实现会有什么具体问题？ | 只有一个实现，或代码行数较多 |
| 防御与恢复 | 防范什么情况？在当前约定下能否发生？应该由哪一层处理？ | 测试没触发、分支很短，或只是觉得这样更安全 |
| 测试代码 | 删除这条用例后，哪些需求、既有功能或约定结果会失去检查？ | 覆盖率增加，或两条用例发现了相同的抽样变异 |
| 验证动作 | 还有什么疑问？这次运行可能改变什么判断？ | 改过代码、准备交付，或习惯上总要再跑一遍 |

对每处可疑实现，应说明为什么需要保留、为什么可以精简，或者目前还无法判断。信息不足不等于实现多余，也不应因此自动增加测试。静态分析先找出值得核对的部分，Agent 再结合业务解释用途；TaskBelay 核对解释引用的来源、位置和实际记录。Agent 给出解释，不代表用户已经授权，也不代表解释已经得到确认。[现有算法边界](https://github.com/Innocent-children/TaskBelay/blob/550ed29e7b68345288198891c33960607ed2d563/docs/algorithm.md#L235-L243)

### 怎样区分必要和多余的防御处理

| 具体情况 | 应当怎样判断 |
| --- | --- |
| 外部输入不受信任，接口要求拒绝非法输入 | 在负责接收和检查输入的位置校验 |
| 文件读写等调用确实可能失败，调用方需要知道结果 | 保留必要的错误传递和资源处理 |
| 正常业务需要处理并发竞争、限流或幂等问题 | 按实际要求处理，不能都归为假想故障 |
| 内部状态已有明确保证，却在多处重复检查 | 核对所有入口，并确认保证始终有效后，再建议删除重复检查 |
| 用户未要求处理基础设施故障，却增加备用存储、降级链、补偿队列或自动恢复 | 核对这些新增行为为什么需要、会增加多少维护工作；默认不扩大故障处理范围 |
| 只为“更稳健”而吞掉异常或返回表示成功的默认结果 | 核对失败时应返回什么结果，优先考虑把错误交给调用方处理 |
| 为尚不存在的旧版本、未来插件或第二种存储增加兼容层 | 核对已有的兼容承诺和实际变化需求，再决定是否保留 |

按照用户级要求，方案设计默认数据库、Redis 等基础组件正常；只有明确要求时，才展开它们的故障处理。正常业务中的约束仍需满足，当前 API 要求处理的失败结果也仍需处理。

先检查新增加、维护代价较高的恢复机制，再检查已有明确保证时是否仍在重复校验。不能直接取消现有保护规则，然后批量撤回错误分支。撤回后测试通过，只能说明现有测试没有发现差异。

这三类问题常常连在一起：Agent 假设将来要支持多种实现，于是增加接口和配置，再为这些配置补兜底逻辑、编写测试，最后追加全量验证。TaskBelay 应尽早检查最初的假设有没有依据；如果不成立，就帮助 Agent 一起省去后面的工作。

## 终极形态下怎样完成一次开发

例如，用户要求“给现有命令增加 CSV 导出”。Agent 先沿用已有导出流程。当它准备增加通用插件层、额外格式配置或假想故障恢复时，TaskBelay 再提示它说明这些内容对应什么要求。理由不成立时，建议只做实现 CSV 导出所需的改动。

测试应检查实际要求的 CSV 格式和受影响的功能。判断相近用例是否重复，要看它们分别检查了什么结果。验证用于回答具体疑问，已有信息足够时就可以交付。文件写入失败时仍应返回错误；没有需求依据的自动重试和备用输出机制，则需要说明为什么增加。

交付前，工具重点列出仍可能多余、而且已有具体精简办法的内容。已经解释清楚并仍然适用的决定，不反复追问；换 Agent 后，也不重新添加已经决定省去的设计。用户照常提需求和开发，得到更直接的实现，少做无价值的验证，也减少后续维护工作。

## 五个阶段的目标

五个阶段按能力之间的依赖关系划分，说明各阶段要达到的目标和完成条件，不预设版本号、日期或近期开发安排。每个阶段都同时考虑设计、测试和防御处理，避免先做完设计检查，才开始处理另外两类问题。每阶段都可以交付独立可用的版本。

| 阶段 | 主要改进 | 阶段完成条件 |
| --- | --- | --- |
| 一 准确指出多做的部分 | 改进现有检查，给出具体精简建议 | 必要功能保持正常，省下的工作多于处理提示所花的精力 |
| 二 分清哪些实现有必要 | 核对设计用途、测试内容和错误发生条件 | 能区分外形相似、但有些该留而有些可删的实现 |
| 三 在动手前提醒 | 尽量避免写完再删、跑完才发现重复 | 少做多余工作，同时不要求每项操作先获批准 |
| 四 一起精简相关内容 | 同时处理多余设计及其专用配置和测试 | 方案完整，必要功能保持正常，检查方案所花的工作少于它省下的维护工作 |
| 五 减少反复提醒 | 满足要求后及时停止追加工作 | 后续任务中，多余工作和处理提示的负担一起减少 |

### 阶段一 准确指出已经多做的部分

**目标与交付**：让现有检查适合日常开启，优先改进对以下问题的反馈：未经要求的对外新增项、缺少实际用途的间接层、相近测试用例，以及输入未变时的重复验证。每处反馈说明检查了什么、涉及哪项要求、什么情况下判断成立，以及建议怎样处理。产品定义应补充如何判断防御处理是否必要，初期先给出有理由的建议。

**与当前实现的区别**：先检查已有算法找出的哪些问题确实多余，哪些只是外形相似，并修正容易误导 Agent 的提示。Agent 登记实现位置，只说明它认为这处实现与需求有关；提示不能将其描述成已经确认这处实现有必要。

**完成条件**：选择范围明确的实际任务，另行核对工具指出的问题和部分未指出问题的实现。检查应能发现具体多余工作，精简后功能仍满足要求，用户修改也被保留。省下的工作应多于阅读提示、解释和纠错所花的精力。如果主要收益仍来自会话恢复，就继续改进核心检查，不因此改变产品目标。

### 阶段二 分清设计、测试和防御是否必要

**目标与交付**：对设计，核对它要应对的实际变化，以及有没有更直接的做法；对测试，核对断言检查了什么、能发现什么错误；对防御，核对失败能否发生、该由谁处理，以及新增恢复操作会怎样改变结果。优先检查没有需求依据的配置和兼容层、重试和降级机制、已有明确保证时的重复检查，以及只照着实现细节编写的测试。

**实现方式与取舍**：复用已有需求、决定和问题记录，先让执行 Agent 针对少量可疑实现解释用途并给出出处，再由程序核对能够确认的内容。仅凭代码结构和用词无法判断错误能否发生时，就说明无法判断；不为得到确定答案而增加关键字黑名单、语言专用规则表或强制引入另一个模型评判。调整现有防御保护前，应先在产品和算法文档中分清哪些必须保留、哪些可以审查。

**完成条件**：能够区分看起来相近、实际用途不同的情况，例如为满足幂等要求而重试与凭空增加重试、外部输入校验与内部重复校验、必要的隔离层与只为将来扩展准备的空架子，以及检查不同副作用的用例与重复断言。Agent 接受建议不代表建议正确。依据不足时继续只提示，不扩大拦截。

### 阶段三 在写代码和运行命令前提醒

**目标与交付**：对已经能可靠判断的问题，在 Agent 开始编写代码或运行命令前提醒。结合已有需求、方案和编辑事件，检查准备新增的入口、依赖、抽象或恢复机制；准备增加大量相近测试或启动验证时，说明已有测试和运行结果是否已经回答当前问题。正常编辑不需要逐项审批。

**与当前实现的区别**：当前已有部分编辑前提醒和命令前重复验证判断。本阶段要改进判断质量，并逐步用于更多合适的情况，尽早避免“先加多余设计，再为它写测试、搭辅助设施”的连串工作。只有工具能观察到拟执行操作或相关事件时，才提前提醒，不能承诺识别 Agent 尚未表达的打算。

**完成条件**：与交付前才提醒相比，Agent 写出后又撤销的多余代码、没有独特作用的测试，以及不提供新信息的验证都减少，同时普通开发不需要逐项解释。如果某类提前提醒经常不准确，就继续在修改后给建议，等判断可靠了再提前。

### 阶段四 给出可以一起执行的精简方案

**目标与交付**：一起精简相互依赖的多余代码、配置和测试。针对一个具体问题，说明哪些设计、配置、重复防御及相关测试可以一并修改或删除，哪些功能必须保留。例如，删除未经要求的通用策略层时，同时处理它专用的配置和结构测试，并保留对实际导出功能的验证。

**实现方式与取舍**：复用现有变更簇和可选动态检查，重点说明精简方案，并核对相关测试检查了什么。只有具备适用的验收用例和检查命令，能够在副本中运行这些命令，并且时间和次数预算足够时，才执行动态检查；默认仍然关闭。撤回试验和抽样变异能帮助判断，但不能证明所有行为完全相同。用户改动和无法确认来源的内容保持当前状态。

**完成条件**：精简方案完整说明问题、替代实现和必须保留的行为，避免删掉一部分后留下无用配置、辅助代码或错误依赖。检查方案所花的总成本，应低于继续维护多余内容的成本。阅读差异已经足以判断时，直接处理；动态分析过于昂贵时，保留为有需要才使用的能力。

### 阶段五 减少反复提醒，让 Agent 及时停手

**目标与交付**：后续任务中少问已经解决的问题，更早发现本项目反复出现的多余设计、测试和防御。根据项目记录调整建议，减少无效提示、重复解释和无价值检查；需求改变后仍能重新判断。需求已经满足、必要验证已经完成时，帮助 Agent 停止继续抽象、补测试和追加防御。

**实现方式与取舍**：逐步改进已有仓库统计、反馈记录和会话恢复，不先建设通用经验平台。一次保留决定只在明确的范围内生效；不能因为建议被采纳、删除后没有恢复，就认定建议正确。出现反例时应降低相关建议的影响，某种做法也不能仅因项目经常使用就被认定为合理。

**完成条件**：在后来出现的新任务上，功能仍满足要求，多余工作持续减少，工具要求的记录、运行和用户关注也减少。如果只是漏掉更多问题，就继续改进判断；更复杂的学习机制没有额外收益时，就保持简单。成熟产品仍可以是本地 CLI、hook 和 MCP。

## 阶段之间怎样衔接，什么时候可以停止扩展

阶段一检查哪些现有反馈可靠；阶段二分清哪些实现只是与需求有关，哪些确实有必要；阶段三把可靠的提醒提前；阶段四让已经写出的复杂实现更容易精简；阶段五减少长期使用负担。防御分析和现有反馈改进可以并行。遇到具体问题时，也可以先做专项精简，不必等前面所有能力都完成。

这五个阶段不意味着五次重构。继续用现有记录保存有效要求和决定，由分析内核找出值得核对的实现，检查层汇总相关信息和建议，Agent 解释业务用途并修改代码。只有现有机制确实无法表达所需关系时，才增加数据或模块。

**产品已经有用、也足够解决主要问题时，就可以停止扩展。** 如果静态提示已经有效，动态精简可以一直按需使用；项目统计没有改善效果，就不继续增加学习机制；某项功能增加的负担高于省下的工作，就缩减它。

## 怎样判断每个阶段是否有效

| 检查方面 | 应当看到的结果 | 不能只看什么 |
| --- | --- | --- |
| 过度设计 | 经核对确实不需要的功能、配置、依赖和间接层更少 | 总行数或接口数量下降 |
| 过度测试 | 必要功能仍有测试检查，没有独特作用的测试和不提供新信息的运行更少 | 测试数、覆盖率或命令数的单独变化 |
| 过度防御 | 处理假想故障的代码和重复检查更少，必要错误处理仍然清楚 | 错误分支总数下降 |
| 判断质量 | 知道哪些建议错了，也知道哪些多余实现没被发现 | 建议采纳率或拦截次数 |
| 用户负担 | 少解释、少返工、少等待、少维护，工具增加的工作可以接受 | 记录量、会话恢复次数或功能数量 |

精简后如果原本正常的功能出错、用户修改被覆盖，或错误地宣称任务完成，就不能因为节省时间而接受这个结果。节省了什么、增加了什么成本，要分别说明；工具自身的计算、运行、模型调用和用户阅读也要计入。核对时既看提示过的问题，也看允许继续执行和没有提示的内容，避免通过少检查压低误报率，也避免把拦截次数当成成效。

专项核对根据当前问题选择有限任务，确定比较条件和何时停止，不机械地建设长期测试矩阵。项目仍只长期保留安装、打包等基础测试；临时验证按当次要求创建和清理。实际使用结果应注明平台、Agent 和适用条件；交叉编译与构造事件不能代替真实接入。[现行评估原则](https://github.com/Innocent-children/TaskBelay/blob/550ed29e7b68345288198891c33960607ed2d563/docs/product-evaluation.md)

## 保持产品简单

**TaskBelay 自身也应做到够用、可靠、易于维护，这一原则贯穿所有阶段。** 提高判断准确性时，也要保持操作和实现简单；新增能力应当省下更多工作，而不是增加更多记录、解释和维护负担。保存任务信息，是为了换会话后还能沿用有效判断；保存代码位置、运行结果和用户要求，是为了说明为什么建议精简。这些功能都应帮助减少多余工作。

通用任务编排、跨团队交换判断材料、云端协作平台、大型仪表盘和另建模型评判机制，都不作为默认发展方向。以后有具体需求时，再比较成本与收益。当前应持续问清楚：**这份设计、这条测试、这段防御和这次验证，在当前需求下究竟起什么必要作用？**
