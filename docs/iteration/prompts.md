# 助手协调与 Codex 执行说明

本文件供本对话中的助手按[自动化迭代方法](../iteration-method.md)推进 TaskBelay 产品进化。主控由助手承担：准备任务、安排独立 Codex 会话、核对证据、决定采用和下一批，并向用户汇报。用户不承担选题、裁决或逐批合并。第 1 节是主控清单；第 2–5 节是按角色发给 Codex 的模板。

所有 Codex 会话使用 6.1 Sol、medium 和自动审核，启动后核实实际配置。本次不按路线图阶段顺序选题；目标是可靠性、有效精简和总使用成本。主控在运行前交清材料，运行中只观察，不追加设计或测试指导。

任务运行没有额外行为 Prompt：用户消息只有 `task.md` 中的公开需求及外部契约，各组使用相同的正常项目指令。隔离、数据切换和版本安装在会话启动前完成。

## 1. 主控助手执行清单

先读方法、decisions.md、backlog.md 和已有批次记录。尚无任务集或计划时自动进入准备，不询问例行选择。主控填写模板中的参数，形成冻结计划后再派发运行；运行中不临时换仓库、换题或放宽验收。

`RUN_ROOT` 是本次重启新建并冻结的执行根目录，旧目录只读保留；主控派发前将模板中的占位符替换为实际绝对路径。

### 开始与准备

1. 记录原 main 提交及未提交文件的哈希，把本次方法和文档备份到 `<RUN_ROOT>/source/`。保留用户原工作区；启动前按用户明确要求核对并提交、推送 main 本次方法文档一次，后续不自动暂存或提交。旧运行和准备原样保留，新执行使用独立新目录，不复用旧无效结果。开发、构建和运行使用独立副本。
2. 固定 T01–T05 来自 TaskBelay，T06、T07 来自 notes-blog-web，T08 来自 WikiSkill。只在准备阶段用第 2 节组建具体需求、代码起点和验收，独立核对后由主控冻结。排除 xkw_projects，不自动启用 knowledge-bridge 或 KBVector。
3. 记录统一工具、依赖、模型配置和 TaskBelay 基础设置；沿用产品默认模式，动态测试检查关闭，启用组打开 debug。验证设置对各版本的实际含义一致；无法一致则本批不能把它们当可比结果。以批次编号为随机种子保存运行顺序。
4. 按方法第 4 节备份原数据、安装与接入配置，验证读取隔离。不能访问正确答案、其他组输出或原始会话；环境做不到且没有已获准替代时停止准备并报告，不把不同目录当作隔离。
5. B00 先比较 off、冻结 main、117 末端。冻结 V0 为固定成本参照，后续同时比较 V0 和上一批已采用快照，不以合并 main 或处理 PR 为条件。模板全部填完后冻结，写入哈希和主控核对结果。

准备时另由独立角色封存未参与选版的终验任务，登记访问和消耗；开发角色不得读取。若细节被用于改进，该任务转为开发资料，终验必须换新任务。用户已删除日常数据，先核实本次初态，不从历史备份恢复。

### 派发、运行与评审

- 为组建任务、每个开发条目、每次任务运行和每次评审分别启动新的 Codex session。只给该角色需要的材料，不继承其他组结论或主控完整历史。一次只运行一个 session，事件、输出和 stderr 存在对应运行目录。
- 在 `<RUN_ROOT>/build/` 的独立副本构建所需源码快照，记录提交、补丁/文件清单及二进制哈希。开发副本加载本流程的 AGENTS 例外和方法；对未提交候选按保存的补丁和新增文件恢复，核对一致后才构建。构建副本不开放给运行 session。
- 每次切换前确认相关进程退出；主控不接入 TaskBelay。建立全新 `~/.taskbelay/`，只写统一设置；启用组安装指定版本，不装组卸载 hook/MCP。结束后把本次完整目录连同 WAL/SHM、debug 归档、核对哈希，失败也保留。下一次仍从空目录开始。
- 评估副本只有固定起点及更早历史。按冻结顺序运行并记录完整对照标识，运行前后核对实际 hook/MCP 和版本。结束后由主控执行隐藏验收，整理原始与盲化时间线。接入失败修复一次后用新编号重跑，原成本计入且占用附加额度；正常零冗余结果不换题。
- 每个评估 session 上限 60 分钟，开发 session 90 分钟，评审 30 分钟。超时保存现场，按失败处理。单条目最多一次补充修正会话；主控只能在新会话交清已完成任务的缺陷和验收事实，不在运行中的会话追加实现方案。
- 第一步评审隐藏分组和 TaskBelay 提示，但保留编辑前后快照、删除前临时文件、命令输入/环境指纹、输出和状态。第二步再揭示提示，核对其影响。评审不得以自述替代实际操作。
- 拿不准且影响采用时只作一次独立复核；仍不明按未知和不采用处理。补跑严格使用方法第 5 节的固定触发条件和最多 8 次附加额度，不把普通争议交给用户。

### 结论、继续与汇报

- 主控逐项执行采用门槛：质量退化不得被其他任务改善抵消；失败、未完成分析和总成本均计入；token/历时同时受上一已采用版及固定 V0 的 110% 约束，单列相对 Off 净开销。提示数量不算净收益，按 E0–E3 及风险报告。保留结果不足或存在退化的原版本，回退失败候选；通过的组合恢复检查后保存为新已采用快照。
- 更新问题池、已定结论和批次记录，不要求更新路线图阶段。原代码仓库不提交、不推送、不合并；每批保存本地源码快照、补丁和恢复清单，下一批使用已采用快照接续。
- 每批结束归档数据并恢复日常安装和配置，向用户汇报问题、改动、三组结果、采用/放弃理由和下一步。无需等待用户回复，有合格条目且额度未用完就继续。
- 一次执行为 B00 加最多 10 个改进批次；没有合格问题、预算用尽、隔离/恢复失败等按方法第 9 节收尾。连续两个判断改动失败后只允许修复和精简。停止时交付可恢复的已采用版本和未解决项，不再自行寻找外围工作。
- 普通工程选择由主控承担。需要新的安全权限、不可恢复操作或其他必须确认的事项时，不执行依赖动作，安全停止并报告；不利用“自动化”绕过确认要求。

## 2. 组建任务集

助手只在开工批准备阶段或下一批准备新的留出任务时使用本模板，在 `<RUN_ROOT>/` 下启动新的 Codex session。仓库名单已确定；本模板只组建具体任务，不能重新挑选仓库。

```text
请在 <RUN_ROOT>/tasks/ 下组建一套评估任务，用来比较 Codex 在装和不装 TaskBelay 时完成同一个需求的差别。规则见 <TaskBelay 仓库路径>/docs/iteration-method.md 第 4 节，请先读。

要求：
- 首批固定 8 个任务，目录名 T01–T08，分两部分：
  - 选题任务 5 个（T01–T05），全部取自 /Users/innocent-children/GoLandProjects/TaskBelay 的 main 分支上 e46c40fe 之后的提交（只查看 e46c40fe..main 这个范围）。优先选改动范围较完整的功能或修复，一个提交里混了多件事的不选。
  - 外部验证任务 3 个（T06–T08，用于选版，不是终验），只从 /Users/innocent-children/WebstormProjects/notes-blog-web（TypeScript/React）和 /Users/innocent-children/PycharmProjects/WikiSkill（Python/React）组建，固定 notes-blog-web 两项（T06、T07），WikiSkill 一项（T08），准备完成由主控核对并冻结，运行时不再决定。
  - notes-blog-web 优先选独立可验收的前端交互；涉及后端时先固定隔离接口和合成数据。WikiSkill 使用合成会话及独立数据，不读取真实会话、日常安装目录或模型凭据。
  - 不读取或选用 /Users/innocent-children/xkw_projects/ 下的任何项目。knowledge-bridge 和 KBVector 是后续批次备选，本次不访问或使用；仓库或验收受阻就报告，不换仓库。
- 每个任务对应该仓库历史上真实做过的一次功能或修复提交。起点取它的父提交。公开需求及外部契约按普通用户提需求的口吻清楚说明结果，只说要什么结果；实现方式、测试和“保持简单”之类的要求都不写进去。验收依赖的外部接口、默认值或时限必须公开；每条断言在 requirement-map.json 写出公开依据。独立评审须排除对合法等价实现的误拒，不能只核对历史实现通过。
- 两部分各至少 1 个任务的正确实现本来就需要新增抽象、较多测试或大范围验证，类别标为“复杂度必要”。按需求来源和类别选题，不根据先跑出的浪费多少筛题；后续没有冗余的任务也保留。
- 每个任务包含 task.md、accept.sh 和 requirement-map.json，计算并记录内容哈希与任务版本。task.md 依次写：仓库地址或本机路径、起点提交、公开需求及外部契约（单独成段，将原样交给 Agent）、必须保留的行为清单、类别（普通 / 复杂度必要）、用途（选题 / 留出）、对应的真实提交（只给评审看）。accept.sh 在任务完成后的评估副本里执行，只检查对外行为（命令行、hook 和 MCP 的输入输出，或对应项目的对外接口），退出码 0 表示通过，不依赖具体的函数名、文件名或测试名。
- 逐个验证 accept.sh：在起点提交上应当失败，在对应的真实提交上应当通过。两项及公开契约审查都满足才算完成；准备阶段不满足时，只在同一已定仓库内另选需求。无法凑齐配额或反例就报告缺口，不放宽验收、不调用备选仓库；主控冻结后不能在本批运行中换题。

完成后向主控助手返回 T01–T08 各自的仓库、起点、公开需求及外部契约、类别、用途、任务版本和验收哈希，以及 accept.sh 的两次验证结果，由助手作独立核对并冻结。任务准备或核对未完成时，不启动评估运行，也不要求用户代为选题。留出任务的实现、验收和原始细节只交授权的组建/评审角色；开发 session 只接收选题任务资料。只在 <RUN_ROOT>/ 下写文件，隔离方式由主控助手在运行前核实。
```

## 3. 产出评审

助手准备好盲化材料后，将本模板交给未参与该次实现的全新 Codex session。

```text
请评审一次开发任务的产出。只依据下面的材料判断，不运行代码，不修改任务目录里的任何文件，结果写到 <运行目录>/review.md。

材料：
- 公开需求及外部契约：<task.md 中的公开需求及外部契约>
- 必须保留的行为：<task.md 中的清单>
- 起点提交 <提交>；任务完成后的目录 <运行目录>/repo。用 git diff <提交> 和 git status 查看全部改动，包括未提交和未跟踪的文件。
- 执行过的命令：<运行目录>/commands.txt
- 脱敏编辑和运行时间线、临时实现及测试删除前的快照：<运行目录>/timeline.jsonl 及其引用文件
- 验收结果：<运行目录>/accept.txt
- 已移除分组和 TaskBelay 提示的审查包；盲化或输入记录的缺口：<说明>

按需求和以下四类标准逐项核对，不评判路线图阶段或推进顺序。每一项写明位置和理由，并标“确定”或“拿不准”：
1. 多余设计：哪个入口、配置、依赖、抽象或防御处理没有需求依据，省去后需求照样满足。
2. 多余测试：哪条用例或哪组数据没有独立检查的内容，删去后哪些检查仍然覆盖它。
3. 重复验证：哪次运行的输入与此前某次相同，没有回答新的问题。
4. 必要工作缺失：哪项验收或必须保留的行为没有满足，哪种错误没有测试能够发现。

判断重复验证时核对两次运行之间的代码、断言、环境及输入快照；信息缺失则标为拿不准。最终 diff 已消失的临时实现也按时间线评审，区分写之前避免和先写后删。代码较多、断言相似或命令相同，本身不足以判为多余。外形相似但承担不同职责的实现、检查不同边界或不同故障路径的用例、修改代码后的重跑，都应保留。某一类没有问题就写“无”。最后给出四类中“确定”的条数。
```

## 4. 提示核对

只用于启用了 TaskBelay 的运行。产出评审完成后，助手另开一个 Codex session，交给它以下模板和第二步材料。

```text
请核对一次开发任务中 TaskBelay 给出的提示。不运行代码，不修改任务目录里的任何文件，结果追加到 <运行目录>/review.md 的“提示核对”一节。

材料：
- <运行目录>/review.md 中已有的产出评审
- TaskBelay 在这次运行中给出的全部提示和时间：<运行目录>/hints.txt
- Agent 的完整事件记录：<运行目录>/events.jsonl
- 任务完成后的目录：<运行目录>/repo

对每条提示写明：
1. 它指的内容是否确实多余：成立、不成立或无法判断，各用一句话说明理由。提示指向必要工作时明确写出。
2. Agent 看到后做了什么：写入前就没写、写了又删、保留，或没有反应。以事件记录里的实际编辑和命令为准，Agent 的自述只作参考。
3. 它是否让产出评审里少了一项多余工作，或造成了一项必要工作缺失。结合第一步保留的临时实现和时间线，区分实际撤销计划、先写后删与只查到了旧结果；另列工具查询/分析和处理反馈的成本。

最后汇总：成立、不成立、无法判断各几条，改变了 Agent 做法的几条，hook 失败和未完成分析各几次。
```

## 5. 开发条目

助手为每个条目在 `<RUN_ROOT>/versions/Bnn/` 的独立开发副本启动新的 Codex session，不在用户原 main 工作区实施。

```text
请完成 TaskBelay 迭代批次 <Bnn> 的一个条目。当前目录为 <独立开发副本>，起点是 <已采用版本清单>。只做这个条目，完成后保留改动并停下，不暂存、提交、推送或发布；主控会保存源码快照并决定采用。

条目：<问题池编号>，类型 <修复 / 精简 / 判断改动>
问题：<问题池中的现象>
出处：<项目、任务编号或轮次、记录位置>
完成标准：<迭代方法第 6 节中该类型的完成标准>

开工前先读 docs/iteration-method.md 第 6 节和 docs/iteration/decisions.md，照常使用本机已安装的 TaskBelay。

按条目类型：
- 修复：先在当前代码上用出处里的原输入重现问题。重现不了就不改代码，报告做过哪些尝试。重现后修正原因；如果只有新增一条按代码外形识别的规则才能解决，就改为收窄或关掉这条提示。
- 精简：关掉或删除指定的提示或功能，同时删除只为它存在的代码和文档。
- 判断改动：只实现条目写明的这一项判断，用文档已有的统计、搜索和确认方法表达；条目给出的反例和你想到的反例，在这一次里一并处理。

共同要求：
- 遵循 AGENTS.md 中本次自动化迭代例外，不按路线图阶段选题。产品行为有变化时，先改对应产品文档，再改代码。
- 不修改 docs/roadmap.md；docs/iteration/ 由主控助手统一更新，这次不改。
- 开发中发现的其他问题，以及没有在真实记录里出现过的边界情况，这次不处理，写在最终回复里。

最终回复写明：做了什么改动，或为什么没有改；怎样确认的（环境、命令、结果）；发现但没有处理的问题。
```
