# TaskBelay 自动化迭代方法

本次进化以“让 TaskBelay 成为好用、可靠、能减少无效工作的产品”为目标，不受路线图阶段顺序约束。助手自主准备任务、冻结计划、安排独立 Codex 会话、核对证据、采用或放弃改动，并向用户汇报。用户不承担中途选题、评审裁决或逐批合并工作。

本文规定的是执行流程。文档修订本身不启动实验，不提交当前工作区。实际启动后，主控按下列规则完成准备并自动推进；原 main、117 分支和用户未提交文件保持原状。

采用一项改动，需要明确真实问题，并通过对应类型的验证与成对评估。功能质量、正常开发负担和总成本共同决定是否保留，具体门槛见第 8 节。TaskBelay 自己是主要的测试对象：找问题、调整判断，都在它自己历史上的真实需求上进行。另留少量其他仓库的任务，只在验收时使用，用来确认在 TaskBelay 身上调出来的判断换一个仓库仍然成立。

交给 Codex 的 Prompt 见 [prompts.md](iteration/prompts.md)，各类记录的位置见第 3 节。

## 1. 117 轮连续自我迭代说明了什么

2026-11-10 至 11-12，Codex 使用已安装的 TaskBelay 连续开发了 117 轮，每轮的指令是“推进下一个可交付的路线图步骤”，每轮在上一轮的分支上继续。各轮的记录保存在 117 轮末端提交 `2a2f06ce` 的 `docs/roadmap.md`“已完成记录”里。结果如下。

| 实际发生的事 | 原因 | 本方法的对应规定 |
| --- | --- | --- |
| 117 轮结束时仍在阶段三。几乎每条记录的结尾都写着：实际任务中是否少做了多余工作，仍无法确认 | 阶段完成条件要求对比，过程里没有可以对比的另一组 | 效果只在任务集上按成对结果判断（第 4、5 节） |
| 058 核对五项任务：325 次命令前 hook 没有一次建议；083 核对十二项任务：五轮开发出的重复行、重复调用提醒没有一次可用的机会 | 每轮的任务是 Codex 自己挑的下一小步。指令和仓库规则已经把它压成“一处小改动加一条临时测试”，多余工作本来就少 | 任务取自较完整的真实需求，起点固定，各组保留相同的正常仓库规则；没有多余工作的任务也保留（第 4 节） |
| 63 轮新增功能，产品代码净增约 2,660 行，只有 025 一轮撤掉了一种提示 | 每轮都必须交付一处改动，没有线索时只能自己找题目 | 没有合格条目就停；“没有改动”和“删掉一种提示”都是合格的交付（第 6、9 节） |
| 104、109–114、117 各自从一个事例得出一条按代码外形识别的规则，再用同一个事例回放确认 | 得出规则和确认规则用的是同一份输入，提出、实现和判定是同一个 Agent | 判断改动要有多个互不相关的任务作依据，在留出任务上验收，由另一个 session 评审（第 5、6、8 节） |
| 026 的一项提示引出 10 轮修补；让相近测试比较在 300 毫秒内完成用了 16 轮，最后几轮的真实运行里仍时常做不完；开场提示的措辞和字数来回改了约 12 轮 | 下一步总是从上一步的日志里找，没有次数上限 | 同一问题最多立项两次，第三次只能缩减（第 6 节） |
| 083 写明“不足以支持继续增加副本写法”，095 写明“不足以支持为寻找跨文件副本延长预览时间”；其后仍有 8 轮按单个事例新增外形规则，4 轮继续优化跨文件比较 | 结论埋在叙述里，对后面的轮次没有约束力 | 结论写进 [已定结论](iteration/decisions.md)，选题前必读（第 3 节） |
| 路线图由 62 KB 增至 296 KB，每轮开工都要读一遍；117 个叠加的 draft PR 一个也没有合并 | 每轮追加一段长记录；没有任何一步需要人确认 | 一个批次形成一个结论和可恢复版本；助手独立评审后采用或回退，不再堆叠等待处理的 PR（第 7 节） |

117 轮里有三次提醒确实带来了设计精简：054、085、109 各删掉一处已经写入的多余实现，都是先写后改，用到的是前期就有的抽象、分支调用和重复实现提醒。103 则通过 TaskBelay 查询历史记录，结合当前改动决定省去一次测量脚本；104 以后按单个事例新增的规则，直到 117 轮都没有在真实开发中触发过。同一时期修掉的真实缺陷（并行 hook 登记超时、工具输出被学成测试用例名、提示噪声等）则是自我使用确实能发现的问题。这两点决定了本方法保留什么、改掉什么。

## 2. 角色

| 角色 | 由谁担任 | 负责什么 |
| --- | --- | --- |
| 用户 | 项目所有者 | 接收进展、效果和阻碍汇报，可随时调整目标或停止 |
| 主控 | 本对话中的助手 | 自主组建并冻结任务、选题、开批、派发条目、安排运行和独立评审，按规则采用、回退、继续或停止；更新 `docs/iteration/` 并汇报。产品实现由开发 session 完成 |
| 开发 session | 每个条目一个新的 Codex session | 在独立批次副本完成一个条目，使用已核实版本的 TaskBelay；由它决定实现与验证方式 |
| 运行 session | 每次任务运行一个新的 Codex session | 只收到任务的需求原文，像平时接需求一样完成它。运行期间没有人追加指示 |
| 评审 session | 新的 Codex session | 按第 5 节的清单核对一次运行的产出。评审产出时看不到这次运行是否启用了 TaskBelay |

## 3. 资料放在哪里

仓库里只放方法和三份小记录，都在 `docs/iteration/`：

- [问题池](iteration/backlog.md)：已经发现、尚未处理的问题线索，每条带出处。
- [已定结论](iteration/decisions.md)：采用、放弃或停止过什么，原因是什么，什么条件下可以重新讨论。主控选题前读它，开发 session 开工前读它。
- `batches/Bnn.md`：每个批次一份记录，开批时写计划，收尾时写结果，格式见 [批次记录模板](iteration/templates/batch.md)。

任务集、验收脚本和每次运行的原始记录放在仓库之外的工作目录，默认是 `~/taskbelay-lab/`。目录分开便于管理；实际可读范围按第 4 节配置。

```text
~/taskbelay-lab/
  tasks/T01/            task.md（仓库、起点提交、需求原文、必须保留的行为、类别、用途）
                        accept.sh（验收脚本，只检查行为）
  runs/B00/T01-off-1/   repo/（本次评估副本）、manifest.json、events.jsonl、timeline.jsonl
                        accept.txt、review.md、taskbelay-data/（本次结束后的完整数据备份）
  original/             开批前的 TaskBelay 数据、安装和接入配置备份
  source/               原 main 的提交、未提交文档副本、差异与哈希清单
  versions/adopted/     当前已采用的不可变产品快照与版本清单
  versions/Bnn/         本批独立开发副本、补丁及采用/回退记录
```

### 任务组建规则

- **5 个选题任务取自 TaskBelay 自己。** 每个任务对应 main 上 `e46c40fe` 之后真实做过的一次功能或修复提交：起点是那次提交的父提交，需求原文按用户平时提需求的口吻写一两句话，只说要什么结果。它们的运行记录可以随意翻看，找线索和调整判断都在这里进行。
- **3 个留出任务固定取自 notes-blog-web 和 WikiSkill。** 固定 notes-blog-web 两个、WikiSkill 一个，同样对应真实做过的提交。它们只在批次验收时运行，只看汇总结果。留出任务的运行细节一旦被用来分析问题或指导改动，就转入开发资料；新的留出任务由主控在下一批准备阶段独立核对并冻结，不在运行中补换。
- **必须包含反例**：两部分各至少 1 个任务的正确做法本来就需要新增抽象、较多测试或大范围验证。它们用来发现工具把必要工作劝掉。
- **验收**：每个任务一份只检查行为的脚本，外加一张“必须保留的行为”清单。脚本和清单由主控在运行结束后使用，不提供给运行 session；读取隔离按下文核实。
- **评估副本**：每次运行独立建一份起点内容相同的副本，Git 中只保留起点及更早的历史，不使用可访问完整原仓库对象库的 worktree。各组保留相同的正常仓库指令（含 `AGENTS.md`）、全局指令和技能配置。若另做移除某类指令的消融试验，单独固定改动并报告，不与主对照混用。

留出任务放在别的仓库，是因为判断若在 TaskBelay 的代码上得出、又只在 TaskBelay 的代码上确认，就分不清它是普遍有用，还是只适合这一个仓库的写法。

一次只跑一个运行。同一个任务从相同起点分别建立独立副本，分三组运行，运行先后顺序在开批时随机确定并保存：

| 组 | 含义 |
| --- | --- |
| 不装组 | 卸载 TaskBelay 的 hook 和 MCP（`taskbelay uninstall codex`） |
| 已采用组 | B00 使用冻结的 main 产品提交；后续使用上一批通过采用条件的产品快照，无需先合并 main |
| 候选组 | B00 使用 117 末端；后续使用本批候选快照构建的 TaskBelay |

三组固定 Agent、模型、思考强度、权限、依赖与工具版本，使用相同的基础设置；启用组开启 `debug`。每次均用新 session，不恢复前一次对话。这里评估的是从全新 TaskBelay 数据开始的表现；积累历史后的收益另设有明确初始快照的试验。

### 每次运行的数据切换与备份

当前 `internal/platform/platform.go` 从用户主目录确定 `~/.taskbelay/`；`internal/agent/install.go` 按用户目录安装 Codex hook 和 MCP，不能仅改 `CODEX_HOME` 就假定两者已隔离。因此在本机串行使用固定数据路径，每次结束完整归档，再为下一次创建新目录：

1. **开批前保留日常现场。** 确认没有其他 Codex/Claude 会话及相关 MCP、hook 或检查进程持有数据文件。只结束本流程自己的会话；用户其他会话仍在使用时不切换数据或强行结束它，保留现场并报告暂不可运行。主控在数据切换期间也不接入 TaskBelay。记录实际数据路径、符号链接目标、已安装版本及相关接入配置；把原数据目录完整备份到 `original/`，核对文件清单与哈希，并另存安装程序和将被修改的配置。原数据移出活动路径后保留，不用空库覆盖。若仍有进程使用目录，先停在这里。
2. **每次从空目录开始。** 为本次编号建立新 `~/.taskbelay/`，只用 `taskbelay config set` 写入计划中的统一设置，不从历史账本复制任务、索引或校准记录。启用组安装并核实指定版本，设置 `debug on`；不装组卸载 hook/MCP，并确认启动的 session 没有 TaskBelay 工具或提示。开发 session 的数据也不得带入评估运行。
3. **启动前核对。** 把代码与二进制版本、有效设置、新数据目录、Codex 接入状态及相关进程检查结果写入 `manifest.json`。相同依赖缓存条件在各组一致，不把某组额外下载或旧构建产物的影响混入结果。
4. **结束后完整备份。** 等 session、MCP 和 hook 退出，把本次整个数据目录归档到该运行的 `taskbelay-data/`，包含 SQLite 的 WAL/SHM（若仍存在）、debug 和其他记录，不能只拷贝数据库主文件。保存清单和哈希；失败、超时、中断的运行也用原编号备份。随后创建新的空目录供下一次使用，不把上次目录恢复进来。
5. **收尾恢复日常现场。** 正常结束或中断清理时，先归档最后一次数据，再恢复开批前的原数据、原安装版本和接入配置，核实恢复结果。其他用户配置若在期间被修改，只恢复本次改动的 TaskBelay 项，不整文件覆盖较新的用户修改。恢复失败就停下报告，不继续运行。

备份只留本机，权限限本机所有者；仓库记录路径、版本和校验值，不收录原库、配置或凭据。记录表格中的 token、时间和重试包含失败尝试；开批安装、切换数据和备份耗时另列批次开销，计算总成本时纳入。

### 验收资料和跨组信息的隔离

数据备份能隔离 TaskBelay 历史，运行 session 的读取范围还需单独限制。启动配置只开放本次 `repo/`、临时构建目录及必要工具、配置；启用组另开放当前 `~/.taskbelay/`。禁止读取任务集中的验收和真实实现、原仓库及其后续提交、其他运行目录、旧会话记录和数据备份；网络或连接器也不能提供对应答案与其他组输出。开发 session 只能看选题任务，留出详情由组建任务和评审角色保管。

先用无敏感内容的探针核对这些路径能否读取，并记录所用限制。只换工作目录或笼统设置为 workspace-write 不算验证了隔离。若当前执行环境无法限制读取，只能选用已获准且能通过探针的隔离环境；没有可用方案则结束准备并报告。创建新用户、修改安全权限或扩大网络访问等需要单独确认的动作不自动执行，不能降级为未隔离运行来凑验收结果。各组必要的认证、构建和正常网络能力保持一致，不复制密钥到评估资料。

每次运行后核对实际接入：不装组没有 TaskBelay 工具、提示或 hook 记录；启用组有对应 session 和构建版本的 hook 记录，并能核对 MCP 接入。配置不符的原运行标为接入失败，保存产出和成本，修复后用新编号重跑；原记录不被替换。连续两次接入失败按停止条件处理。

不装组没有多余工作的任务照常保留，它们用于衡量正常任务中的误报和额外成本。只有任务或验收本身无效时才提出更换，主控记录原因和旧结果，结束本批受影响比较，在下一批按相同来源与类别准备新任务并重新冻结；不征求例行选题确认。若整批没有明确精简机会，报告该样本未观察到机会，停止据此立项判断改动；另行寻找机会只用于开发集，不按结果筛换封存留出任务。

## 5. 一次运行怎样评审

评审分两步，各用一个新的 session。

**第一步，核对产出和过程。** 评审拿到需求原文、起点到结束的完整 diff、验收结果、“必须保留的行为”清单，以及脱敏的编辑和运行时间线：每次编辑前后的内容或 Git 对象、命令及参数/目录、相关环境和工具指纹、运行前后输入快照、退出状态和必要输出。临时文件删除前也保存源码。主控用中性编号替换分组/版本路径，移除 TaskBelay 提示及会暴露分组的自述，保留全部操作事实；原始记录另存用于第二步核对。盲化无法完成时记录哪些信息暴露，不宣称完全盲评。评审依据需求、必须保留的行为和以下标准逐项列出；不检查路线图推进情况：

| 类别 | 判为成立需要写明 |
| --- | --- |
| 多余设计 | 哪个入口、配置、依赖、抽象或防御处理没有需求依据，省去后需求照样满足 |
| 多余测试 | 哪条用例或哪组数据没有独立检查的内容，删去后哪些检查仍然覆盖它 |
| 重复验证 | 哪次运行的输入与此前某次相同，没有回答新的问题 |
| 必要工作缺失 | 哪项验收或必须保留的行为没有满足，哪种错误没有测试能发现 |

每一项标“确定”或“拿不准”。主控只对影响采用结论的争议安排一次独立复核，复核最多 30 分钟；仍拿不准就保留为未知，不计收益、不以此删除必要行为。若未知涉及正确性或决定采用门槛，条目不采用。主控按这个默认规则作结论，不交用户裁决。

**第二步，核对提示。** 只对启用了 TaskBelay 的运行做。评审拿到第一步的结果和这次运行里 TaskBelay 给过的全部提示，逐条写明：提示指的东西是否确实多余（成立、不成立、无法判断）；Agent 看到后做了什么（写入前就没写、写了又删、保留、没有反应）；因此少了第一步里的哪一项。

每次运行记下：各项验收结果；四类各几项；提示成立和不成立各几条；hook 失败和未完成分析的次数；token、历时、命令数、重试和人工处理时间。无法核对的输入或输出标为未知；部分分析不计为没有问题。代码行数和测试条数只作参考。

一次运行的结果会随 Agent 波动。补跑规则固定如下：接入或基础设施失败只修复一次并用新编号重跑，原失败计入成本；候选与对照出现无法由代码、验收或环境证据解释的质量反转，或单次成本越过门槛但记录显示偶发等待时，对该任务的相关两组各补一次，必要时再各补一次。明确产品缺陷直接判不采用，不靠补跑冲淡。全部附加运行合计最多 8 次，按任务编号顺序处理，接入重试也占用额度；没有触发条件不补跑，额度不足就记证据不足。保留全部质量失败与成本，不用中位数删除失败。

## 6. 问题池与三类条目

线索有三个来源，记入问题池时写明出处：

1. **选题任务**：5 个 TaskBelay 任务的运行和评审记录。不装组多做了什么、已采用组漏掉或说错了什么，是判断改动的主要线索。
2. **批次里的开发 session**：它们本身就是在用 TaskBelay 开发 TaskBelay。条目都很小，这里只收故障，即 hook 失败或超时、分类错误、提示明显不成立。
3. **用户的真实项目**：平时用 Codex 加 TaskBelay 做别的项目时留下的记录（`taskbelay hits --since 14d`、debug 日志），以及用户说得出具体事例的“不好用”。

条目分三类，优先顺序是修复、精简、判断改动。工具本身不可靠时，测不出判断的效果。

| 类型 | 立项条件 | 完成标准 |
| --- | --- | --- |
| 修复 | 工具没有按文档工作，或给出了明显不成立的提示；有一条能定位到具体输入的真实记录 | 在当前已采用版本上用原输入重现，改后不再出现。办法是修正原因、收窄或关掉这条提示。重现不了就不改，如实记录 |
| 精简 | 某种提示连续两个批次在任务集和真实项目里没有一次成立，或某项功能只服务于迭代过程本身 | 关掉或删除后任务集结果没有变差，代码和文档净减少 |
| 判断改动 | 同一种多余工作在至少 3 个互不相关的任务里自然出现（选题任务或已授权真实项目），评审判为确定；能用文档已有的统计、搜索和确认方法表达；写得出一个外形相同、但应当保留的反例 | 满足第 8 节的采用条件 |

新增或修改给 Agent 的固定提示文字，按判断改动处理。

三条限制用来截断连锁反应：

- **同一问题最多立项两次。** 第二次仍没有解决，第三次只能是缩减：关闭、退回到交付前检查，或缩小范围，并写入已定结论。
- **条目内把已知的反例一起处理完。** 交付后才想到、但没有在真实记录里出现的情形，只登记到问题池，等它真实出现。
- **构造的输入只用来确认代码按设计工作。** 是否有效果，只看任务集上的成对结果和真实项目里的记录。

## 7. 批次流程与版本保存

一个批次回答一个问题。一批只放一类条目：最多 5 个修复，或 1 项精简，或 1 项判断改动。每个条目由新的开发 session 完成，最多一次补充修正会话；不做无上限修复循环。

### 保留用户工作区

原 main 可以保留未提交文档，不要求用户先提交。开工时记录 main 提交，复制本次方法、AGENTS 和其他未提交文档到 `source/`，保存逐文件哈希及差异。所有构建、开发和评估都在实验目录的独立副本中进行。原工作区只由主控更新规定的批次小记录，不切分支，也不覆盖用户较新的编辑。按用户 2026-11-12 指令，启动前仅提交本次已核对的方法和配套文档一次；后续产品进化仍以独立副本和本地快照接续，不自动提交或发布。

B00 的产品基线只取冻结的 main 提交，不把未提交过程文档或 117 产品改动混入。各角色另外接收本流程的相同执行约束；被评估任务各组使用相同的正常项目指令。

给开发副本叠加已冻结的本流程 AGENTS 例外、方法和已定结论，并在源码清单中单独标记过程文档。运行组的指令另按第 4 节保持一致。产品版本用“起始提交＋相对补丁及新增文件＋文件清单哈希＋二进制哈希”标识，构建前在独立副本恢复并核对。即使没有新 Git 提交，也能恢复和比较同一个版本。每批候选结束时保存不可变快照，采用后更新 `versions/adopted/` 的指针，上一版本继续保留。数据和凭据不进入源码快照。

### 自动推进

1. **准备与开批。** 主控读已定结论和问题池，按影响真实任务的程度选题，优先解除有效性阻碍，其次精简，再考虑新判断；同优先级按问题编号选取。将当前已采用版本复制到 `versions/Bnn/`，填写批次计划。T01–T08 的具体任务、验收、工具环境、设置、隔离探针和上限全部齐备后自动冻结。运行顺序用批次编号作为固定随机种子洗牌并保存，执行时不重排来迁就结果。
2. **开发。** 每条目使用 6.1 Sol、medium、自动审核的新会话。主控交付目标、原始事实和完成标准；实现与测试由 Codex 自主决定，运行中不追加设计或测试指导。开发完成只保存本地改动和结果，不要求提交。重现不了或不值得改时关闭条目，不为交付制造修改。
3. **验收运行。** 从固定快照构建各组版本，串行切换全新数据运行任务。对照标识包含产品快照/二进制、任务起点、需求/指令/验收哈希、依赖和工具、Agent/模型/思考强度/权限、技能、设置和数据初态。逐项一致且原记录可核对时才复用，否则重跑并保留旧结果。每个评估 session 最多 60 分钟；单个开发 session 最多 90 分钟。达到上限先保存现场并停止该会话，按失败计入，不在原会话中无限催促。
4. **评审。** 按第 5 节由未参与实现的新会话做两步核对；每个评审最多 30 分钟。主控处理证据分歧，无法确认的按未知或不采用处理，不向用户转交普通工程选择。
5. **采用或回退。** 按第 8 节决定。采用条件全部满足才推进本地已采用版本；不满足则保留原版，存好失败候选及原因。存在严重错误拦截或破坏必要行为时，停止该候选的后续运行，先恢复稳定版和用户现场。
6. **归档与汇报。** 更新问题池、已定结论及批次记录，保存源码快照、补丁和恢复清单，核实数据备份，恢复日常安装和配置。汇报本批改变、质量与成本、取舍及下一步，不等待回复。存在合格条目且未达到停止条件时，按下一批计划继续。

启动前的方法文档按用户明确要求在本地提交一次；此后默认交付为本地可恢复版本和报告，不自动提交、推送、合并或发布。PR 不再是推进条件；以后获得明确发布授权时再整理已采用改动，不把评估结论自动等同于合并或发布权限。

## 8. 采用条件

每个批次都要满足：

1. 逐任务、逐验收项对照已采用组：原来通过而候选失败的项，以及新增的必要工作缺失，必须定位和处理后才能采用；不能用另一任务的改善抵消。因环境等原因无法判断的项仍是未通过采用条件。
2. hook 失败和未完成分析的次数不高于已采用组。
3. token 总量和总历时都不超过已采用组的 110%，包含各自失败、重试及工具开销，逐任务差异也需列出；共享的准备、归档和人工处理成本单独列出并计入批次总成本。本次流程不在看到结果后放宽比例。

各类条目另外要满足：

- **修复**：原记录回放时问题不再出现。
- **精简**：四类数字都没有变差，代码和文档净减少。
- **判断改动**：只看没有被用来得出这项判断的任务，即留出任务和为这一批新补的任务。批次计划在运行前点名预期出现变化的任务；这些任务没有出现预期机会时，记录本批证据不足，不按结果换题或追加有利样本。在这些任务上，这项判断给出的提示成立的多于不成立的；至少有一次完整的“提示 → Agent 改变做法 → 评审确认少了一项多余工作”；候选组的多余项合计少于已采用组。

结果不明确时按未满足处理。条件没有满足的条目回退，主控对保留组合核对引用及必要验证后保存已采用快照；失败候选及原结果保留供追溯，不覆盖上一已采用版本。

## 9. 自动收尾与异常处理

主控不把“下一步怎么做”交给用户。按下列默认规则继续或结束，并汇报依据：

- **没有合格条目：**保留已采用版本，结束本次进化；不重跑同一批任务来制造新问题，不自动启用备选仓库。
- **同一问题两次失败：**只能再做一次缩减；没有安全缩减方案就关闭该问题。连续两个判断改动批次被回退后，本次执行不再新增判断，只处理合格修复和精简。
- **资源上限：**一次执行包含 B00 和最多 10 个产品改进批次。B00 首轮 24 次；每批最多 24 次首轮评估和 8 次附加运行。开发、运行和评审均按第 7 节限时。单个会话到时只停止该会话，记录失败并按既定补跑规则处理；单批运行额度用尽只收尾该批，证据不足的候选不采用。达到 B00 后 10 个改进批次的总上限时，结束本次执行并报告保留版本，不自动扩大任务集、预算或循环次数。
- **环境故障：**连续两次接入失败、数据恢复失败、隔离探针不通过且没有已获准方案时，停止受影响阶段，保存可恢复现场并报告；不删失败记录、不绕过权限限制。
- **信息与权限：**只在授权范围内自主决策。遇到凭据泄露、不可恢复删除、需要新的安全权限或其他必须单独确认的动作时，不执行该动作，停止依赖步骤并报告。普通选题、工程取舍、证据不足和批次采用不要求用户参与。
- **用户改变目标或要求暂停：**立即停止新派发，按新要求保存正在运行的任务和数据。

中断恢复前先核查进程、快照和运行编号；已完成的运行直接使用，不重开重复会话。未完成运行保留为中断，是否补跑按既定额度处理。每次安全停机都先备份评估数据，再恢复日常数据、安装和配置。

## 10. 怎样判断产品已经值得使用

本次不以路线图阶段完成为终点。主控综合以下证据决定是否进入稳定使用阶段：

- 必要功能与用户修改保护没有新增退化，没有未处理的严重错误拦截；接入与分析的失败、未完成范围明确可接受。
- 设计侧和测试/验证侧分别在未参与本轮调规则的真实任务中出现可核对的无效工作减少；“事后删掉”“事前避免”和查询复用分别记录。
- 在正常和复杂度必要的任务上没有以少做必要工作换收益，工具及处理反馈的总成本符合采用条件。
- 至少两个使用不同新留出需求的批次给出一致方向的证据；开发集的改善和单一廉价操作的省略不足以宣布产品成熟。

达到这些条件后停止新增能力，交付当前稳定版本、适用范围和剩余问题。尚未达到但本次额度已用完时，按实际证据报告“局部改善”或“收益未证”，不把暂停包装成达标。路线图可作为产品背景参考，不要求同步阶段进度或等用户标记完成。
