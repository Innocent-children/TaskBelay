# 语言无关的算法核心

TaskBelay 用同一套表示判断过度设计和过度测试。算法只在本次改动及其邻域上计算：静态信号负责找出和排序候选，在副本里的实际运行负责确认，判断所需的语言知识全部从仓库自身的内容和运行记录中统计得到。算法不含按语言写的规则，也不以代码行数、用例条数或运行次数的固定阈值下结论。

统一表示和运行方式见 [输入与执行协议](languages.md)，两类判定分别见 [过度设计判定](over-design.md) 和 [过度测试判定](over-testing.md)。

## 设计原则

1. **复用和局部计算**：按内容复用文件分析与仓库约定，差分围绕改动计算，需求相关区采用局部推送；仓库索引装载成本单独计入。
2. **静态提出，运行确认，事实拦截**：统计和词汇信号只用来找出候选、给候选排序。“这处改动是否需要”“这条用例是否有用”由实际运行回答，报告中的运行结论都经过确认运行。拦截只依据能直接核对的事实：文件和清单的内容、探针输出、账本中的登记、确认运行的结果和完全相同的验证输入。
3. **从仓库学习**：关键字、注释写法、测试写法和约定入口按文件扩展名分组统计，算法不知道扩展名对应什么语言。
4. **可以复核**：每个结论附带输入版本、来源和推导路径。信息不足时结论是未知，不当作通过。
5. **持续校准**：信号的权重按本项目中反馈的实际结果更新，用于给建议排序。
6. **本机完成**：全部计算在本机进行，只运行项目自己的命令，不调用外部模型或网络服务。

文中的 ε、α 等是精度和预算参数，只影响近似程度和耗时，不是判定阈值。建议的排序由合并信号和校准决定，拦截由第六节列出的事实条件决定。

## 总流程

```text
交付检查(任务):
  Δ ← 词级差分(起点快照, 当前快照)
  G ← 强连通分量缩点(hunk 依赖(Δ))                                  # 变更簇
  对每条有效需求 R:
      相关区[R] ← 扫描切割(局部推送(种子(R), 代码图))
  候选 ← 相关区外的簇 ∪ 未锚定的对外新增项 ∪ 没有变化的间接层 ∪ 近似重复 ∪ 没人使用的代码
  动态检查开启且有验收依据时:
      可撤回 ← 分组检验(候选中全部来自 Agent 编辑的簇, G, 验收依据) 后确认运行
      保留用例 ← 贪心集合覆盖(去冗余(逐个变异运行得到的发现矩阵), 保留集合) 后确认运行
  拦截 ← 满足第六节事实条件的候选
  反馈 ← 背包选择(合并信号(其余候选), 反馈预算)
```

动态步骤在 session 的 MCP 进程中后台进行，交付时使用已有结果，见第九节。

## 一、输入

| 输入 | 内容 |
| --- | --- |
| 内容 | 任务起点快照、当前快照、累计 diff 和各文件的 blob 标识 |
| 来源 | 可核对的 Agent 编辑、工作区更新及其所在的工具调用 |
| 需求 | 用户原话与引用、需求内容、验收标准、实现位置、有效方案和用户决定 |
| 运行记录 | 命令、目录、参数、环境摘要、工具身份、输出、退出状态和时间 |
| 仓库统计 | 按 [输入与执行协议](languages.md) 从起点内容学到的词法、版面和约定 |

一次计算只使用同一组输入版本。发布结果前再次核对版本；版本已变化时，结果只保存为历史。

## 二、变更簇

累计 diff 先按行比较（Myers 算法，O((N+M)D)），再在每个 hunk 内部按词比较，得到实际改变的词。每个 hunk 归入一类：

| 类别 | 判断方式 |
| --- | --- |
| 只改空白或注释 | 两侧去掉空白和注释后的词序列相同 |
| 一致改名 | 两侧词序列之间存在标识符的一一对应，O(n) 可以检查 |
| 移动 | 删除侧的内容在新增侧完整出现（winnowing 选出的 k-gram 哈希全部匹配） |
| 行为改动 | 其余情况 |

**新词**是起点词表里没有、当前内容里出现的标识符。hunk 之间按两种关系建立依赖：

- hunk B 用到了 hunk A 引入的新词，B 依赖 A。
- hunk A 改了某个单元的首行，hunk B 改了含这个单元名字的行，两者互相依赖。

用 Tarjan 算法求强连通分量（O(V+E)）并缩点，得到一张有向无环图，每个节点是一个**变更簇**。保留和撤回都以变更簇为单位；撤回一个簇时，依赖它的簇一并撤回，因此不会留下悬空的引用。失败运行没有可解析的单条用例结果，且输出同时点名撤回簇与保留簇的新增声明时，记录这条关联，将涉及的 Agent 簇合并后重新计算。无法定位相关声明时保留未知，不把运行失败直接当作某个簇必要。

每个变更簇记录来源：全部来自可核对的 Agent 编辑、全部来自工作区更新，或两者混合。只有全部来自 Agent 编辑的簇可以成为撤回候选；其余的簇保留当前内容，只报告现状。

## 三、需求相关区

需求相关区回答“哪些单元和变更簇与这条需求有关”。它是图聚类中围绕需求形成的社区，用来代替沿同名引用无限传递的归属方式。

### 图

| 节点之间 | 边权 |
| --- | --- |
| 单元—标识符 | `idf(词) × log(1 + 该词在单元中出现的次数)` |
| 变更簇—单元 | 变更簇改动了这个单元 |
| 变更簇—变更簇 | 同一次编辑调用写出，代表 Agent 自己的工作分组 |
| 单元—文件 | 包含关系，权重较低 |

`idf(词) = log(单元总数 ÷ 含这个词的单元数)`。`err`、`i`、`ctx` 这类常见词的 idf 接近零，边权低于精度参数 ε 的边不建立。新词只出现在少数单元里，idf 很高，所以“新代码使用新代码”是强连接，“都调用了同一个日志函数”是弱连接。

### 种子

种子是推送开始时放在节点上的质量：

1. **用户原话**：用 Aho–Corasick 自动机（O(文本长度 + 匹配数)）一次匹配仓库词表，包括完整标识符、按驼峰和下划线拆开的子词、文件路径和 `路径:行号`。
2. **已确认方案**：半自动模式下方案的涉及范围和对外入口，与原话同等对待。
3. **需求内容和验收标准**：Agent 写的需求内容常把原话转述成代码里的词，例如“export 命令通过 `--format csv` 输出 CSV”。按同样方式匹配，权重低于原话。
4. **实现位置**：Agent 登记的位置，权重最低。

各类种子的相对权重由校准决定（见第七节）。最强路径起点上各来源所占的质量参与共同拟合；拟合结果调整对应来源的质量，始终保持原话优先于需求内容、需求内容优先于实现位置。原话、方案和需求内容都匹配不到任何词时，这条需求的相关区为未知，与它有关的判断只作提示。

### 计算

对每条需求，用 Andersen–Chung–Lang 局部推送算法近似计算个性化 PageRank：每次取一个残量较大的节点，把残量的 α 部分记为它的得分，其余按边权推给邻居，直到每个节点的残量都小于 ε 乘以它的度。推送的总工作量为 O(1/(εα))，与图的总规模无关。

然后按“得分 ÷ 度”从高到低排列节点，依次计算每个前缀集合的导率（conductance：集合对外的边权之和，除以集合与其余部分中边权总和较小的一侧），取导率最小的前缀作为需求相关区。这一步的代价为 O(s log s)，s 是得分不为零的节点数。该方法有 Cheeger 型保证：种子所在区域若存在导率为 φ 的集合，对其中大部分种子，找到的集合导率不超过 O(√(φ·log m))，m 为边数。

### 解释

每个变更簇记录它到各需求相关区的最强路径：在边长为 −log(归一化边权) 的图上用 Dijkstra 算法求最短路。报告给出路径上的关键节点，例如“只经由常见词 `Info` 与 R1 相连”。

## 四、验收依据

验收依据是判断改动是否需要、用例是否有用时采用的运行标准：

- **既有行为**：起点已有的测试和检查命令中，在当前快照的副本里能通过的部分。
- **实现前登记的验收**：需求的验收标准写明用哪条用例或哪条命令确认结果。验收标准所在的需求修订早于这条需求相关区内最早的 Agent 编辑时，它作为验收依据；晚于它的只作补充依据，由它得出的结论只用于提示。半自动模式下，方案成功标准中写明的用例或命令随方案确认，在开发前登记，满足这个条件。
- **用户点名的用例**：用户原话中要求编写或保留的用例。

验收标准里的用例名和命令，与测试单元的名字及已观察到的命令按词匹配；匹配不到时，这条验收标准记为未落实。

实现以后才写、只服务于新增功能的测试不属于验收依据，否则多出来的功能和为它写的测试会互相证明对方必要。

每次运行都执行全部验收依据。既有行为是所有变更簇共用的依据；实现前登记的验收和用户点名的用例属于各自的需求。一条需求没有自己的验收依据时，撤回试验和变异对它相关区内的变更簇不提供结论，相关判断只用静态信号：起点已有的测试通常覆盖不到新功能，只用它们判断，会得出“整个新功能都可以撤回”的错误结论。

## 五、分组检验

撤回试验（见 [过度设计判定](over-design.md)）要回答：n 个候选变更簇里，哪些撤回后会让验收依据失败。逐个运行需要 n 次；分组检验让一次运行同时检验一组候选。

- 一次运行把一组候选同时撤回，再运行验收依据。全部通过，说明这组候选可以一起撤回；失败再二分。
- 采用 Hwang 的广义二分法。设 d 是撤回后会导致失败、需要保留的候选数，运行次数约为 `d·log₂(n/d) + O(d)`，接近信息论下界 `log₂ C(n,d)`。d 远小于 n 时节省明显；d 接近 n 时接近逐个运行。
- 候选只取静态信号标出的变更簇，可信度低、可能需要保留的先单独检验。静态信号越准，d 越小。
- 失败组合按二分缩小范围；输出能核对到不同簇的新增声明时，按第二节补充依赖并合并。

分组检验的效率依赖一个假设：组内任何一个候选撤回后会导致失败，整组撤回也会失败。候选之间互相抵消时这个假设不成立，因此最终结论都要经过一次**确认运行**：把最终的撤回集合整体作用到副本上运行一次。结论只针对这一整组，给出的撤回补丁也正是这一组，所以假设不成立只会让找到的候选变少，不会产生错误结论。

确认运行失败，说明有几个候选单独可以撤回、合在一起不行。这时按可信度从高到低，把候选逐个加入撤回集合，每加入一个运行一次，失败就把它移出；以最后一次通过的集合为结论，预算到期时同样以最后一次通过的集合为准。

这条保证只适用于撤回试验。变异需要知道每条用例分别发现了哪些变异，成组运行时互相抵消的变异会让用例看起来什么都没发现，所以变异逐个运行，见 [过度测试判定](over-testing.md)。

## 六、合并信号与选择反馈

### 合并信号

每个候选有一组信号，例如是否在需求相关区内、锚定级别、撤回试验的结果、相似度、变化数、来源、是否在方案中，以及所在文件的结构置信度。信号合并成这条建议的**可信度**：按本项目的反馈记录，同类建议成立的概率。

```text
log-odds(成立) = w₀ + Σ wᵢ · xᵢ
```

xᵢ 是第 i 个信号的取值，权重 wᵢ 用逻辑回归从第七节的标签中拟合。所有信号一起拟合：需求相关区、锚定和没人使用都来自同一套词汇关系，一起拟合时它们分摊权重，同一条依据不会被计算多次。拟合加 L2 正则，向随程序发布的初始权重收缩，样本少时结果接近初始权重。初始权重是保守先验，不代表真实 Agent 效果的实测结果。项目积累的标签参与拟合；没有本项目标签时，先采用本机全部项目的标签。具体取值集中在对应包的 `params.go`，真实效果按 [算法评估](product-evaluation.md) 核对。

可信度只用于给建议排序和选择反馈条目，不决定拦截。

### 选择反馈条目

反馈有长度预算。每个候选的收益是撤回后减少的行数、新词数和测试运行耗时。在预算和每类条目数上限内，最大化 Σ 收益 × 可信度。这是带分类上限的 0/1 背包问题，候选数量不大，用动态规划精确求解，每类先做带条目数的动态规划，再合并各类的容量曲线；复杂度为 O(n·B·L + C·B²)，B 是按固定单位换算的预算，L 是每类上限，C 是类别数。

每条反馈写明具体动作：撤回哪个变更簇、用什么替换哪几处、删除或合并哪几条用例，并附确认运行的结果，或说明尚未运行。

### 拦截

拦截只依据能直接核对的事实。以下三类条目满足全部条件时，可以拦截一次，识别方式见两份判定文档：

1. **对外新增项**：识别方式可靠，即新文件、清单中新增的依赖、配置文件中新增的键，或探针确认的参数、子命令和路由；全部来自 Agent 编辑；名字和取值在原话和已确认方案中都找不到；没有登记为任何需求的实现位置。
2. **可以撤回又与需求无关的变更簇**：撤回试验的确认运行通过；整组补丁中的簇都不在任何需求相关区内；涉及的单元没有登记为任何需求的实现位置。附确认过的整组补丁，不能把整组通过推断为其中任意子集可单独撤回。
3. **重复验证**：验证输入与上次通过时完全相同，附上次的输出。

前两类被拦截后，Agent 可以撤回；也可以用 `requirement_save` 把它登记为某条需求的实现位置，并引用对应的原话。登记过的条目列入交付报告的“由 Agent 说明对应需求的新增”，用户能直接看到。需求相关区和锚定都是词汇上的对应，在这里只用来排除有对应关系的条目，不用来证明哪处改动有必要。其余条目都是按可信度排好序的建议。

## 七、校准

每条反馈之后发生的事自动成为标签：

| 之后发生的事 | 标签 |
| --- | --- |
| Agent 照做，到任务完成时没有被恢复 | 成立 |
| Agent 拒绝，之后用户自己删除了这部分 | 成立（记为漏判） |
| Agent 照做，之后用户把内容加了回来（用 MinHash 识别相似内容再次出现） | 不成立 |
| Agent 照做，之后验收依据失败，失败与撤回的内容有关 | 不成立 |
| Agent 拒绝，理由可以核对：用户原话要求、被需要保留的变更簇依赖、撤回后验收依据会失败 | 不成立 |

每次反馈对应一条标签；后续恢复或相关验收失败会更新同一条标签，不把一次反馈的不同结果重复累计。标签用于拟合第六节的权重。某个信号对结果没有区分作用时，它的权重自动趋近于零；某类建议不成立的情况增多时，它的可信度随之下降，在反馈中排得更靠后。

“Agent 照做，没有被恢复”只说明建议被采纳后保持住了。Agent 通常会按反馈处理；用户没有注意到，或换一种写法重新实现时，误判也会记为成立。所以可信度衡量的是采纳后保持的程度，只用于排序；拦截条件不依赖它，拦截是否正确按 [算法评估](product-evaluation.md) 人工核对。

TaskBelay 记录问题实际展示时的快照、内容签名和观察编号，沿后续编辑记录判断 Agent 是否删除过对应内容，再判断是否恢复、完成交付或发生相关验收失败。校准直接使用编辑和运行记录，删除事件不以笔记为前提。保留理由可用 `note_add` 指向检查问题：以用户要求为理由时带 `quote` 和 `source_id`，以依赖或验收为理由时写明对应的位置或用例，由依赖图和运行记录核对。采纳后的验收失败，只有在同一命令、环境和工具下，两次固定快照仅相差已记录的撤回文件，且已登记验收由通过变为失败时，才关联到该反馈。工作区更新只能证明变化无法归入已核对的 Agent 编辑，不能直接证明操作者是用户；混合来源、缺失编辑链或无法识别内容时不产生标签。同一问题发生记录的重复展示和多条笔记只更新同一条标签。

## 八、问题身份与完成状态

一份报告分别表达四个维度，不用一个“通过”同时代表它们：

| 维度 | 内容 |
| --- | --- |
| 处理状态 | 计划的计算和运行是否完成，是否超时、取消或失败 |
| 依据范围 | 哪些候选有运行结果，哪些只有静态信号，哪些因相关区未知、缺少验收依据或运行失败而未知 |
| 结论 | 各候选的可信度、拦截所依据的事实、确认运行结果、保留集合和未检验的范围 |
| 产品动作 | 放行、提示或拦截一次，以及适用对象 |

没有候选、没有可运行的验收依据、运行超时和程序出错，都不能写成“没有多余”或“测试足够”。

问题身份由任务、问题种类、逻辑对象和关键事实确定。逻辑对象是变更簇、对外新增项、单元或用例的稳定标识，移动后通过移动检测沿用原身份。修改其他文件、补充笔记或格式化不产生新问题；问题解决后再次引入，增加一次发生记录。同一问题每个 session 最多拦截一次，每轮合计最多三次；这是交互上限，不是判定阈值。

## 九、什么时候计算

| 时机 | 计算内容 |
| --- | --- |
| 用户消息 | 匹配种子，在起点图上推送，把最相关、使用最广的已有单元作为可复用的实现提示 Agent |
| 编辑前 | 只对被编辑的文件做增量词法，检查新文件、对外新增项和近似重复 |
| 命令前 | 计算验证输入，查询验证输入记录 |
| 命令后 | 更新验证输入记录 |
| 交付 | 更新变更簇、需求相关区和各项静态信号，合并信号并选择反馈 |
| 动态检查开启时 | 撤回试验和变异在 session 的 MCP 进程中后台进行，结果逐步写入账本 |

MCP 进程在 Agent 调用 `task_finish`、`check_run` 时，以及每次被调用时发现输入已变化且没有运行中的动态任务时，开始后台运行。后台定时读取已登记的任务输入；相同输入通过账本中的运行记录去重。动态部分可以随时停止：停止时已完成的确认运行仍然有效，交付使用已有结果；结果尚未完成时，Stop 在动态检查预算内继续，到期后使用已完成部分，其余只给静态结论。后台运行使用较低的优先级，Agent 开始自己的验证时暂停；预算到期时终止本次启动的进程，清理副本。有新内容或用户主动刷新时，复用未变化的词法结果，并重新计算对应输入的相关结果。

## 十、复杂度

| 环节 | 算法 | 复杂度 | 规模取决于 |
| --- | --- | --- | --- |
| 词法与版面 | 确定有限自动机、栈、缩进层级 | O(字节数)，按 blob 缓存 | 变化的文件 |
| 仓库统计 | 计数与对数几率比 | O(词数)，按 blob 累加 | 变化的文件 |
| 差分 | Myers 行差分 + 词级差分 | O((N+M)D) | 改动大小 |
| 变更簇 | Tarjan 强连通分量 | O(V+E) | 改动大小 |
| 种子 | Aho–Corasick | O(文本 + 匹配数) | 消息与需求长度 |
| 需求相关区 | 局部推送 + 扫描切割 | O(1/(εα)) + O(s log s) | 与仓库规模无关 |
| 近似重复 | MinHash + LSH | 签名 O(n)，查询期望 O(1) | 改动大小 |
| 变化度 | 括号配对 + 集合包含 | O(新词出现次数) | 改动大小 |
| 等价类 | 排序 + 二分查找 | O(用例数 × log 常量数) | 改动大小 |
| 撤回试验 | 广义二分分组检验 | 约 d·log₂(n/d)+O(d) 次运行，d 接近 n 时接近 n 次 | 候选数与需要保留的数目 |
| 测试约简 | 逐个变异运行 + 去冗余变异 + 贪心集合覆盖 | 每个抽到的变异运行一次 | 抽样数 |
| 反馈 | 逻辑回归打分 + 0/1 背包 | 打分 O(n)，选择 O(n·B·L + C·B²) | 候选数 |
| 校准 | 带 L2 正则的逻辑回归 | 每轮迭代 O(样本数 × 信号数) | 标签数 |

文件词法按 blob 复用，相关区推送受局部精度控制。装载仓库统计、组装图、检索候选和序列化仍有随仓库规模增长的成本，不能把局部推送的界当成整个检查的耗时界；第一次读取起点时还需要全量词法和统计。动态部分的运行次数：撤回试验在需要保留的候选少时接近对数级，多时接近逐个运行；变异等于抽到的变异数，由抽样的停止规则和预算控制。单次运行的耗时由项目自己的命令决定。

## 十一、边界

- 用户意图本身无法计算。原话锚定只覆盖用户说出的词；其余部分靠交付报告中的“未经要求的新增”和“由 Agent 说明对应需求的新增”让用户看见。
- 需求相关区和锚定只说明词汇上的对应，不说明授权或必要性；Agent 写的需求内容和实现位置也会扩大相关区。所以它们只用于排序和排除，拦截另有事实条件。
- 验证输入不包含 Agent 之外的变化：用户在其他终端修改环境变量、数据库或服务时，TaskBelay 观察不到。重复验证的拦截附上次输出和重跑方式，Agent 用 `note_add` 写明理由后即可重跑。
- 撤回试验只说明“撤回后验收依据仍然通过”。验收依据覆盖不到的行为不能由此判断，所以缺少验收依据时只作提示。
- 防御性代码（错误处理、参数校验）的必要性在验收中通常看不出来，不作为撤回候选，条件见 [过度设计判定](over-design.md)。
- 局部推送、分组检验和贪心集合覆盖的数学界各有前提，不等于产品的实际效果；效果按 [算法评估](product-evaluation.md) 测量。
- 文本提供的结构信息少时，结构置信度低，结论变少而不是变错；样本少的新仓库同样更保守。
