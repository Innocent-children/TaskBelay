# 语言无关的算法核心

TaskBelay 用同一套内容表示判断过度设计和过度测试。算法只分析本次改动及其邻域：先根据静态信号找出候选并排序，再在副本中实际运行，确认相关判断。判断所需的语言知识全部从仓库自身的内容和运行记录中统计得到。算法不为特定语言编写规则，也不以代码行数、用例条数或运行次数的固定阈值下结论。

统一表示和运行方式见 [输入与执行协议](languages.md)，两类判定分别见 [过度设计判定](over-design.md) 和 [过度测试判定](over-testing.md)。

## 设计原则

1. **局部计算**：静态部分的工作量取决于改动及其邻域的规模，不随仓库总规模增长。
2. **用静态信号提出候选，用运行结果确认判断，按事实决定拦截**：统计和词汇信号只用来找出候选、给候选排序。通过实际运行判断“这处改动是否需要”“这条用例是否有用”；报告中的运行结论都经过确认运行。拦截只依据能直接核对的事实：文件和清单的内容、探针输出、账本中的登记、确认运行的结果和完全相同的验证输入。
3. **从仓库学习**：关键字、注释写法、测试写法和约定入口按文件扩展名分组统计，算法不知道扩展名对应什么语言。
4. **可以复核**：每个结论附带输入版本、来源和推导路径。信息不足时结论是未知，不当作通过。
5. **持续校准**：信号的权重按本项目中反馈的实际结果更新，用于给建议排序。
6. **本机完成**：全部计算在本机进行，只运行项目自己的命令，不调用外部模型或网络服务。

文中的 ε、α 等是精度和预算参数，只影响近似程度和耗时，不是判定阈值。算法合并各项信号，并根据校准结果给建议排序；是否拦截，由第六节列出的事实条件决定。

## 总流程

```text
交付检查(任务):
  Δ ← 词级差分(起点快照, 当前快照)
  G ← 强连通分量缩点(hunk 依赖(Δ))                                  # 变更簇
  对每条有效需求 R:
      相关区[R] ← 扫描切割(局部推送(种子(R), 代码图))
  候选 ← 相关区外的簇 ∪ 没有对应说明的对外新增项 ∪ 没有变化的间接层 ∪ 近似重复 ∪ 没人使用的代码
  动态检查开启且有验收依据时:
      可撤回 ← 分组检验(候选中全部来自 Agent 编辑的簇, G, 验收依据) 后确认运行
      保留用例 ← 贪心集合覆盖(去冗余(逐个变异运行得到的发现矩阵), 保留集合) 后确认运行
  拦截 ← 满足第六节事实条件的候选
  反馈 ← 背包选择(合并信号(其余候选), 反馈预算)
```

动态步骤在 session 的 MCP 进程中后台进行，交付时使用已有结果，见第九节。

## 一、输入

| 输入 | 内容 |
| --- | --- |
| 内容 | 任务起点快照、当前快照、累计 diff 和各文件的 blob 标识 |
| 来源 | 可核对的 Agent 编辑、Agent 命令写入、工作区更新及其所在的工具调用 |
| 需求 | 用户原话与引用、需求内容、验收标准、实现位置、有效方案和用户决定 |
| 用途说明 | 当前需求下的可疑对象、Agent 的判断、代码出处、独立依据及记录时的观察点 |
| 运行记录 | 命令、目录、参数、环境摘要、工具标识、输出、退出状态和时间 |
| 仓库统计 | 按 [输入与执行协议](languages.md) 从起点内容学到的词法、版面和约定 |

一次计算只使用同一组输入版本。发布结果前再次核对版本；版本已变化时，结果只保存为历史。

## 二、变更簇

累计 diff 先按行比较（Myers 算法，O((N+M)D)），再在每个 hunk 内部按词比较，得到实际改变的词。每个 hunk 归入一类：

| 类别 | 判断方式 |
| --- | --- |
| 只改空白或注释 | 两侧去掉空白和注释后的词序列相同 |
| 一致改名 | 两侧词序列之间存在标识符的一一对应，O(n) 可以检查 |
| 移动 | 删除侧的内容在新增侧完整出现（winnowing 选出的 k-gram 哈希全部匹配） |
| 行为改动 | 其余情况 |

**新词**是起点词表里没有、当前内容里出现的标识符。hunk 之间按两种关系建立依赖：

- hunk B 用到了 hunk A 引入的新词，B 依赖 A。
- hunk A 改了某个单元的首行，hunk B 改了含这个单元名字的行，两者互相依赖。

用 Tarjan 算法求强连通分量（O(V+E)）并缩点，得到一张有向无环图，每个节点是一个**变更簇**。保留和撤回都以变更簇为单位；撤回一个簇时，依赖它的簇一并撤回，因此不会留下悬空的引用。如果一次运行失败，输出无法解析出单条用例结果，却同时提到了撤回簇与保留簇中的新增声明，就记录这条关联，合并涉及的 Agent 变更簇后重新计算。无法定位相关声明时，结论保留为未知，不能仅凭运行失败就认定某个簇必须保留。

每个变更簇记录来源：全部来自可核对的 Agent 编辑、含 Agent 命令写入、全部来自工作区更新，或混有工作区更新。只有全部来自 Agent 编辑的簇可以成为撤回候选；含命令写入的簇可以给出精简建议，不拦截；其余的簇保留当前内容，只报告现状。

## 三、需求相关区

需求相关区回答“哪些单元和变更簇与这条需求有关”。算法通过图聚类，找出围绕需求形成的社区，作为需求相关区；不再沿同名引用无限扩大归属范围。

### 图

| 节点之间 | 边权 |
| --- | --- |
| 单元—标识符 | `idf(词) × log(1 + 该词在单元中出现的次数)` |
| 变更簇—单元 | 变更簇改动了这个单元 |
| 变更簇—变更簇 | 同一次编辑调用写出，代表 Agent 自己的工作分组 |
| 单元—文件 | 包含关系，权重较低 |

`idf(词) = log(单元总数 ÷ 含这个词的单元数)`。`err`、`i`、`ctx` 这类常见词的 idf 接近零，边权低于精度参数 ε 的边不建立。新词只出现在少数单元里，idf 很高，所以“新代码使用新代码”是强连接，“都调用了同一个日志函数”是弱连接。

### 种子

种子规定局部推送从哪些节点开始，以及最初分配给各节点的质量：

1. **用户原话**：用 Aho–Corasick 自动机（O(文本长度 + 匹配数)）一次匹配仓库词表，包括完整标识符、按驼峰和下划线拆开的子词、文件路径和 `路径:行号`。
2. **已确认方案**：半自动模式下方案的涉及范围和对外入口，与原话同等对待。
3. **需求内容和验收标准**：Agent 写的需求内容常把原话转述成代码里的词，例如“export 命令通过 `--format csv` 输出 CSV”。按同样方式匹配，权重低于原话。
4. **实现位置**：Agent 登记的位置，权重最低。

各类种子的相对权重由校准决定（见第七节）。在最强路径的起点，记录各来源所占的质量，并将这些数值一起用于拟合。再根据拟合结果调整各来源分配的质量，始终保持原话优先于需求内容、需求内容优先于实现位置。原话、方案和需求内容都匹配不到任何词时，这条需求的相关区为未知，与它有关的判断只作提示。

### 计算

对每条需求，用 Andersen–Chung–Lang 局部推送算法近似计算个性化 PageRank：每次取一个残量较大的节点，把残量的 α 部分记为它的得分，其余按边权推给邻居，直到每个节点的残量都小于 ε 乘以它的度。推送的总工作量为 O(1/(εα))，与图的总规模无关。

然后按“得分 ÷ 度”从高到低排列节点，依次计算每个前缀集合的导率（conductance：集合对外的边权之和，除以集合与其余部分中边权总和较小的一侧），取导率最小的前缀作为需求相关区。这一步的代价为 O(s log s)，s 是得分不为零的节点数。该方法有 Cheeger 型保证：种子所在区域若存在导率为 φ 的集合，对其中大部分种子，找到的集合导率不超过 O(√(φ·log m))，m 为边数。

### 解释

每个变更簇记录它到各需求相关区的最强路径：在边长为 −log(归一化边权) 的图上用 Dijkstra 算法求最短路。报告给出路径上的关键节点，例如“只经由常见词 `Info` 与 R1 相连”。

## 四、验收依据

验收依据是判断改动是否需要、用例是否有用时采用的运行标准：

- **既有行为**：起点已有的测试和检查命令中，在当前快照的副本里能通过的部分。
- **实现前登记的验收**：需求的验收标准写明用哪条用例或哪条命令确认结果。若保存这版验收标准的时间早于 Agent 在该需求相关区内的首次编辑，就将它作为验收依据；若晚于首次编辑，则只作为补充依据，所得结论只用于提示。半自动模式下，方案成功标准中写明的用例或命令随方案一起确认，并在开发前登记，因此满足这个条件。
- **用户点名的用例**：用户原话中要求编写或保留的用例。

验收标准里的用例名和命令，与测试单元的名字及已观察到的命令按词匹配；匹配不到时，这条验收标准记为未落实。

实现以后才写、只服务于新增功能的测试不属于验收依据，否则多出来的功能和为它写的测试会互相证明对方必要。

每次试验都运行验收依据中列出的全部用例和检查命令。其中，检查既有行为的用例和命令由所有变更簇共用；实现前登记的验收和用户点名的用例则分别对应各自的需求。一条需求没有自己的验收依据时，不根据撤回试验或变异对其相关区内的变更簇下结论，只使用静态信号提出建议。这是因为起点已有的测试通常覆盖不到新功能，只用它们判断，会得出“整个新功能都可以撤回”的错误结论。

## 五、分组检验

撤回试验（见 [过度设计判定](over-design.md)）要回答：n 个候选变更簇里，哪些撤回后会使验收依据中的用例或命令运行失败。逐个检验需要运行 n 次；分组检验则用一次运行同时检验一组候选。

- 每次先在副本中同时撤回一组候选，再运行验收依据中列出的全部用例和命令。全部通过，说明这组候选可以一起撤回；失败时再将这组候选二分。
- 采用 Hwang 的广义二分法。设 d 是撤回后会导致失败、需要保留的候选数，运行次数约为 `d·log₂(n/d) + O(d)`，接近信息论下界 `log₂ C(n,d)`。d 远小于 n 时节省明显；d 接近 n 时接近逐个运行。
- 候选只取静态信号标出的变更簇，可信度低、可能需要保留的先单独检验。静态信号越准，d 越小。
- 失败组合按二分缩小范围；输出能核对到不同簇的新增声明时，按第二节补充依赖并合并。

分组检验的效率依赖一个假设：组内任何一个候选撤回后会导致失败，整组撤回也会失败。候选之间互相抵消时，这个假设不成立，因此最终结论都要经过一次**确认运行**：将最终的撤回集合整体应用到副本，再运行一次验收依据中的全部用例和命令。结论只针对这一整组，给出的撤回补丁也正是这一组，所以假设不成立只会让找到的候选变少，不会产生错误结论。

确认运行失败，说明有几个候选单独可以撤回、合在一起不行。这时按可信度从高到低，把候选逐个加入撤回集合，每加入一个运行一次，失败就把它移出；以最后一次通过的集合为结论，预算到期时同样以最后一次通过的集合为准。

这条保证只适用于撤回试验。变异需要知道每条用例分别发现了哪些变异，成组运行时互相抵消的变异会让用例看起来什么都没发现，所以变异逐个运行，见 [过度测试判定](over-testing.md)。

## 六、合并信号与选择反馈

### 用途核对

执行 Agent 只对值得核对的改动补充用途。它可沿用检查指出的位置，也可主动指出配置、兼容层、恢复分支或测试中的可疑实现。用 `note_add` 关联有效需求，写明精简后哪个行为会怎样变化，引用被核对的代码，并按需提供用户原话、有效方案或其他具体代码作为依据。笔记参数见[任务账本](requirements-ledger.md#笔记和用户决定)。

检查从笔记的观察点和本次检查的固定快照读取所引文件。对象片段须可准确定位并触及当前改动。代码依据须位于独立的位置。仅用代码支持解释时，还要核对起点已有的原文、它是否落在改动之外，以及两处是否在同一声明内、引用对方声明名或含有同名调用形状。这些联系应按实际识别结果展示，无法据此证明所有调用方受同一保证约束。用户原话按当前需求的引用范围核对。方案以当前有效版本为准，部分撤销后不能确认自由文本的适用范围时保留缺口。项目约定应有与起点及当前文件一致的内容标识。检查能确认引用和位置，业务解释由 Agent 给出。

对象须触及当前新增或修改的代码行。核对来源时，还要计入片段内部被删除的行；片段边界之外的删除归于各自的位置。代码依据的行号指向记录时的文件。核对起点原文时，按累计差异将未改动的片段映射回起点的对应行，再核对原文及唯一性。

当前改动中的用途说明进入完整检查报告，按已有反馈预算选择展示。有适用依据时展示保留理由或有条件的精简建议。对象或依据文件已变化、引用有歧义、需求含义已改变、只有自身或没有独立依据时，指出具体缺口，保留当前行为。同一需求、类别和对象采用最新说明。需求已撤销，或对象文件已没有新增或修改的代码行时，历史笔记仅供查阅。含工作区更新的对象只报告现状。用途判断只作提示，不能授予编辑、放行或保留权限。新增用途提示不作为动态撤回候选。检查输入包含用途笔记，新增或更正说明后重新生成报告。

### 合并信号

每个候选有一组信号，例如是否在需求相关区内、需求对应关系的级别、撤回试验的结果、相似度、变化数、来源、是否在方案中，以及所在文件的结构置信度。算法合并这些信号，算出这条建议的**可信度**：按本项目的反馈记录估计同类建议成立的概率。

```text
log-odds(成立) = w₀ + Σ wᵢ · xᵢ
```

xᵢ 是第 i 个信号的取值，权重 wᵢ 用逻辑回归从第七节的标签中拟合。所有信号一起拟合：需求相关区、需求对应关系和没人使用的代码都从同一套词汇关系中识别。一起拟合时，它们分摊权重，避免将同一条依据重复计入。拟合时加入 L2 正则，使结果向随程序发布的初始权重收缩；样本少时，结果接近初始权重。初始权重是保守先验，不代表真实 Agent 效果的实测结果。拟合使用本项目积累的标签；没有本项目标签时，先采用本机全部项目的标签。具体取值集中在对应包的 `params.go`，真实效果按 [算法评估](product-evaluation.md) 核对。

可信度只用于给建议排序和选择反馈条目，不决定拦截。

### 选择反馈条目

反馈长度受预算限制。每个候选的收益是撤回后减少的行数、新词数和测试运行耗时。算法在总长度预算和每类条目数上限内，选择使 Σ 收益 × 可信度 最大的一组候选。这是带分类上限的 0/1 背包问题；候选数量不大，可以用动态规划精确求解。先对每一类按条目数约束做动态规划，再合并各类的容量曲线；复杂度为 O(n·B·L + C·B²)，B 是按固定单位换算的预算，L 是每类上限，C 是类别数。

每条反馈写明具体动作：撤回哪个变更簇、用什么替换哪几处、删除或合并哪几条用例，并附确认运行的结果，或说明尚未运行。

### 拦截

拦截只依据能直接核对的事实。以下三类条目满足全部条件时，可以拦截一次，识别方式见两份判定文档：

1. **对外新增项**：识别方式可靠，即新文件、清单中新增的依赖，或探针确认的新增项；全部来自 Agent 编辑；名字和取值在原话和已确认方案中都找不到；没有登记为任何需求的实现位置。仅按键值版面识别的配置键可能是内部常量，与注册式调用和入口字面量一样，未经探针确认只作提示。
2. **可以撤回又与需求无关的变更簇**：撤回试验的确认运行通过；整组补丁中的簇都不在任何需求相关区内；涉及的单元没有登记为任何需求的实现位置。附确认过的整组补丁，不能把整组通过推断为其中任意子集可单独撤回。
3. **重复验证**：验证输入与上次通过时完全相同，附上次的输出。

前两类被拦截后，Agent 可以撤回；也可以用 `requirement_save` 把它登记为某条需求的实现位置，并引用对应的原话。登记过的条目列入交付报告的“由 Agent 说明对应需求的新增”，用户能直接看到。需求相关区和需求对应关系都根据词汇匹配建立，在这里只用来排除有对应关系的条目，不用来证明哪处改动有必要。其余条目都是按可信度排好序的建议。

## 七、校准

TaskBelay 根据每条反馈之后实际发生的情况，自动为这条反馈生成标签：

| 之后发生的事 | 标签 |
| --- | --- |
| Agent 照建议删除了内容，到任务完成时仍未恢复这些内容 | 成立 |
| Agent 拒绝，之后用户自己删除了这部分 | 成立（记为漏判） |
| Agent 照做，之后用户把内容加了回来（用 MinHash 识别相似内容再次出现） | 不成立 |
| Agent 照做，之后验收依据中的用例或命令运行失败，且失败与撤回的内容有关 | 不成立 |
| Agent 拒绝，理由可以核对：用户原话要求保留、需要保留的变更簇依赖这部分内容，或撤回后验收依据中的用例或命令会运行失败 | 不成立 |

每次反馈对应一条标签；后续恢复内容或相关验收失败时，更新这条标签，不将同一次反馈的不同结果重复计数。标签用于拟合第六节的权重。某个信号不能区分结果时，它的权重自动趋近于零；某类建议不成立的情况增多时，它的可信度随之下降，在反馈中排得更靠后。

“Agent 照建议删除了内容，之后没有恢复”只说明这次修改保留了下来。Agent 通常会按反馈处理；如果用户没有注意到问题，或换一种写法重新实现，误判也可能被记为成立。因此，可信度衡量的是建议被采纳后，相关修改保留下来的程度，只用于排序。拦截条件不依赖它；拦截是否正确，按 [算法评估](product-evaluation.md) 人工核对。

TaskBelay 记录问题实际展示时的快照、内容签名和观察编号，再根据后续编辑记录判断 Agent 是否删除过对应内容，以及之后是否恢复内容、完成交付或出现相关验收失败。校准直接使用编辑和运行记录，不要求 Agent 先用笔记说明删除操作。保留理由可用 `note_add` 关联到检查问题：以用户要求为理由时带 `quote` 和 `source_id`；以依赖或验收为理由时写明对应的位置或用例，由 TaskBelay 根据依赖图和运行记录核对。

采纳建议后出现验收失败，只有满足以下条件，才将失败关联到这条反馈：两次运行使用同一命令、环境和工具；两次固定快照之间只有已记录的撤回文件不同；已登记的验收由通过变为失败。工作区更新只能说明这部分变化无法归入已核对的 Agent 编辑，不能直接证明操作者是用户。内容来源混合、缺少连续编辑记录或无法识别内容时，不生成标签。同一问题发生记录即使重复展示或收到多条笔记，也只更新同一条标签。

## 八、问题标识与完成状态

一份报告分别表达四个维度，不用一个“通过”同时代表它们：

| 维度 | 内容 |
| --- | --- |
| 处理状态 | 计划的计算和运行是否完成，是否超时、取消或失败 |
| 依据范围 | 哪些候选有运行结果，哪些只有静态信号，哪些因相关区未知、缺少验收依据或运行失败而未知 |
| 结论 | 各候选的可信度、拦截所依据的事实、确认运行结果、保留集合和未检验的范围 |
| 产品动作 | 放行、提示或拦截一次，以及适用对象 |

没有候选、验收依据中没有可运行的用例或命令、运行超时和程序出错，都不能写成“没有多余”或“测试足够”。

问题标识由任务、问题种类、所指对象和关键事实确定。所指对象通过变更簇、对外新增项、单元或用例的稳定标识定位；检测到对象移动后，仍沿用原来的问题标识。修改其他文件、补充笔记或格式化不产生新问题；问题解决后再次引入，增加一次发生记录。同一问题每个 session 最多拦截一次，每轮合计最多三次；这是交互上限，不是判定阈值。

## 九、什么时候计算

首次建立起点索引时，先学习全仓库约定，再逐文件将归属清单、学习摘要和单元写入尚未发布的代次。跨文件统计只保留随后还会用到的结构。文件词流缓存保存一份原文和每个词的类型与长度，读取单元时还原对应范围，也可以读取旧格式。计算图体积时，先把文档频率和单元词频相同的贡献按整数计数合并，再计算各项权重。

起点 tree 对应一份持久索引，保存词到单元的倒排索引、出现计数与 df、单元总数、首行与名字、约定与测试划分、MinHash/LSH 分桶和名字使用计数。文件词流按 blob 与词法约定保存；检查只读取累计 diff 中的文件及实际访问的邻域。覆盖层先记录成员增减，查询某个键时，才将这些变化与该键的起点记录合并。图推送按节点查询邻居，根据当前单元总数和 df 计算边权，并从计数汇总中取得图体积。解释关联的路径只在推送访问的邻域内寻找；没有找到路径时，结论保留为未知。

起点变化时，根据 Git 提供的两个 tree 之间的差异，只更新变化文件的内容分析结果。学习约定时，使用按文件保存的计数与首行汇总；词法约定变化时，重算受影响的扩展名组；测试模型变化时，更新对应的测试划分。间接层先验按结构摘要和查询依赖更新；关键字、返回写法或调用识别发生变化时，重新计算对应扩展名组的摘要，完成后发布新的索引版本。后续运行结束后，如果增加了初始测试样本，也生成独立版本。若起点、约定和运行样本均与已有缓存一致，就复用缓存，不再重新合并全仓库的统计结果。统计摘要按键分页读取，在事务外合并版本；索引行通过短事务分批写入，最后发布根记录。未完成的版本不能用于判断。

验证输入保存可增减的文件摘要，以及纳入和排除的文件数量；根据起点索引和当前 tree 确定文件集合。普通代码变化时，只替换变化文件的摘要，并更新它直接引用的文档；文档变化时，通过字面引用索引和 glob 倒排索引反查相关代码。报告保存本次计算的输入、改动和结论，不重新序列化全仓库的文件分析结果。

同一次检查中的覆盖层复用只读起点索引的读取缓存，合并成员时复制映射。发布时，已读父层中值相同的成员直接继承。索引按行数和字节数分批，将相邻条目合成可按键查找的压缩页，在短事务中一起保存页正文和目录。各批保存完成后发布索引根，查询按原有层次处理新增、覆盖和删除。存储格式见[系统架构](product-architecture.md#存储和修订)。

编辑来源只还原当前累计差异涉及、且曾有已核对 Agent 编辑或 Agent 命令写入的文件；仅有工作区更新的文件不能据此变成 Agent 编辑，无需重放其正文。需要还原的文件仍读取完整变更链，保留混合来源的保护。已删除且起点不存在的临时文件不参加当前改动判断。反馈校准先排除其他算法版本的记录，再读取对应快照。

| 时机 | 计算内容 |
| --- | --- |
| 用户消息 | 匹配种子并在起点图上执行局部推送，再提示 Agent 可复用哪些与需求关系最密切、使用最广的已有单元；使用已发布的索引 |
| 编辑前 | 对目标的当前与拟写入内容做增量词法，检查新文件、对外新增项、近似重复及相邻调用赋值和条件分支中的调用，恢复用途只供核对，见[防御处理的核对](over-design.md#防御处理的核对)；抽象和转发包装只用目标内容计算结构，分别核对隔离用途与包装职责，见[编辑前核对抽象用途](over-design.md#编辑前核对抽象用途)和[编辑前核对转发包装](over-design.md#编辑前核对转发包装)；相近测试复用等价类及断言比较，按已发布索引补齐直接参照并核对其内容仍有效，见 [编辑前提醒](over-testing.md#编辑前提醒) |
| 命令前 | 对非只读命令保存工作区观察，使用已发布的索引和状态摘要比较验证输入，需要判断跨命令关系时查询历史输入与结果 |
| 命令后 | 更新验证输入记录，保存当前状态的验证输入摘要；使用已发布的索引 |
| MCP 调用后 | 在后台为当前任务建立起点索引，并入新的运行输出 |
| 交付 | 更新变更簇、需求相关区和各项静态信号，合并信号并选择反馈 |
| 动态检查开启时 | 撤回试验和变异在 session 的 MCP 进程中后台进行，结果逐步写入账本 |

编辑前对已识别的新文件，提示核对使用者、当前需求、已有文件能否承接及独立维护成本，不把缺少代码引用当作没有用途的证据，见[编辑前核对新增文件](over-design.md#编辑前核对新增文件)。对已识别的参数、环境变量、路由字面量和注册式调用候选，补充已有取值片段，提示核对实际入口、当前使用者、需求、已有入口和使用维护成本，见[编辑前核对新增入口](over-design.md#编辑前核对新增入口)。对已识别的新增依赖补充版本片段，提示核对当前用途、已有实现和引入成本，见[编辑前核对新增依赖](over-design.md#编辑前核对新增依赖)。这些提醒沿用原有需求匹配，只作附加上下文，不改变修改后检查。

编辑前的新增测试用途提醒复用已有测试侧调用和断言词识别，不依赖等价类比较，不把词汇依据当作测试多余的证明。已有和明确保留的用例不重新提醒，不因此追加断言或验证，见 [编辑前提醒](over-testing.md#编辑前提醒)。

编辑前的重复实现建议先核对起点索引中的参照仍有效：请求外的文件按当前内容及模式核对，每个候选文件只读一次；同批目标中的声明须在当前与拟写入内容中都保持原位置、范围和完整词流。失效参照略过，不扩大检索范围；读取失败或超时沿用预览略过规则。具体边界见[重复实现与没人使用的代码](over-design.md#5-重复实现与没人使用的代码)。

多个 session 同时为同一项目、起点和索引变体预热时，共用账本的 MCP 进程通过操作系统锁选出一个构建者。其他进程可继续响应工具调用，并在后台查看发布结果。构建进程中途退出时，等待者可接手。锁不可用时，各进程可以独立构建，索引仍通过账本的代次核对原子发布。前台交付检查使用原有时间预算。

允许执行动态检查时，Agent 调用 `task_finish` 或 `check_run` 会使 MCP 进程开始在后台运行。MCP 进程收到其他调用时，若发现输入已变化且当前没有运行中的动态任务，也会开始后台运行。后台定时读取已登记的任务输入，并查询账本中的运行记录，避免对相同输入重复运行。

动态检查可以随时停止。停止时，已完成的确认运行仍然有效，交付使用已有结果。若结果尚未完成，Stop 会在动态检查预算内继续运行或等待后台结果；预算到期后使用已完成的部分，其余部分只给出静态结论。后台运行使用较低的优先级，Agent 开始自己的验证时暂停；预算到期时终止本次启动的进程并清理副本。有新内容或用户主动刷新时，复用未变化的词法结果，再按新输入重新计算相关结果。

## 十、复杂度

| 环节 | 算法 | 复杂度 | 规模取决于 |
| --- | --- | --- | --- |
| 词法与版面 | 确定有限自动机、栈、缩进层级 | O(字节数)，按 blob 缓存 | 变化的文件 |
| 仓库统计 | 计数与对数几率比 | O(词数)，按 blob 累加 | 变化的文件 |
| 差分 | Myers 行差分 + 词级差分 | O((N+M)D) | 改动大小 |
| 变更簇 | Tarjan 强连通分量 | O(V+E) | 改动大小 |
| 种子 | Aho–Corasick | O(文本 + 匹配数) | 消息与需求长度 |
| 需求相关区 | 局部推送 + 扫描切割 | O(1/(εα)) + O(s log s) | 与仓库规模无关 |
| 近似重复 | MinHash + LSH | 签名 O(n)，查询期望 O(1) | 改动大小 |
| 变化度 | 括号配对 + 集合包含 | O(新词出现次数) | 改动大小 |
| 等价类 | 排序 + 二分查找 | O(用例数 × log 常量数) | 改动大小 |
| 撤回试验 | 广义二分分组检验 | 约 d·log₂(n/d)+O(d) 次运行，d 接近 n 时接近 n 次 | 候选数与需要保留的数目 |
| 测试约简 | 逐个变异运行 + 去冗余变异 + 贪心集合覆盖 | 每个抽到的变异运行一次 | 抽样数 |
| 反馈 | 逻辑回归打分 + 0/1 背包 | 打分 O(n)，选择 O(n·B·L + C·B²) | 候选数 |
| 校准 | 带 L2 正则的逻辑回归 | 每轮迭代 O(样本数 × 信号数) | 标签数 |

缓存命中时，静态部分的计算量只和改动规模有关；第一次进入一个仓库时，通过一次线性扫描完成全量词法分析和统计。动态部分的运行次数取决于候选和抽样结果：撤回试验在需要保留的候选少时接近对数级，多时接近逐个运行；变异运行次数等于抽到的变异数，由抽样的停止规则和预算控制。单次运行的耗时由项目自己的命令决定。

## 十一、边界

- 用户意图本身无法计算。“原话对应”只核对用户说出的词；其余部分列在交付报告的“未经要求的新增”和“由 Agent 说明对应需求的新增”中，让用户看见。
- 需求相关区和需求对应关系只说明词汇匹配情况，不能证明用户已经授权，也不能证明改动有必要；Agent 写的需求内容和实现位置也会扩大相关区。因此，它们只用于排序和排除，拦截另有事实条件。
- 验证输入无法反映 TaskBelay 未观察到的外部变化，例如用户在其他终端修改环境变量、数据库或服务。重复验证的拦截附上次输出和重跑方式，Agent 用 `note_add` 写明理由后即可重跑。
- 撤回试验只说明“撤回后，验收依据中列出的用例和命令仍然通过”。这些用例和命令没有覆盖的行为，不能由此判断，所以缺少验收依据时只作提示。
- 防御性代码（错误处理、参数校验）的必要性在验收中通常看不出来，不作为撤回候选，条件见 [过度设计判定](over-design.md)。
- 局部推送、分组检验和贪心集合覆盖的数学界各有前提，不等于产品的实际效果；效果按 [算法评估](product-evaluation.md) 测量。
- 文本提供的结构信息少时，结构置信度低，结论变少而不是变错；样本少的新仓库同样更保守。
