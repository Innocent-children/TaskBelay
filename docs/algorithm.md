# 算法设计

过度设计检查和过度测试检查共用事实与证据：前者寻找满足当前需求、维护负担较低的实现，后者选择能回答当前问题、成本较低的验证操作。两项检查都必须保留已有的有效行为和用户修改，不能根据开发语言、代码行数或测试次数直接裁定。

本文描述的新算法尚未实现。现有语言适配、规则、命令配置和账本格式见 [文档说明](README.md)。本文的数据结构尚不属于已发布的 MCP 接口，也未指定外部模型服务。

## 输入信息与证据要求

算法输入由任务起点、当前内容、累计改动、可核对编辑、需求及授权、验证观察组成。所有来源带内容版本；一次求解只使用同一输入版本。具体采集协议见 [分析输入与验证执行](languages.md)。

| 对象 | 说明 |
| --- | --- |
| 需求与约束 | 用户要求、有效方案、直接相关的既有行为和工程约束 |
| 改动单元 | 带文件、内容标识和范围的新增、修改、删除、移动；允许无法拆分 |
| 实现机制 | 完成行为的一组代码、配置、依赖及状态；不是某种语言的语法节点 |
| 待验证问题 | 尚需回答的行为问题，包含前提、动作、可观察结果和适用环境 |
| 操作 | 检查、测试、构建或具体精简方案，带前提、成本与输出约定 |
| 观察与证据 | 实际发生的结果，以及它支持什么、在什么范围内有效 |

文件内容、命令结果和用户消息属于可观察事实；“这个接口有必要”“此用例覆盖错误恢复”属于需要依据的语义判断。Agent 或独立语义复核可提出候选关系，但必须附来源、准确位置、版本、成立条件和不确定项。引用能够在原文中找到，只证明出处；不能证明解释正确。多个模型重复同一说法也不产生多份独立证据。

算法不依赖特定的 AST 或测试 Runner。已有解析器、执行跟踪和项目声明可以提供事实，判定标准保持一致。无法确定某段内容的含义时，应列出无法判断的问题，不能因此认定某门语言不适用，也不能将检查记为通过。

## 证据关系与版本管理

用有向超图 `G=(V,E)` 保存支持关系。普通依赖边表示“可能使用或影响”，支持超边表示“这些前提共同支持这个结论”。两者分别建索引，不能把可达性当成需求归属。

```text
Fact    = { id, kind, content_hash, scope, source_ids, validity }
Support = { premises[], conclusion, evidence_ids[], certainty }
```

`{A,B} → R` 表示 A 和 B 同时成立才支持 R；另有 `{C} → R` 时，C 是另一条支持路径。证据状态区分已核对、候选、未知和已失效。只有已核对的关系能参与确定结论；含候选关系的方案只能作为待复核建议。

候选进入确认关系图前，依次核对来源内容与版本、关系对应的实际行为及成立条件、与有效需求和已有证据是否冲突。直接观察须能绑定到具体调用或内容；语义关系须保存复核依据，不能仅凭模型自报的置信度将其标为已核对。范围或含义仍有歧义时保持候选。复核无法证明的前提，必须在结果中明确列出。

图保存两种视图：

- **确认关系图**：用于推导当前能够成立的结论，所有前提与支持关系均有有效依据。
- **可能依赖图**：用于确定可能失效的证据，包含已知依赖、候选依赖和未知范围标记。候选列表不完整时，必须连接相应的未知范围；不能把搜索到的候选当作全部可能依赖。

依赖完整性是单独的证据。反射、插件发现、目录枚举、配置驱动和外部状态等范围没有核实时，只能扩大失效范围或保持未知。“没有观察到调用”不能推出“没有调用”。

### 内容标识与增量更新

内容块以摘要标识，文件集合可组织为 Merkle 结构；反向索引记录内容、需求、授权、配置及环境到结论的依赖。摘要用于内容相等比较，不证明语义等价。发现变更仍需要实际观察，Merkle 结构不免除读文件或枚举目录的成本。

一次更新执行以下步骤：

1. 核对新输入版本，找出改变或失效的根事实。
2. 沿可能依赖图确定受影响闭包；未知范围一并展开到相应边界。
3. 撤回闭包中受影响的派生结论，保留原始观察与历史结论。
4. 从仍有效的根事实、闭包外有效支持重新推导；所有前提成立的超边才激活结论。
5. 更新对应约束分量、待验证问题和候选操作。发布前再次核对输入版本，短事务发布；版本变化则只保存历史结果。

删除后重推导采用 DRed 的思想，不能仅用引用计数保留循环。若 A 只由 B 支持、B 只由 A 支持，最后一个外部有效根被删除后，两者均不成立。实现可在受影响区域使用待处理队列和超边未满足前提计数；同一阶段每个节点与每次关联只处理一次。

在固定、有限、已实例化的正向支持超图上，维护成本为 `O(nΔ + mΔ)`，其中 `nΔ` 是受影响节点数，`mΔ` 是该区域处理的前提与结论关联数。边的数量不能代替关联数。含否定的事实须先把作用范围和版本确定下来，作为根事实输入；不宣称上述界覆盖任意规则语言。全局配置或广泛未知依赖变化时，受影响区域可能就是整张图。

语义提取、候选搜索、内容采集、约束求解不包括在这项线性界内。图中部分区域尚未生成，也不能称为已维护整个项目。

## 设计检查与验证选择

| 决策 | 数学模型 | 输出 |
| --- | --- | --- |
| 保留哪些实现机制 | 满足硬约束的有限域成本最小化 | 具体可行的简化方案、必要性依据、取舍或未知 |
| 下一步做哪些验证 | 对尚未回答的问题做加权集合覆盖 | 有成本依据的操作顺序、现有证据复用及停止条件 |

过度设计的变量、约束、树分解和求解证书见 [过度设计判定](over-design.md)。验证覆盖、依赖失效和重复运行见 [过度测试判定](over-testing.md)。两个优化器都不能为降低分数改变需求、删除用户修改或自动增加验证目标。

## 检查状态与结论

一份报告至少分别表达以下四个维度，不用一个“通过”同时表示它们：

| 维度 | 必须表达的内容 |
| --- | --- |
| 处理状态 | 本次计划的处理是否完成，是否超时、取消或失败 |
| 证据范围 | 已回答的问题、仍未知的问题、依赖边界和来源版本 |
| 求解结果 | 可行方案、已证明的模型内最优或不可行、上下界及未搜索范围 |
| 处理方式 | 放行、提示、有限拦截；依据与适用对象 |

处理完所有已知输入不等于需求已经验证。没有生成候选、没有可用命令、求解超时和程序出错都不能写成“无需修改”或“零测试足够”。程序正常退出也不等于业务验收通过。

可直接核对的越界行为或重复验证满足完整条件时，可按产品规则拦截一次。工程取舍只提示；未知不构成拦截理由。历史问题暂时无法复核时保留原状态并注明未知，不静默改成已解决。

问题身份由任务、问题性质、逻辑对象与关键事实确定，具体位置只是显示信息。同一问题移动、其他文件修改或普通笔记追加不重置身份；解决后再次引入可增加发生记录。同一问题每个 session 最多拦一次，每轮合计最多三次；这些是交互上限，不是过度设计或测试的判定阈值。

## 时间限制与运行成本

一次检查使用共同截止时间，分别记录采集、语义提取、图维护、求解、实际验证和发布耗时。快速 hook 只做已索引事实的核对与必要失效标记，不在每次工具调用前运行完整语义分析或全局求解。没有可复用依据时先放行并保留未知，交付或明确检查时再按预算处理。

优先处理本次改动及直接、间接影响；已有分量和有效证据按依赖版本复用。预算到期保存已完成的独立结论和未完成范围；不得为凑齐报告自动开启下一轮检查、扩大测试集或反复运行模型。下一次有新事实或用户主动刷新时，才重新安排相关工作。

设采集、语义提取和实际命令成本分别为 `Tcollect`、`Tsemantic`、`Texec`，一次检查总成本为：

```text
T = Tcollect + Tsemantic + Tgraph + Tsolve + Tselect + Texec + Tpublish
```

图维护、低树宽求解和集合覆盖的复杂度都有适用前提，这些结果不能保证任意项目都能在毫秒内完成。大型共享依赖、稠密约束和语义不确定性可能主导成本。预算控制最坏等待时间，不能消除难问题，也不能把超时转成正确结论。

## 实现要求与适用条件

判定逻辑接收统一格式的事实和操作，不接收“语言支持等级”。同构的事实、约束与操作输入，经过确定的同分处理后，应输出同构的决策及证据。语言名称与文件后缀不作为算法预置的成本、授权或拦截条件；用户明确指定的文件范围和工具要求仍按原义执行。

需要保存的记录见 [任务账本](requirements-ledger.md#新算法需要的记录)，模块职责和现有实现差异见 [系统架构](product-architecture.md)。接收和复核分析结果的方式、数据库表结构须在实施时确定；当前工具不接受这些尚未定义的参数。

该设计不能判定任意程序的语义等价性，也不能保证在多项式时间内求出全局精确最优解。经典算法的复杂度和近似保证不等于产品实际效果；误判、漏判、正确性与总成本仍需按专项验证的授权范围测量，方法见 [算法评估](product-evaluation.md)。

算法依据：增量推导参考 [Gupta 等人的增量视图维护与 DRed](https://doi.org/10.1145/170035.170066)；有限约束分解参考 [Freuder 的 k-tree 约束满足算法](https://dl.acm.org/doi/10.5555/1865499.1865500)；加权集合覆盖参考 [Chvátal 的贪心算法分析](https://doi.org/10.1287/moor.4.3.233)。这些文献支撑各自的算法部件及条件，不直接证明 TaskBelay 的语义输入正确或整体效果。
