# 任务接续

TaskBelay 根据账本和当前工作区生成摘要，让另一个 Agent 或新 session 接着完成任务。用户最后一次修改的代码，是接续的起点。

## 什么时候给摘要

| 场景 | 处理 |
| --- | --- |
| 新 session、切换 Agent、清空或压缩上下文 | 给当前任务摘要 |
| 恢复或分叉 session | 比较账本修订号、工作区状态、任务上下文和设置；有变化时补充摘要 |
| 用户直接修改代码但没有发消息 | 下次观察时给变化摘要，更新相关检查和下一步提示 |
| 恢复暂停任务或重新打开已完成任务 | 给该任务的摘要，附暂停或完成之后的工作区更新 |
| 切分支后找到对应任务 | 切换当前任务并给摘要 |

没有当前任务时，列出与当前上下文相关的最近任务，Agent 根据用户请求选择恢复或开始新任务。

接续任务时，检查是否还有需要 Agent 处理的事项：已有可核对的编辑却没有有效需求时，提示补记需求；最新交付请求已过期，又没有新的有效请求时，提示重新申请交付。这些事项显示在任务编号等基本信息之后，并计入每个 session 的摘要输入版本。同一 session 的下一轮，以及其他 Agent 接手时，都能收到提示。补齐需求、新交付请求生效或切换任务后，不再显示已经不适用的事项。这些提示不会使普通 Stop 强制要求 Agent 继续工作。

## 摘要内容与长度

摘要和事前提示合计不超过 2,000 token，按中文每字一个、英文每四个字符一个估算。任务编号等基本信息、工作模式、方案状态和查询完整账本的入口固定保留；其余内容通过缩短句子、限制条数和截断来控制长度。

| 顺序 | 内容 | 限额 |
| --- | --- | --- |
| 1 | 任务编号、标题、状态、工作模式、最后更新时间 | 120 token |
| 2 | 当前需求和变更，优先未完成和刚修改的需求 | 500 token，最多 8 条，只列编号、状态和简述 |
| 3 | 半自动方案版本、有效范围、待确认变更、文件路径 | 180 token |
| 4 | 最新工作区更新，以及 Agent 应先读的位置 | 250 token，最多 5 处 |
| 5 | 下一步及记录时间，注明之后是否有代码变化 | 120 token |
| 6 | 当前仍有效的用户决定和未解决问题 | 200 token，最多 5 条 |
| 7 | 改动文件和最近验证 | 150 token，各最多 5 条 |

接手任务准备运行验证时，可以先从摘要给出的 `task_get` 调用查看当时的命令、状态和已保存的输出。摘要选取本任务里最近一条符合条件的请求。除了账本已根据运行历史认定的验证，完整解析为单个前台测试、构建或检查命令的请求也可入选。例如，首次运行 `go test` 检查新加的临时用例，随后又清理了文件，接手者仍能从摘要打开测试输出。管道、组合命令和带有写入重定向的请求不能单凭命令类型入选。接手者可以从状态和输出核对是否实际执行、检查了哪些用例。命令前的重跑判断仍依据验证输入和运行历史。

如果同一命令后来失败、仍在运行、结果未知或被拦截，摘要显示那次请求。只有旧版记录可供参考时会注明来源。尚未选择任务时，登记新消息和生成摘要都跳过验证历史。选定任务后再读取该任务的记录。

最近一次验证已执行并返回成功或失败时，摘要会比较工作区快照。如果命令开始前、结束后和本次完整观察的快照都相同，接手者可以先看已有输出，判断它是否已经回答当前问题。如果当前快照不同，先核对哪些改动会影响这项检查。命令前后快照不同、缺少运行快照或本次只观察了目标文件时，摘要会说明能核对到哪里。快照只反映工作区内容；运行工具、环境和外部数据仍需结合当前问题判断。

摘要不展开命令参数和输出。在这一项的长度限额内，先保留验证记录入口和检查状态，再列改动文件。

拟写实现时，如果分支会覆盖刚算出的值，或下游会对同一批输入重新计算，事前提示引导 Agent 先看结果由谁使用。例如，预览和交付需要不同的说明时，可以在各自的分支里生成文案。两层按同一条件筛选用例时，可以把筛选结果传给下游。推迟计算要确认原调用没有必须保留的副作用，复用结果还要确认输入和相关状态仍然相同。

写测试前，事前提示引导 Agent 先看已有用例还缺哪项行为检查，再选择测试入口。如果调用负责这项行为的函数就能观察到所需结果，可以省去完整流程中与断言无关的准备。如果要检查多个环节怎样配合，就从能覆盖这些环节的实际入口运行。

如果记得相关任务曾写过临时用例，但文件已经清理，可以用 `task_get` 在那项任务的 `verifications` 中按用例名查命令或输出。选中实际运行的记录后，若有 `state.workspace_tree`，用 `git grep -n -F -e TestExport <workspace_tree> --` 在该快照中定位用例，再用 `git show <workspace_tree>:<path>` 阅读断言和夹具。按实际用例名替换 `TestExport`。结合当前需求与代码，判断哪些准备可以复用、哪些行为还需要检查。仓库外的临时用例不会进入这份快照。

交付时若只想检查本次提交的空白错误，事前提示建议先暂存要提交的改动，再运行一次 `git diff --cached --check`。组合命令中的文件清单、差异统计或分支状态仍可按需查看。部分暂存、补丁变化或检查规则变化时，两次检查各自回答什么问题，见[重复验证](over-testing.md#重复验证)。

重跑前先看已有输出能否回答当前问题。如果摘要指向另一条命令，或专项测试还没有被识别为验证，可以用 `task_get` 在 `verifications` 列表按 `command_contains` 查找命令里的用例名或路径。整组运行的命令有时只写包名或匹配表达式，这时可用 `output_contains` 查找输出里的用例名或报错片段。列表给出命令开头和整次运行的状态，并摘录首次匹配处的原文。末次匹配处的原文有区别时也一并展示。连续几行都打印同一场景的测量值时，首段还可带出下一行匹配值。按用例名查找时，末段有时能带出结束前打印的一行错误或实测值。核对它属于哪个用例，摘录已回答问题时可直接引用，需要其他输出或运行条件时再读正文。查不到时，仍可能是已保存的输出没有保留该片段。

需要写入前比较时，可以在当前工作区内用编辑工具编写临时测试。工作区外的文件和 shell 写入都不会进入这次比较，仍可按任务需要使用。编辑预览的条件见[过度测试判定](over-testing.md#编辑前提醒)。

事前提示最多 350 token，为固定入口和省略说明预留 130 token。待处理事项计入总预算，并优先于后面的可变内容保留。先将每项内容压缩到各自的限额内；若总长度仍超出预算，再从最后一项开始缩减。需求过多时，给出需求总数和省略条数；需要完整原话、验收标准和历史版本时，通过 `task_get` 列出记录，再分段读取正文。

摘要末尾固定说明：用 `task_get` 查看完整任务；在编辑工作区更新涉及的位置前，先读当前内容。

## Agent 记录什么

- 开始开发前保存需求，完成、修改和撤销时更新状态。
- 做出影响后续实现的选择时记录决定，写清做法和理由。
- 未完成就停下时记录下一步。
- 要交付时调用 `task_finish`；临时暂停、问问题和等待方案确认时保留任务。

消息、编辑、工作区更新、验证和检查由 TaskBelay 自动记录。没有记录下一步时，摘要会提供当前需求、代码变化和最近结果，供 Agent 判断如何继续。

## 算法结果的接续

算法的中间结果按 blob、tree 和输入版本保存在账本中，新 session 或另一个 Agent 可以直接复用：内容不变时，复用文件分析与仓库统计；需求与内容均不变时，复用需求相关区和静态信号；对应内容不变时，复用撤回试验与变异的确认结果。验证输入记录跨 session、跨 Agent 有效。摘要沿用现有长度预算，只列出未处理的拦截问题和排序靠前的建议；完整结果留在账本中，不全部放入上下文。逻辑记录见 [任务账本](requirements-ledger.md#算法的逻辑记录)，需要完整结果时，读取检查记录的正文。

用户在两次接续之间修改了代码时，复用未变化的词法结果，再根据当前输入计算变更簇和相关区；混合了用户修改的变更簇不再作为撤回候选。旧笔记中的“下一步跑全量测试”只是当时的计划，不改变根据验证输入作出的判断；一次检查尚未完成，也不代表用户已经授权补测。

同一问题不会因为位置或 session 摘要变化，就被当作新问题。校准标签根据实际处理和内容恢复情况记录，换 Agent 不重复计数。切换 Agent 本身也不增加需求、重跑理由或用户授权。

## 用户手动修改后的接续

Claude Code 已写出 `writeCSV`，用户把错误处理改好并提交。TaskBelay 在下次 hook 中发现文件变化，摘要写明这个函数有工作区更新。Codex 接手后先读当前函数，继续尚未完成的导出流程；旧笔记里若写着“重写错误处理”，摘要会注明笔记之后代码已更新。

工作区更新不自动改变需求的完成状态，也不自动成为新增功能的授权。Agent 根据代码和当前需求更新进度，需要确认行为时再与用户讨论。

## 插入另一项任务

Agent 判断新消息是在补充当前需求、询问进度，还是另一项独立工作。补充和讨论留在当前任务；独立工作用 `task_start` 开始，原任务暂停。用户回来继续时，按编号或标题恢复，不要求重新解释需求。

## 同时使用两个 session

同一工作区的 session 在十分钟内都有活动时，提示双方正在共享同一份代码和当前任务。两边可以协作完成同一任务；独立的并行开发可用 worktree 分开。

账本通过短事务写入。每次保存需求或方案时，都带上读取时的修订号。使用旧版本写入发生冲突时，返回最新内容，由 Agent 合并后重试。一个 session 申请交付后，另一个 session 的新编辑会使交付检查过期，任务继续进行。

用户在 IDE 或终端里修改、提交，不需要关闭任何 session。
