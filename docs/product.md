# TaskBelay 产品需求

TaskBelay 是一个在本机运行的命令行程序，接在 Claude Code 和 Codex 上，解决 Agent 写代码时的三个问题：做得比要求的多（过度设计），测得比需要的多（过度测试），以及换一个 Agent 或开一个新 session 之后接不上之前的工作。用户照常和 Agent 对话，使用习惯不用改变。TaskBelay 有两种工作模式：全自动模式下，用户给出需求后就不用再管，等着看结果；半自动模式下，Agent 先交出方案，用户确认后才开始开发。

本文讲 TaskBelay 做什么，以及怎样算做成功。怎样判断、怎样实现，见各份设计文档；文档的分工和术语见 [文档说明](README.md)。

## 要解决的问题

### Agent 容易做多

用户说“给 export 命令加一个导出 CSV 的选项”，Agent 交回来的改动里常常还多出这些东西：一个只有 CSV 一种实现的 `Exporter` 接口，一个用户没提过的 `--delimiter` 参数，一个所有调用处都传 `','` 的函数参数，还有几处顺手改掉的无关代码。每一项单独看都说得通，合在一起，改动量是实际需要的好几倍。用户要花时间读、判断，再让 Agent 删掉。

原因在于 Agent 判断“需不需要”时，参照的是“一个完善的系统应该有什么”，而不是“用户这次要了什么”。在提示词里写“保持简单”作用有限，因为 Agent 总能给每一项找到理由。

### Agent 容易测多

同样一个改动，Agent 常常写出十几条测试：表格里八行输入走的是同一段代码，getter 和构造函数也各有一条，还有几条测的是这次根本没改的代码。写完之后，每改一行就把全部测试、构建、lint 跑一遍，代码没变也再跑一遍“确认一下”。测试代码比功能代码还长，以后改功能时这些测试都要跟着改；反复验证又耗掉大量时间和 token。

### 换 Agent、换 session 之后接不上

一个任务做到一半，Claude Code 的额度用完了，用户换到 Codex；或者 session 太长被压缩，或者用户第二天开了新 session。新的 Agent 不知道用户要了什么、做到了哪一步、做过哪些决定。用户只能把任务重新讲一遍，或者让 Agent 从 git diff 里自己猜。

## 目标用户和使用场景

TaskBelay 面向在自己电脑上用 Claude Code 或 Codex 写代码的开发者，代码放在 git 仓库里。典型场景有三种：

- 让 Agent 加一个小功能、修一个 bug、做一次小范围重构，希望交回来的改动只包含要求的部分。
- 同时用 Claude Code 和 Codex，按额度或各自擅长的事来回切换。
- 一个任务跨好几个 session，中间会被压缩、清空，或者隔天才接着做。

## 功能

TaskBelay 检查 Agent 的改动、写的测试和运行的命令，判断它们多不多。它对 Agent 的影响只有三种：拦下、提示、给建议，改不改、怎么改由 Agent 决定。

### 两种工作模式

- **全自动**：用户给出需求后就不用管，Agent 直接开发，TaskBelay 在过程中检查，用户最后看结果。
- **半自动**：Agent 先分析需求，写出一份技术方案，列出要改的代码文件、要新增的对外入口和依赖，交给用户确认。用户确认之前，Agent 不改任何文件；确认之后才开始开发。开发中改到方案以外的文件会被退回，Agent 要先改方案、再请用户确认。

两种模式下，下面三项功能都照常工作。半自动模式的设计见 [半自动模式](semi-auto.md)。

### 防止过度设计

Agent 准备结束时，TaskBelay 检查这次任务的全部改动。用户没要的功能、眼下用不上的抽象、和任务无关的顺手修改，会被列成一份清单退回给 Agent，写明哪个文件的哪一处、为什么算多余、建议怎么改。Agent 接着修改；它认为需要保留的，会向用户说明理由并询问。一处改动留不留，以用户的话为准，用户同意的才算合理。

Agent 不处理就结束时，TaskBelay 不会一直拦着它，没解决的问题会显示给用户。任务完成时，用户会看到一份报告：每条需求对应了哪些改动；新增的命令行参数、环境变量这类对外入口，以及凭用户的话保留下来的地方，都单独标出来。

判断规则见 [过度设计判定](over-design.md)。

### 防止过度测试

Agent 准备结束时，TaskBelay 同样检查这次新写的测试：重复的、测不到这次改动的、只测了简单代码的用例，会被退回给 Agent；测试数量明显超出改动风险所需时，Agent 会收到提示。

Agent 运行测试、构建这类命令之前，TaskBelay 会拦下结果已经确定的重复运行，比如代码没变又跑一遍同样的测试；跑的范围超出改动影响、或者验证次数太多时，Agent 会收到提示。

判断规则见 [过度测试判定](over-testing.md)。

### 跨 Agent、跨 session 接续

同一个工作区里，Claude Code 和 Codex 共用同一本任务账本。新 session 开始、session 被压缩或清空之后，Agent 会收到当前任务的摘要：用户要了什么，哪些做完了，做过哪些决定，下一步做什么，改了哪些文件，检查和测试的最新结果。摘要的大部分内容由 TaskBelay 自动记录，不靠 Agent 在结束前写总结，所以 Agent 额度突然用完或被中断时也能接上。

设计见 [任务接续](handoff.md)。

## 一个完整的例子

**上午，防止多做。**

1. 用户在 Claude Code 里说：“给 export 命令加一个导出 CSV 的选项。”
2. Claude Code 把用户的要求记成一条需求：export 命令能输出 CSV。
3. Claude Code 改代码：加了 `--format` 参数，加了 `Exporter` 接口和唯一的实现 `csvExporter`，又加了一个 `--delimiter` 参数；写了 6 条测试，其中 4 条测的是同一段代码。中途有一次在代码没变的情况下又运行了 `go test`，被拦下。
4. Claude Code 准备结束，被退回，理由有三条：`Exporter` 只有一种实现；`--delimiter` 用户没提过；有 3 条测试和另一条测的是同一段代码，也发现不了额外的问题。
5. Claude Code 去掉接口，删掉 3 条测试，并就 `--delimiter` 问用户要不要保留。用户回复“分隔符不用，逗号就行”。Claude Code 删掉这个参数，再次结束时检查通过。用户看到最终报告：这条需求对应 `--format` 参数和两个函数，配了 2 条测试。

**同样的需求，换成半自动模式。** Claude Code 记下需求后先写方案：用标准库写 CSV，`export` 命令加一个 `--format` 参数，涉及 `cmd/export.go` 和 `internal/export/csv.go` 两个文件，没有新依赖。用户看完回复“可以，按这个做”，Claude Code 才开始改代码。开发中它想顺手改 `internal/log/log.go`，被退回，因为这个文件不在方案里。

**下午，换 Agent 接着做。**

6. 用户让 Claude Code 给 import 命令也加上 CSV 支持，Claude Code 开始新任务。做到一半，Claude Code 额度用完，停了下来，没来得及写任何总结。
7. 用户在同一个目录打开 Codex。Codex 的 session 一开始就收到摘要：任务“import 支持 CSV”进行中；需求还没完成；`internal/importer/csv.go` 新增了 40 行；最后一次 `go test ./internal/importer` 在 15:03 失败。用户只说了一句“继续”，Codex 就从失败的测试接着做。

## 支持范围

- **Agent**：Claude Code、Codex。
- **语言**：任何语言的开发任务都能用，检查得多深取决于语言。所有文件都能按整个文件检查改动和需求的对应、新增的依赖和验证命令；TaskBelay 内置了语法的语言，比如 Go、Python、JavaScript、TypeScript、Java、Rust、C、C++、C#、Ruby、PHP，还能按函数、类这样的声明检查多余的代码和抽象；Go、Python、JavaScript、TypeScript、Java、Rust 还能逐条运行测试用例，检查重复和多余的测试。语言支持不到而没做的检查，任务完成报告里会写明。各种语言支持到哪一级，见 [语言支持](languages.md)。
- **平台**：Windows、macOS、Linux，三个平台上都能接入 Claude Code 和 Codex。在 Windows 的 WSL 里使用 Agent 时，TaskBelay 按 Linux 安装和运行；两个 Agent 都在 WSL 里，或者都在 Windows 上，才共用同一本任务账本。
- **前提**：代码在 git 工作区里。检查测试代码时要运行测试，机器上要装有项目自己的测试工具，以及 [语言支持](languages.md) 列出的覆盖率工具。不在 git 工作区里时，TaskBelay 什么都不做。
- **接入**：安装之后，用一条命令分别接入 Claude Code 和 Codex，对这台电脑上所有的 git 工作区生效，见 [Agent 接入](product-agent-integration.md)。
- **数据**：只存在本机。

## 默认行为

- **工作模式**：默认是全自动。用户可以改成半自动，改动之后新开始的任务按半自动进行。
- **拦截强度**：默认拦截一次。检查发现必须处理的问题时，TaskBelay 阻止 Agent 结束一次，把问题清单交给它；Agent 处理之后再结束，会重新检查；Agent 不处理就结束，TaskBelay 不再阻止，问题显示给用户。用户可以把拦截强度改成只提示，这时 TaskBelay 不会阻止 Agent 结束，也不会拦下命令，所有问题都只作为提示交给 Agent。
- **需求确认**：需求由 Agent 根据用户的话来拆，用户不用逐条确认。用户没说过、Agent 自己推断出来的事可以记下，但不能作为保留改动或测试的理由。

## 成功标准

下面的标准都在 [算法评估](product-evaluation.md) 定义的任务集上衡量。除了“半自动”一项，其余各项对比的都是同一批任务在关闭和开启 TaskBelay 时的结果。

| 方面 | 标准 |
| --- | --- |
| 改动量 | Agent 新增的非测试代码行数和参考改动之比，中位数下降 30% 以上 |
| 测试量 | 新增测试用例数和参考改动之比，中位数下降 30% 以上 |
| 验证次数 | 每次运行中验证命令的次数，中位数下降 30% 以上 |
| 正确性 | 30 个任务里，开启后隐藏验收测试结果变差的任务，比变好的任务最多多 2 个 |
| 接续 | 中途换 Agent 后，隐藏验收测试的通过率和不中断时相差不超过 5 个百分点 |
| 误判 | 拦截的问题里，人工判断不该拦的不超过 10% |
| 半自动 | 半自动模式下，方案确认之前工作区里没有文件被改动；任务结束时，改动过的非测试文件都在已确认方案里 |
| 速度 | 用户发消息、Agent 运行命令前，TaskBelay 在 1 秒内处理完；Agent 准备结束时的检查，除去运行测试的部分，在 5 万行以内的项目上 20 秒内完成 |
