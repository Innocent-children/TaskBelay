# TaskBelay 产品需求

TaskBelay 是一个在本机运行的命令行程序，接在 Claude Code 和 Codex 上，帮助开发者减少 Agent 多做的功能、抽象和测试，减少重复验证，并在切换 Agent 或 session 后接着工作。

用户照常提需求、改代码、提交和切换分支。TaskBelay 记录任务，检查 Agent 的工作，把有依据的问题交给 Agent 处理。用户直接修改 Agent 写出的代码，也是开发过程的一部分：接下来的工作以当前代码为准。

文档的分工和术语见 [文档说明](README.md)。算法将项目内容转换为统一的表示，再结合仓库统计和可核对的运行结果进行分析。

## 保持产品简单

TaskBelay 帮助 Agent 减少过度设计、过度测试和不必要的防御性编程，自身也应做到够用、可靠、易于维护。这一原则贯穿产品的各个阶段：提高判断准确性，同时减少用户需要记录、解释、等待和维护的工作。

新增能力应解决明确的实际问题。能用现有机制和简单做法满足目标时，优先复用；确实需要新增功能、抽象或依赖时，应比较它省下的工作与增加的运行、使用和维护成本。任务账本、代码位置、运行记录和会话接续都用于支持核心判断，不以记录更多信息或提供更多功能为目标。

产品已经足以解决主要问题时，可以停止扩展。静态提示已经有效，动态检查就可以一直按需使用；复杂机制没有额外收益，就保持简单；某项功能增加的负担高于省下的工作，就精简它。必要功能、错误处理和用户修改保护仍须满足。通用任务编排、云端协作平台、大型仪表盘等不作为默认发展方向，只有出现具体需求时再判断是否值得增加。

长期方向、各阶段目标和完成条件以 [TaskBelay 终极形态与进化路线图](roadmap.md) 为准，实际开发进展统一写入其中的“已完成记录”。项目开发须遵循 `AGENTS.md` 中的范围和记录要求；除必要的 bug 修复外，按路线图推进。

## 要解决的问题

### Agent 容易做多

用户只要 CSV 导出，Agent 可能同时加上只有一种实现的接口、没人需要的分隔符选项和几处顺手重构。TaskBelay 把改动与本次需求对应起来，指出可以省掉的部分，让 Agent 交回够用、容易维护的实现。

### Agent 容易测多

Agent 可能为同一行为写很多相近用例，反复运行全量测试、构建和 lint。TaskBelay 分别检查测试代码和验证过程。保留测试的标准是它守住了什么行为；运行验证的标准是这次运行能提供什么新信息。

### 工作难以接续

额度用完、上下文压缩、隔天重开 session 或临时插入另一件事后，Agent 容易丢失需求、决定和进度。TaskBelay 保存任务账本，按当前工作区生成摘要。

## 正常的开发过程

下面这些操作都按正常开发处理，用户不需要为 TaskBelay 提前登记：

| 用户在做什么 | TaskBelay 怎样处理 |
| --- | --- |
| 一个需求分多次提交，部分文件暂存、部分不暂存 | 始终相对任务起点计算累计 diff，提交不结束任务，也不清空记录 |
| 自己改了 Agent 写得不好的代码，没有告诉 Agent | 下次观察工作区时记录更新，刷新相关检查；Agent 从当前内容继续，保留这部分修改 |
| 删除、改名、移动 Agent 写出的文件或函数 | 更新实现位置，旧位置保留在任务记录里；无法确定新旧位置的对应关系时，让 Agent 补充当前位置 |
| 追加、修改或撤销需求 | 更新同一任务的需求，保留之前的版本和变更依据 |
| 临时处理另一件事，再回来继续 | 暂停原任务，之后恢复原来的需求、快照和进度 |
| 切分支、stash、pull、rebase 或 amend | 重新核对工作区与任务的关系；新出现的内容先作为工作区更新处理 |
| 明确要求再跑一次测试，或暂时保留某处实现 | 按这次要求执行并记录适用范围，后续接手的 Agent 能看到这项决定 |

任务范围、工作区更新和需求变更的规则见 [任务和需求](requirements.md)。

## 功能

### 防止过度设计

TaskBelay 把累计改动分成必须一起保留或撤回的变更簇，用局部图聚类找出每条需求的相关区，再检查与需求无关的改动、原话中找不到对应要求的对外新增项、可能缺少实际用途的间接层、重复实现和没人使用的代码。每处反馈写明已知事实、判断成立的条件和具体动作：撤回哪个变更簇、满足哪些条件后可以内联、复用哪个已有单元。不能只根据代码行数、接口数或实现个数下结论。

间接层的静态分析根据成员名共现、实参文本和转发形状找出候选，不证明抽象没有隔离用途、参数运行值固定或直接调用保持原行为。反馈展示实际识别结果、与需求相关区的关系以及尚需核对的条件，再分别说明如何替换抽象、删除固定参数或迁移转发调用。相关区中的词汇关联不证明实现有必要，已有旧名也不证明存在公开兼容承诺。无法核对为全部来自 Agent 编辑的对象，只报告现状并保留当前内容。

动态检查开启时，TaskBelay 在副本中撤回候选改动，运行验收依据中规定的用例和命令，再用分组检验确认哪些改动可以撤回，并给出确认过的撤回补丁。交付时，以下两类问题可以拦截一次：

- 对外新增项已被可靠识别，全部来自 Agent 编辑，原话中找不到对应要求，也没有登记为任何需求的实现位置。
- 改动已经确认可以撤回，与需求无关，也没有登记为需求的实现位置。

Agent 可以撤回这些内容，也可以将它们登记为需求的实现位置并引用原话。其余问题只作为建议，按优先级展示。具体规则见 [过度设计判定](over-design.md)。

TaskBelay 根据本项目对反馈的实际处理结果校准各项信号的权重，用于给建议排序。检查是否完成、结论适用于哪些内容、得出了什么结论，以及采取了什么动作，分别记录；信息不足时将结论记为未知。共用算法和问题标识见 [算法核心](algorithm.md)。

Agent 可以就少量可疑实现说明为什么要保留、可以怎样简化，或者还缺什么信息。工具把说明关联到需求和本次改动，分别展示可以核对的出处及 Agent 的判断。设计要说明隔离的实际依赖、已有兼容承诺或更直接的实现。防御要说明失败的触发条件、负责处理的层次和恢复操作对结果的影响。必要的错误传递、资源处理、并发、限流和幂等行为应保留。具体规则见 [用途核对](algorithm.md#用途核对)和[防御处理的核对](over-design.md#防御处理的核对)。

编辑请求能够完整核对时，TaskBelay 在写入前提示本次拟改动中“调用赋值、紧邻条件直接判断返回值、分支内再调用”的结构，帮助 Agent 提前核对恢复操作的用途。例如，条件只用刚算出的 `key` 读取 `seen[key]` 时，跳过这条提醒。这些结构不能确认失败条件或证明恢复多余，提醒不拒绝普通编辑、不要求逐项说明，也不启动动态检查。具体范围见[防御处理的核对](over-design.md#防御处理的核对)。

编辑新增或改写了声明首行，且拟写入的声明符合抽象形状时，预览给出行号和声明片段，供 Agent 核对已有类型能否表达所需状态、隔离依赖并满足调用约定。仅给既有类型增删字段、声明首行未变时，预览跳过这条提醒。抽象形状只能提示 Agent 核对用途，预览不统计实现数量，普通编辑照常进行。具体范围见[编辑前核对抽象用途](over-design.md#编辑前核对抽象用途)。

本次拟改动中的声明符合转发包装形状时，写入前也会提示被调名字，以及需要核对的行为、独立职责、入口和兼容约定。结构相似不能证明直接调用等价，必要包装继续保留；未改动的既有包装不重复提示。具体范围见[编辑前核对转发包装](over-design.md#编辑前核对转发包装)。

写入前提示可以复用的已有实现时，先核对索引参照仍与当前内容一致；同批编辑中的参照还须在拟写入内容中保留原声明。过期或被同批编辑改变的参照不用于建议，其他有效候选继续核对；相似不证明行为等价，普通编辑继续放行。具体边界见[重复实现与没人使用的代码](over-design.md#5-重复实现与没人使用的代码)。

可核对的编辑请求准备增加独立文件时，写入前提示核对文件的使用者、当前需求、已有文件能否承接，以及单独维护的成本。未识别到代码引用不证明文件没有独立用途，必要的文档、脚本、示例和配置仍应保留；已有登记沿用用途和引用，普通编辑继续放行。具体范围见[编辑前核对新增文件](over-design.md#编辑前核对新增文件)。

可核对的编辑请求准备增加参数、环境变量、路由或注册式调用时，写入前提示核对入口的使用者、当前需求、已有入口能否满足，以及使用和维护成本。代码形状不能确认它确为对外入口或有必要；已有登记沿用用途和引用，原话或有效方案直接对应的项仍略过，普通编辑继续放行。具体范围见[编辑前核对新增入口](over-design.md#编辑前核对新增入口)。

可核对的编辑请求准备增加配置键时，写入前提示核对实际配置用途、使用者、当前需求、何时需要切换取值、固定行为会失去什么功能，以及使用和维护成本。内部常量也可能符合键值形状，不能据此确认它供使用者切换或有必要；依据不足时保留必要配置，不因此补测试。已有登记沿用用途和引用，普通编辑继续放行。具体范围见[编辑前核对新增配置](over-design.md#编辑前核对新增配置)。

### 防止过度测试

如果同一文件里的新用例只是给另一条用例换了名字，编辑前会指出两条用例，供 Agent 核对名称、夹具和重复执行是否承担不同职责。确认检查相同后，可以一起省去副本和它的单独运行。对于已经识别出独立用例的新测试文件，TaskBelay 不再仅因其他代码没有引用它，就要求解释整份文件的用途。

TaskBelay 用被测代码中参与比较的常量划分等价类和边界，找出落在同一等价类的重复用例。动态检查开启时，再逐个运行抽样的变异，记录每条用例能够发现哪些变异，并用贪心集合覆盖算法选择保留的用例，使它们仍能发现同一组变异。其余用例作为删除或合并候选。确有变异没被任何用例发现时，才提示补测试。

可核对的编辑请求准备新增相近测试时，TaskBelay 在写入前展示比较对象、被测单元、等价类及断言异同。两个用例落在同一区间，但只有一个检查紧邻分界的值，或它们在不同输入位置检查该值时，分别保留这两处检查。相同断言仍需核对副作用；断言不同或无法完整读取时，提示保留检查。提醒以目标文件当前内容为基线，只针对本次准备新增的用例及其中的表格行，不要求逐项解释或批准。具体范围及略过条件见 [过度测试判定](over-testing.md#编辑前提醒)。

新增用例中，未识别到断言词时，写入前提示核对当前需求、实际行为及删去会失去的检查。词汇依据不能证明它没有结果检查或确实多余；参数只含测试偏向词也不足以单独触发用途提醒，因为回调、类型和夹具操作同样可能匹配。必要的调用次数、顺序及其他行为检查继续保留，不因此追加断言或验证。已有和明确保留的用例不重新提醒，具体规则见 [编辑前提醒](over-testing.md#编辑前提醒)。

本批新增用例或表格行超过按等价类与边界点计算的建议数量时，写入前展示超出部分的位置、被测单元和等价类，提示核对是否增加了不同的行为检查。建议数量不是上限，也不证明用例多余；必要检查继续保留，不因此追加验证或拒绝编辑。具体计数和保留规则见 [编辑前提醒](over-testing.md#编辑前提醒)。

运行命令前，TaskBelay 按验证输入判断这次运行能否提供新信息：验证输入与上次通过时完全相同，就拦截一次并返回上次的输出；用户要求重跑、上次失败或结果未知、命令会写入时照常运行。如果只是根据运行记录推断本次验证可能没有新信息，例如更大范围的验证已经通过，则只给出提示并附上次输出。规则见 [过度测试判定](over-testing.md)。

首次请求较小路径范围的命令时，如果已经读取的近期记录中有相同输入下通过的较大范围验证，也可提前展示该结果。此时本次命令仍照常运行，不因范围提示被自动归为验证；没有合适记录时不额外查询全历史。

动态测试检查由项目设置开启，也可由 Agent 主动请求。默认的交付检查先做静态分析，不额外启动项目测试。

### 跨 Agent、跨 session 接续

同一工作区的两个 Agent 共用任务账本。摘要包含当前需求、方案、进度、决定、工作区更新和最新检查结果。用户中途手改代码时，摘要提醒 Agent 先读更新后的内容，不要求它为了执行旧的下一步而恢复旧代码。见 [任务接续](handoff.md)。

### 两种工作模式

- **全自动**：用户给出需求后，Agent 直接开发，TaskBelay 在过程中检查。
- **半自动**：Agent 先提交方案，用户确认后开发。方案约定行为、涉及的范围、新入口和新依赖；范围内的实现调整由 Agent 完成，扩大约定范围时再确认。

用户可以在任务中途调整工作模式，已经完成的工作保留。半自动模式只约束 Agent 接下来的开发，用户随时可以自己改文件。见 [半自动模式](semi-auto.md)。

### 安装与日常管理

用户通过一条安装命令把程序装到自己的用户目录，无需管理员权限。安装后运行 `taskbelay`，在终端菜单中完成 Agent 接入、移除接入、常用设置、状态查看、检查、程序更新和卸载。上下方向键移动，右方向键或回车进入，左方向键返回，空格勾选 Agent；卸载和开启动态检查需要在菜单中确认。

已有子命令继续用于脚本。非交互环境无参数运行时显示帮助，不等待键盘输入。安装、更新和卸载保留任务账本及用户原有的配置；自更新和自卸载只处理带有安装脚本标记的程序。具体入口和发布包要求见 [Agent 接入](product-agent-integration.md)。

### 调试与过程复盘

用户可开启 debug 模式，详细记录 TaskBelay 接收到的任务事件、MCP 调用、处理环节、检查依据、返回结果、错误和耗时。记录保存在用户目录 `.taskbelay/debug/`，按日期分组，文件以任务唯一标识命名。任务结束后记录继续保留，用户需要时再让 Agent 分析这些记录，查找接入、判断、接续和性能上的不足。开关默认关闭，不自动分析或上传记录。记录格式、范围和查看方式见 [系统架构](product-architecture.md#调试记录)。

## 一个完整的例子

1. 用户在 Claude Code 里说：“给 export 命令加一个导出 CSV 的选项。”
2. Claude Code 记录需求，开发 CSV 导出，用户中途提交了一次。
3. 用户觉得错误处理写得不好，自己修改了函数，没有发消息。Claude Code 下次编辑时，TaskBelay 告诉它该文件有更新；它先读当前函数，再继续开发。
4. Claude Code 申请交付。TaskBelay 指出 `--delimiter` 在原话中找不到对应要求，也没有登记到任何需求；对接口则展示按成员名共现识别到的一个候选实现，提示核对类型关系和隔离用途。Claude Code 确认该接口没有必要保留，直接使用实现类型。项目开启了动态检查时，探针确认 `--delimiter` 是新增参数，TaskBelay 拦截一次，并附上撤回后验收用例仍然通过的补丁。Claude Code 撤回额外参数，保留用户修改的错误处理。
5. 用户又提交一次，任务完成报告仍然覆盖这次需求的全部改动。
6. 下一项任务做到一半，用户临时让 Agent 修一个小问题。原任务暂停，小问题完成后恢复原任务；如果换成 Codex，Codex 会拿到同一本账本和当前代码的摘要。

## 支持范围

- **Agent**：Claude Code、Codex，通过各自的 hook 和 MCP 接入。
- **语言**：算法对任何开发语言使用同一套词法、版面和统计方法，不按语言分级；判断所需的语言知识从仓库自身统计得到。文本结构信息少时降低置信度并保留未知，不能据此证明代码正确。信息不足时的处理见 [输入与执行协议](languages.md)。
- **平台**：Windows、macOS、Linux。WSL 按 Linux 安装和运行，同一环境里的 Agent 共用账本。
- **工作区**：git 仓库及其 worktree，各工作区分别管理任务。不在 git 工作区时直接结束 hook。
- **数据**：保存在本机。安装、配置和存储位置见 [Agent 接入](product-agent-integration.md) 和 [系统架构](product-architecture.md)。

## 默认行为

- 默认全自动，拦截强度为拦截一次；用户可改为只提示。
- TaskBelay 按具体问题记录拦截次数。修复其他文件、补充笔记或更新需求状态，不会让同一问题重新被拦截；同一问题每个 session 最多拦一次，每轮合计最多三次。
- 普通停顿、分析和等待用户回复时，检查结果作为提示。Agent 申请交付后，Stop 才执行交付拦截。
- TaskBelay 自动记录工作区更新。无法核对来源的内容仍按现状分析，只向 Agent 提供提示，不要求用户补充声明。
- 设置按用户、项目、当前任务依次覆盖。用户在当前对话里的明确要求即时适用于当前任务。
- TaskBelay 自己出错时，Agent 继续工作；本次检查的完成情况显示在报告里。

## 成功标准

效果按 [算法评估](product-evaluation.md) 的方法，在另行授权的专项验证中衡量。以下为目标与采用条件，不是已测得的效果；不能用代码或测试数量下降替代正确性。

| 方面 | 标准 |
| --- | --- |
| 精简效果 | 减少确认多余的改动和不提供新信息的验证，报告成本变化及不确定性；不强求每项数量下降 |
| 正确性 | 比较行为验收与有效回归的结果，逐项调查新增失败；精简不能以破坏应有行为为代价 |
| 接续 | 切换 Agent 后继续完成同一需求，保留仍有效的结果、尚不能确定的部分与用户决定 |
| 用户修改 | 保留用户最后一次修改后的程序行为，用户无需补充原话、登记文件或暂停手动开发 |
| 开发习惯 | 在多次提交、暂存、分支操作、暂停恢复和需求变更等场景中都能完成任务，账本记录不中断 |
| 误判与漏判 | 拦截中经核对为错误的比例不超过一成；建议的采纳与恢复、漏判分别统计，并报告样本数与不确定性；不能靠全部放行获得低误判率 |
| 普适性 | 扩展名和工具名一致改名后结果不变；语言之间的差异只体现为统计结果和结构置信度 |
| 半自动 | 用户确认前拦下 Agent 的编辑；确认后按有效方案和后续授权工作，用户修改照常保留 |
| 速度与总成本 | 静态部分的耗时随改动规模而不是仓库规模增长；动态部分的运行次数受预算限制，撤回试验在需要保留的候选少时接近对数级，变异按抽样数运行；计入 TaskBelay 自己的运行，报告冷启动、增量、缓存命中及退化场景，不宣称未测得的时延 |

## 会话动作记录

TaskBelay 将以下动作追加为简短的中文 Markdown 记录：

- 保存需求、决定、下一步和方案。
- 开始或恢复任务、申请交付。
- 输出接续信息和检查反馈、拒绝验证或过期编辑。
- 取得检查或验证结果。

普通读取和未作干预的工具调用不逐项记录。会话动作记录不依赖 debug。

用户直接打开用户数据目录的 `session-records/` 查看，无需发起查询。记录只写当时能确认的情况，分别说明数据是否保存成功、提示是否输出成功、检查是否复用了已有结果，以及是否仍在运行或结果未知；申请交付不代表任务完成。程序不提供查询或汇总入口，也不扫描或补写历史记录。路径与保留方式见 [系统架构](product-architecture.md#会话动作记录)。
