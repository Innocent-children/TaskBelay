# 算法评估

## 当前仓库的测试维护范围

本仓库长期只保留打包、安装及必要安装维护的基础测试，包括发布元数据、版本比较、校验与替换、接入配置和用户数据保留。模块修改需要验证时，依据本次确认的需求和当前实现重新编写必要的临时测试；通过后删除测试代码、专用辅助代码、样例和临时产物，在当次交付回复中说明验证范围、环境、命令与结论，不保留项目内验证归档。意图明确、可直接阅读推演的改动不为走流程新增测试。

旧测试不能直接作为当前需求，更不能为了迎合已经过期的断言修改正确实现。其他模块测试、规则资料包、端到端数据集和评估脚本不作为常驻资产维护，也不假定本机存在历史结果。产品自身的测试分析和验证记录功能保持原样，长期维护政策见根目录 `AGENTS.md`。

下文保留可参考的评估方法与结果解释口径，供有明确需求的专项验证选择，不代表已有测试入口或待执行任务，也不是自动补回测试或恢复多轮评估的要求。历史缺口不据此宣称已通过。

## 历史评估设计

TaskBelay 的效果要同时体现在交付质量和日常使用上：Agent 少做多余工作，用户仍能按原来的方式修改、提交、插入任务和接着开发。

评估分三层：规则例子检验判定，开发场景检验流程，端到端对比检验实际收益。真实使用记录用于补充前两层。

## 判定例子集

需要规则验证时，在当次临时目录构造起点项目、改动及账本事实，按当前需求明确预期结论、问题身份、处理记录和检查完成情况；验证后删除这些材料。

OD、OT、SA 编号与核心文档的例子对应。Go、Python、TypeScript、Java、Rust 各覆盖支持的规则；C#、Ruby、PHP 覆盖通用代码分析；文档、配置、依赖清单覆盖文件级分析。没有对应能力时，期望列明实际完成的检查。

每条规则至少包括应该提示、应该放行及例外；有拦截档位的规则另外检查完整前提和单次拦截。D5 包括隐式零值和后续更新，T2 包括不同断言、无有效变异、编译失败和基线失败，V1 包括不同目录、环境变化、未知结果和用户要求重跑。

根据本次影响选择实际可用的平台，构造任务、应用变化、运行检查并与当前需求对照。命令解析涉及 POSIX 或 PowerShell 时比较解析后参数，保留引号内字面值。报告实际运行的平台和 Agent；交叉编译和构造事件不代替目标平台原生运行或真实 Agent 接入。

规则文档、参数、代码和期望在同一次变更中更新。每处期望变化说明对应的行为改变。

## 正常开发场景

这些场景通过有序事件、文件变化和账本快照运行，重点检查代码最后留下了什么、账本如何接续，以及用户被额外打断了几次。

| 编号 | 操作过程 | 验收 |
| --- | --- | --- |
| WF-01 | 一个需求分三次提交，中间部分暂存、部分未暂存 | 起点不变，累计 diff 完整，真正的暂存区不被修改 |
| WF-02 | 用户直接改善 Agent 的函数，不发送消息，Agent 随后继续改相邻代码 | 工作区更新被观察到，保留用户改进，Agent 使用当前内容 |
| WF-03 | 用户和 Agent 修改同一片段 | 过期编辑退回重读，不整段恢复旧实现，不要求用户补原话 |
| WF-04 | 用户手动移动、改名或删除位置 | 需求保留，位置更新或待补，纯删除需求能表示 |
| WF-05 | A 任务中途插入 B，做完 B 后换 Agent 恢复 A | A 的起点与决定保留，B 的内容不归责给恢复后的 Agent |
| WF-06 | 切分支、stash、pull、rebase、amend 后继续 | 核对上下文和工作区更新，不把这些操作当作任务结束 |
| WF-07 | 追加、修改和撤销需求 | 新修订生效，旧授权不继续支撑已撤销行为 |
| WF-08 | 用户回复“可以”，或在请求里明确说直接按方案改 | 正确绑定方案版本与完整消息，不要求固定长度的确认语 |
| WF-09 | 已确认方案内拆文件，增补方案等待时继续原范围 | 正常开发，只有新增未授权部分等待 |
| WF-10 | 用户明确要求重跑；上次验证失败、未知或环境变化 | 命令照常运行，记录原因和实际结果 |
| WF-11 | 用户在 120 秒动态检查期间编辑代码 | 旧结果不用于当前交付，不锁工作区，不自动反复重跑 |
| WF-12 | task_finish 后触发 Stop，分别直接结束和修改后再申请交付 | 输入未变时完成原请求；修改后使用新请求，不重复建立任务 |
| WF-13 | 方案、工具能力、分析设置变化，代码和需求没变 | 相应缓存失效，修复工具后可补检查 |
| WF-14 | 两个 session 基于同一修订更新需求 | 返回版本冲突，合并后保留双方有效信息 |
| WF-15 | 改了其他文件、提交或补笔记，同一问题仍存在 | 同一问题不重新计作首次拦截 |
| WF-16 | 需求超过摘要预算，恢复时用户又在外部改了代码 | 摘要在预算内，给出省略条数和完整入口，优先提示当前更新 |
| WF-17 | 大小写敏感卷、路径空格、中文、符号链接和不同 worktree | 识别实际工作区，路径与 hook 参数正确 |
| WF-18 | hook 超时、数据库暂时忙、进程中断后重复到达 | 原工具操作继续，记录幂等，没有半成品交付 |

WF-02、WF-03 的用户改动包括错误处理、命名、边界条件和测试断言。验收检查这些行为在后续结果中仍然存在，不能只比较一段文字是否原样保留。

每个场景统计额外审批次数、重复提示次数、无效阻断次数、是否要求用户改变 Git 或编辑习惯。正常操作不新增审批；有新产品行为或超出有效方案的 Agent 工作，按正常确认流程计数。

## 端到端任务集

从十个开源项目选择三十个已合并 PR。Go、Python、TypeScript、Java、Rust 各两个项目、六个任务，覆盖 bug 修复、小功能和小范围重构。非测试改动为二十至三百行。

每个任务保存用户请求、起点、隐藏验收测试和参考改动。请求只描述行为；Agent 结束后才放入隐藏测试。

两个 Agent、开启与关闭 TaskBelay，各运行三次，共三百六十次。小范围规则调整先跑对应例子、开发场景和十个任务的对比，共一百二十次；采用前扩展到完整任务集。没有改变 Agent、模型和设置的已有对照可复用，并记录来源。

脚本使用 Claude Code 的 `claude -p --output-format stream-json` 和 Codex 的 `codex exec --json`，在同一 session 中按场景脚本接续。每轮固定并记录 Agent 版本、模型与设置，需要用户决定时保留提问原因和次数。

每次开启运行核对 SessionStart、Stop 和实际工具活动，确认 hook 参与。缺失时将该次标为接入失败，修复后重跑，并保留失败率和处理耗时。

## 指标和采用标准

| 指标 | 统计 |
| --- | --- |
| 改动量比 | 新增非测试代码行数除以参考改动新增行数 |
| 测试量比 | 新增用例数除以参考用例数，参考为零按一算 |
| Agent 验证 | 实际执行的验证次数，不把被拦的命令算作执行 |
| TaskBelay 运行成本 | 准备、编译、基线、变异的次数、进程数、耗时和资源 |
| 总使用成本 | Agent 与 TaskBelay 合计耗时、模型 token、提示量和用户确认次数 |
| 正确性 | 隐藏验收测试和已有测试分别统计通过率、失败任务及失败行为 |
| 使用连续性 | 开发场景通过率、用户修改保留情况、任务恢复结果 |

数量指标取中位数，完整记录每个任务的结果。动态检查关闭和开启分别报告，避免把额外测试成本藏在 Agent 验证次数之外。

正确性同时看总通过率和逐任务结果。三次运行中从 3/3 变成 2/3 也记录退步，不能因差值不足两次而忽略。对结果变化的任务，两种模式各增加三次运行，核对失败行为；新出现的稳定失败先修复。隐藏测试与已有测试的通过率均不下降，开发场景全部通过，才继续比较精简收益。

评估产品时，三项数量指标目标见 [产品需求](product.md)。评估一次修改时，三项没有一项变差超过 5%，至少一项变好 5%，且总使用成本没有明显增加，才采用。两个 Agent 分别检查，不能用一边的收益抵消另一边的失败。

## 半自动与接续

半自动另跑三十个任务、两个 Agent，各一次。首次方案按脚本确认；后续区分范围内调整和真正的范围变更，检查审批是否必要。确认前的用户手改与 Agent 编辑分别核对，不以“整个工作区没有变化”代替验收。

接续从十个任务中选固定中断点，双向切换 Claude Code 和 Codex，各运行三次。包括额度中断、压缩、暂停恢复，以及中断后用户没有发消息就改过代码。比较接续与不中断的验收通过率和用户改动保留情况。

## 平台与性能

规则和开发场景在 Windows、macOS、Linux 全部运行。端到端主对比在 macOS；另外两平台各选十个任务、两个 Agent，各一次，核对接入、命令记录和任务接续。Windows 同时覆盖 Git Bash、PowerShell；WSL 按 Linux 环境单独运行。

性能记录冷启动、热缓存、包含新文件、较大仓库和数据库竞争的各阶段耗时，报告中位数及 P95。预算到期时核对进程已终止、工作区仍可继续开发、结果版本与完成情况正确。

## 真实使用与参数调整

`taskbelay hits --since 14d` 导出具体问题、证据、拦截及后续处理。每两周按规则抽取三十条拦截人工判断，同时抽查精简建议；分别统计误拦和无效建议。用户修改的内容被建议撤回、反复审批和重复提示，直接补入开发场景。

参数一次调整一项，先运行对应例子和场景，再对比端到端收益。采纳时同步更新文档、参数、期望与评估数字，说明改善了哪些行为及付出了多少运行成本。
