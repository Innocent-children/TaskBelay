# 任务账本

账本保存任务目标、开发过程和交付结果。两个 Agent 的 hook 和 MCP 进程共用同一个 SQLite 文件。术语和目标行为由 [任务和需求](requirements.md)、[算法核心](algorithm.md)、两份判定文档、[半自动模式](semi-auto.md) 和 [任务接续](handoff.md) 定义。

账本使用 schema 14。计算在事务外进行，业务记录与检查结果通过短事务保存，读写前均核对账本版本是否受当前进程支持。

## 谁写什么

| 记录 | 写入方 | 时机 |
| --- | --- | --- |
| 用户消息、session 和 hook 活动 | TaskBelay | 事件到达 |
| 需求、实现位置、决定和下一步 | Agent | 分析、开发和接续 |
| 方案正文、范围及确认来源 | Agent 提交，TaskBelay 核对并保存 | 提交和确认方案 |
| 观察点、Agent 编辑、工作区更新 | TaskBelay | 观察文件及核对编辑前后 |
| 验证与检查 | TaskBelay | 命令运行、检查和交付 |
| 任务切换及交付状态 | TaskBelay | Agent 请求开始、恢复和交付 |

Agent 通过 MCP 写入自己负责的记录；TaskBelay 保留用户消息原文及工具观察到的原始内容。更新需求、方案和决定时，追加新的修订版本，原记录仍可供接续任务和查询报告时使用。

## 记录和字段

### 工作区与设置

工作区记录保存仓库与 worktree 标识、当前路径、分支、HEAD、当前任务和最新观察点。路径变化后更新位置，工作区标识不变。重启或重新挂载使同一目录的设备号变化时，沿用这个目录原有的标识，任务、观察和索引不分开。任务可以按分支恢复，但分支名只用于了解当前工作环境，不作为判断代码来源的依据。

设置记录保存用户默认值、项目覆盖值和任务覆盖值，包括 `workflow`、`enforcement`、动态检查开关和副本并发条件。同一个本地仓库的 worktree 共用项目设置，各任务可以分别覆盖。解析后的有效设置带修订号。

### 设置项

设置分用户、项目、任务三个范围保存，任务设置优先于项目设置，项目设置优先于用户设置。副本只重新运行本任务中已经成功运行且输入可核对的项目命令。

| 设置项 | 值和默认值 |
| --- | --- |
| `workflow` | `auto` 或 `semi`，默认 auto |
| `enforcement` | `block` 或 `hint`，默认 block |
| `analysis.tests` | `on` 或 `off`，默认 off |
| `analysis.parallel` | 一至四，默认一；大于一表示项目命令可以独立并行运行 |
| `debug` | `on` 或 `off`，默认 off；详细记录当前任务的使用过程 |

命令按对应平台的 shell 解析，动态检查开启后才重新运行这些可信命令。CLI 用 `config set <设置项> <值>` 保存用户默认值，加 `--project` 或 `--task` 则分别保存项目或任务设置。当前会话中的明确要求由 Agent 记入任务决定，不要求用户另行编辑设置。

`debug` 只控制诊断记录，不改变检查输入、授权或拦截规则。记录独立保存为任务 JSONL 文件，具体内容和保留方式见 [系统架构](product-architecture.md#调试记录)。

### 任务

| 字段 | 含义 |
| --- | --- |
| 编号、标题、工作区 | 全局唯一编号，形如 t17 |
| 状态 | 进行中、待交付、已暂停、已完成、已中止 |
| 起点消息、起点快照 | 原始任务起点，提交和暂停不改变它 |
| 上下文和恢复观察点 | 分支、HEAD、上次恢复时工作区状态 |
| 工作模式、设置修订 | 当前任务的有效设置 |
| 需求修订、方案修订、记录修订 | 检查和接续使用的版本 |
| 交付请求 | 请求者、轮次、请求时状态和本轮任务编号 |
| 创建、更新、暂停及结束时间 | 生命周期时间 |

`task_start` 切换任务的操作在同一个事务里完成：暂停当前任务，选中或建立目标任务，保存恢复观察点。

### 用户消息和需求

消息保存编号、原文、时间、Agent、session、轮次、到达时的上下文和工作区状态。引用保存消息编号与原文范围；已确认方案和项目约定也保存来源编号。

需求记录保存 R 编号、内容、验收标准、状态、原话来源、类型、实现位置、用途说明、修订号和修改者。状态为未开始、进行中、已完成、已撤销。每次更新都保留之前的版本；用户通过新要求撤回的决定标为失效。

实现位置记录保存种类、当前位置、编辑前位置、变更类型、引用和用途。文件或声明移动、改名时更新当前位置；对应内容被删除后，仍能从起点快照或编辑记录中查看原位置。

### 方案

每版方案保存正文文件路径、完整范围清单、新入口和依赖、变更摘要、提交者、提交时间及观察点。方案确认记录保存确认的版本、完整用户消息、引用范围、授权时间和授权方式。

有效方案包括已确认的范围与仍然有效的后续授权；待确认的增补内容单独记录。新版本保存完整的授权范围，旧版的确认历史继续保留。每次提交、确认、撤回或调整范围，都增加方案修订号。

### 观察与编辑

| 记录 | 字段 |
| --- | --- |
| 观察点 | 时间、触发事件、上下文、完整 tree 或目标文件的内容标识 |
| Agent 编辑 | 工具调用编号、请求路径、编辑前内容、请求中的改动、编辑后内容、核对结果 |
| 工作区更新 | 前后观察点、文件和片段、首次观察时间、与需求位置的联系 |

内容使用快照或 blob 标识引用。只有请求中的改动能与实际前后内容对应时，才记为可核对的 Agent 编辑。非只读命令开始前先保存观察，把已有变化记为工作区更新。命令前后观察完整、HEAD 和分支一致时，期间发现的差异带上该次工具调用编号，可用于给出精简建议。命令运行期间的并发保存无法区分。

观察记录、编辑记录和需求修订共同组成检查输入。同一声明中的 Agent 编辑与工作区更新无法分开时，保留当前内容，对整段代码只给出精简提示，不据此拦截。

### 笔记和用户决定

笔记分为决定和下一步两类，保存内容、时间、作者，以及记录时的工作区状态。决定还可以指定作用对象、用户要求的来源和适用范围。

核对某处实现时，使用 `kind=decision` 和 `target={kind:"requirement", id:"R1"}`，省略授权作用。可选的 `review` 含类别 `kind`（`design`、`test`、`defense`）、Agent 的判断 `assessment`（`keep`、`simplify`、`unknown`）、被核对的片段 `subject` 和依据片段数组 `evidence`。每个片段用仓库相对文件名 `path` 和原文 `quote` 指定，原文出现多次时加起始行号 `line`（从 1 开始）。`text` 说明用途、前提和具体影响。原话仍使用笔记已有的 `source_id` 与 `quote`。笔记保存后，检查在固定快照上核对内容，结果作为问题写入现有报告。

若已有检查指出了准确位置，可在 `target.at` 填写同一文件的声明或行号。检查会核对它是否包含所引片段，并把结果关联到该位置的提示。在同一需求和类别下沿用该位置，可以更正代码变化后的用途说明。省略位置时，按所引片段区分对象。

例如，若需求 R1 的来源 m12 明确规定发送失败后应返回原始错误，Agent 可这样说明新增重试的影响：

```json
{
  "kind": "decision",
  "target": {"kind": "requirement", "id": "R1", "at": "send.go:Deliver"},
  "text": "再次发送可能把第一次失败改为成功。若调用方依赖原始错误，应直接返回该错误。",
  "source_id": "m12",
  "quote": "发送失败后返回原始错误",
  "review": {
    "kind": "defense",
    "assessment": "simplify",
    "subject": {"path": "send.go", "quote": "return send(msg)"}
  }
}
```

决定的作用对象可以是需求、方案、检查问题或验证记录。用户要求暂不检查时，将决定关联到当前任务，并注明只在本轮有效还是整个任务期间有效；有效期间跳过相应检查，在报告中注明用户决定。重跑决定关联到一次验证，并生成一条只供下一次相同验证使用的授权，用过后标记为已使用。普通的解释性笔记不会自动豁免拦截。记录成为有效的用户决定或重跑授权时，更新对应的授权修订号。

### 检查和问题

检查记录保存任务编号、快照、需求修订、方案修订、编辑记录修订、算法版本、有效分析设置、针对问题的处理说明和已结束的验证记录摘要。用途笔记的编号绑定它的说明、代码引用、需求版本和观察点。检查输入中的 `rules_version` 标识报告和副本候选采用的判断规则，规则变化后重新生成结果，文件索引和验证输入按各自的版本复用。静态、动态结果分开保存，注明完成、部分完成、失败或已过期。相同内容的观察、hook 活动时间、摘要、检查输出和普通笔记不改变检查输入。

动态检查分别保存当前副本、哨兵、探针、撤回、变异和确认运行各环节的命令、输出、退出状态、耗时及是否启动。无法启动、超时和结果无法解析时，分别记录原因，不能计作通过。

评估时，按检查记录序号区分新执行的检查和复用的结果，不根据工具环境的摘要去重，也不重复累计同一报告中原样运行和变异明细中的结果。单个环节的记录不能代表整次检查的成本：复用缓存前后的环境核对、准备工作副本及 Git 操作可能没有计入；并行命令的耗时之和也不等于实际经过的总时间。未记录的开销按 [评估与验收](product-evaluation.md) 标为未知。

每处问题保存稳定编号、规则、档位、逻辑位置、已确认的情况、建议、判断依据的来源、处理状态，以及已经拦截过的 session。问题所依据的情况没有变化时沿用编号，移动位置不会重置拦截次数。已解决的问题再次出现时，新增一次发生记录。

检查结束前重新核对输入版本。输入已经变化时，将本次结果保存为历史记录，不用于当前拦截。因缺少工具、超时或出错而未完成的部分，可以在环境修复或主动刷新后重试，不能永久缓存为放行结论。

未完成原因按位置和检查类型去重，每组保存前五项具体原因及其余项数，分组汇总不改变未完成状态。hook 日志和默认检查输出限制展示数量，状态命令可查看全部已保存分组。

### session、hook 和验证

session 保存 Agent、session 编号、工作区、开始及最近活动时间、上次摘要采用的输入版本。hook 活动保存事件种类、时间、session、轮次、处理状态，供接入诊断和评估核对 SessionStart、Stop 等事件。

对于需要通过 hook 补齐 MCP 调用身份的 Agent，账本另外保存工作区、Agent、session、工具调用编号与轮次、工具名的对应关系。工作区、Agent、session 和工具调用编号共同唯一确定一条记录。重复写入相同内容不改变关联；同一编号对应的轮次或工具不同，则拒绝覆盖。MCP 只根据 Agent 提供的工具调用编号读取对应记录，不从最近的消息推断。该记录只用于确定调用归属，不改变任务检查输入；传递方式见 [Agent 接入](product-agent-integration.md#pretooluseclaude-code-的-mcp-调用身份)。

验证记录保存编号、工具调用编号、session、轮次、实际目录、解析后的命令及参数、显示原文、是否混有其他命令、输入与环境标识、开始结束时间、结果和退出码。正在运行、通过、失败、中断、未知分别记录。环境标识只保存比较用摘要，不保存凭据。

被拦截而未运行的命令记为拦截事件，不增加实际验证次数。后续结果只有可核对时才补写；拿不到的保留未知。

## MCP 工具

算法输入使用以下八个工具的现有字段，具体记录见 [算法的逻辑记录](#算法的逻辑记录)。

| 工具 | 参数 | 作用和返回 |
| --- | --- | --- |
| `task_get` | `task_id` 可选；列表用 `category`、`after_seq`、`limit`，命令记录列表还可用 `command_contains`、`output_contains`；正文用 `record_id`、`revision`、`char_offset`、`char_limit` | 默认返回有限概要、当前状态和记录总数；记录列表与正文按需续读 |
| `task_start` | 新任务用 `title`；恢复用 `task_id`；可选 `start_message_id`、`workflow` | 暂停原任务，开始、恢复或重新打开目标任务；返回任务和恢复摘要 |
| `requirement_save` | `id` 可选、`content`、`quote`、`source_id`、`acceptance`、`status`、`implemented_by`、更新时的 `base_revision` | 返回任务和需求编号、修订、状态、来源编号、待补位置数及有限示例 |
| `note_add` | `kind`、`text`；可选 `target`、`quote`、`source_id`、`review` | 返回笔记编号、类型、保存结果、决定是否生效及原因 |
| `check_run` | `depth` 为 `static` 或 `tests`，可选 `refresh` | 返回检查编号、输入版本、实际执行状态、复用标记、原执行时间、问题和缺口总数及有限明细 |
| `task_finish` | `outcome` 默认为 `complete`，用户放弃时为 `cancel` | complete 保存待交付请求并返回已有结果；cancel 保存中止及原因 |
| `plan_save` | `content`、`files`、`entries`、`deps`、`base_revision` | 保存完整方案及变更摘要，返回版本和路径 |
| `plan_confirm` | `version`、`source_id`、`quote` | 核对版本、消息来源和授权时间，返回确认状态、有效与待确认版本及正文入口 |

写入响应不附带完整任务视图，也不重复用户原文、需求或方案正文。默认概要的 `details` 包含有限的需求、有效决定、工作区更新、方案及检查摘要；`counts` 给出可查询记录的总数，`plans_revision` 用于下一次 `plan_save.base_revision`。没有当前任务时，只返回最多五个候选任务概要与选择入口。

记录类别为 `messages`、`sources`、`requirements`、`notes`、`plans`、`checks`、`verifications`、`workspace_updates` 和 `task_updates`。最后两类分别对应观察发现的工作区更新和任务恢复时的更新。列表按不可变记录序号升序读取，需求采用修订记录序号，方案采用提交版本序号；`limit` 默认 20、最多 100。响应中的 `last_seq` 是实际返回的最后序号，`has_more` 表示仍可续读；下一页传 `after_seq=last_seq`。并发追加的记录出现在后续页面。

单条读取的 `record_id` 和需求、方案的 `revision` 从记录列表或写入返回的 `read` 入口取得。方案的正文修订号与提交版本、任务方案修订分别返回，确认不会改写原提交正文。`body` 是完整记录正文的 JSON 文本片段；按 `next_offset` 续读，拼接全部片段后解析 JSON。字符范围按 Unicode 字符计数，默认每次 2,000 个，最多请求 12,000 个；协议预算可进一步缩短，`char_offset`、`char_end`、`char_total` 与 `next_offset` 始终反映实际范围。

准备重跑时，可用 `{"category":"verifications","command_contains":"TestExport"}` 在所选任务已保存的脱敏命令全文中按字面查找，区分大小写。每条匹配记录的 `command_prefix` 显示命令开头，略过开头的空格、制表符和换行，取首行最多 120 个字符。例如，运行测试和在 PR 说明中引用测试命令都可能匹配，用命令开头和执行状态选出要回看的记录，再按 `read` 读取完整命令和输出。失败、尚无结果、被拦截以及未归为验证的请求也参与查找。`total` 给出匹配数，续页沿用同一片段和上一页的 `last_seq`。

例如，`{"category":"verifications","output_contains":"TestExport"}` 可找到整组运行中输出过该用例名的记录。`output_contains` 在已保存的输出中按字面查找，区分大小写。`output_excerpt` 给出首次匹配处的原文。末次匹配的摘录与首次不同时，`last_output_excerpt` 给出末次原文。每段最多 120 个 Unicode 字符。

按单行文字查询且首末两段都显示时，若紧邻末次匹配的上一行含有非空白文字，末段可以附上这一行，例如用例结束前打印的错误。如果首次匹配的下一行也含有查询文字，且在末段之前，首段可以附上这一行。例如，四行连续测量值都带有同一个场景名，两段各能放下两行时，就可以直接核对四个值。附行须位于两段之间，并能连同原换行完整放入该段的字符限额。并行任务也可能在此处写入日志，行的先后只说明输出顺序。整次运行的状态见 `state`，需要其他输出或运行条件时按 `read` 读取正文。同时指定命令和输出片段时，只列出两项都匹配的记录，续页保留两项条件。

按命令或输出查找时，列表会为实际执行、结果为通过或失败且前后快照齐全的命令给出工作区 Git tree。两端相同时，`state.workspace_tree` 是这个共同的对象名，可用来比较两次运行之间的文件变化。两端不同时，`state.before_tree` 和 `state.after_tree` 分别是命令开始前和结束后的对象名。用 `git diff <before_tree> <after_tree>` 可以查看这次运行期间哪些文件发生了变化，再结合命令和输出判断变化是否与验证有关。仅凭两端快照无法确定命令读到了中间哪个版本。

缺少任一端的观察或结果未知时，列表省略这些字段。即使临时用例已删除，只要对象还在本地 Git 仓库，就能查看当时的文件。工具版本、环境变量和外部数据需另行核对。

工具说明及输入字段说明须直接写明参数的适用条件，让新会话不必先调用失败才知道用法：

- `task_get` 的列表不含正文，列表页使用 `category`、`after_seq` 和 `limit`，只有 `verifications` 列表可指定 `command_contains` 或 `output_contains`。`revision`、`char_offset` 和 `char_limit` 仅用于已指定 `record_id` 的正文读取，不能与列表参数混用。例如先用 `{"category":"messages","limit":5}` 取得列表，再按其中的 `records[].read` 读取正文，需要时增加 `char_limit`，按 `next_offset` 续读。
- `requirement_save`、`note_add` 及 `implemented_by` 中的原话引用 `quote` 与 `source_id` 必须成对提供。来源编号使用 `messages` 或 `sources` 列表中的 `id`，例如消息编号 `m12`；需求编号 `R1` 不是来源编号。没有原话依据的推断需求、实现判断笔记或不引用原话的位置可以同时省略这两项，省略引用不构成用户授权。笔记关联需求使用 `target={kind:"requirement",id:"R1"}`。
- `task_start.workflow` 只接受 `auto`（全自动）或 `semi`（半自动），省略时沿用有效设置。工具说明和字段说明均列出这两个值。

列表与正文参数混用、引用缺少配对字段时，错误须指出相关字段并说明如何重新读取或补齐；不自动忽略参数、猜测来源或补写原话。

历史正文与查询时的 `state` 分开返回。查询结果另外说明笔记是否生效、方案是否确认及撤回数量、验证的执行状态与退出码，以及检查的档位和有效性。检查正文保留完整报告、需求位置、已取得的测试情况和问题依据；交付时显示的状态与后续验证信息单独保存。内部读取时将这些内容合并为完整交付信息，不重写原执行报告。

检查列表的 `validity` 为 `not_checked`。读取单条检查时，程序才核对当前输入；无法核对时保持 `unknown`，不能据此声称历史结果仍有效。原文及确认依据可按来源编号读取。

最终 MCP 响应（包括文本和结构化内容）的估算预算：普通写入 1,000 token，`task_start` 2,000，`task_get` 与 `check_run` 8,000。估算沿用中文每字一个、英文每四个字符一个；debug 另记业务 JSON 与最终协议的 UTF-8 字节数，不将估算值当作模型实测 token。超过预算时保留身份、状态、修订、总数和续读入口，裁剪 `details` 或减少本页记录，并标记 `truncated`。拦截问题优先展示。内部账本和动态用例选择仍读取完整报告。

检查报告对未能得出结论的部分记录 `kind`、位置、操作和原因；`gap_counts` 分别统计 `unknown`、`error`、`incomplete`。存在这些情况的检查记为 `partial`；没有这些情况，也只表示计划执行的计算已经完成，不能解释为全部业务行为都已验证。`unconfirmed_count` 表示本次没有重新确认的问题数量；`reused` 只表示采用已有结果。

静态检查可以复用相同输入下最新的完整检查记录，也可以复用仅因信息不足而被标为部分完成的记录；执行出错或计算未完成的结果不能复用。复用时保留原状态、编号、执行时间，以及未能得出结论的部分。文件词法按 blob 与起点约定缓存，起点索引和改动覆盖层按 [算法核心](algorithm.md#九什么时候计算) 查询；主动刷新时重新核对检查结果，仍复用内容未变化的分析结果。

检查记录用 `feedback_version` 标记生成反馈时采用的格式。程序升级后，格式不一致的静态或动态报告不直接复用，按当前规则重新生成反馈；已有文件索引、相同输入下的动态分析和验证记录仍按各自规则复用。该版本不参与算法输入计算，不因提示调整而使已有验证结果失效。

检查报告的 `analysis` 保存约定、变更簇、需求相关区、静态信号、权重和已选择条目；`dynamic` 保存副本运行、确认集合、补丁、发现矩阵、保留集合及缺口。完整逻辑记录通过检查正文读取，MCP 摘要只显示有限明细。

`implemented_by` 每项包含 `at`、可选的 `quote`、`source_id`、`purpose` 和变更类型。传入时替换这一版的位置列表，历史修订保留；不传时沿用原列表。位置未能对应时保留待更新项和原因。

`files` 每项包含 `path`、`change` 和 `note`，以 `/` 结尾表示目录范围。`entries` 每项包含 `at` 和 `note`；`deps` 每项包含 `module` 和 `reason`。空项传空列表。

更新需求或方案时采用 `base_revision` 核对，发生冲突返回最新修订号和读取入口，Agent 取得正文后再合并。各工具的幂等重试以 session、工具调用编号和目标版本识别，重复到达不重复开始任务或追加同版方案。

`task_finish` 不运行耗时测试，也不立即清除当前任务。Stop 根据本轮保存的交付请求，检查对应任务并处理完成状态。首次反馈后仍保留本轮请求；输入未变时，再次 Stop 可以直接完成报告。

本轮没有交付请求时，同一 session 的当前轮次可以继续处理当前待交付任务尚未完成的请求，保留原请求来源和反馈状态，并重新核对输入版本。期间发生新编辑，或需求、决定、已结束的验证记录有变化时，请求过期，任务回到进行中。Agent 申请完成前应更新需求状态；未完成或已撤销的需求分别列入报告。

全自动任务调用方案工具时，返回当前模式和有效需求，不新增审批。用户明确改变工作模式时，用 `task_start` 指定当前任务和新模式，保留已有内容。

## 算法的逻辑记录

以下记录保存 [算法核心](algorithm.md) 的计算输入和结果。文件分析和仓库统计按内容缓存，中间结果按任务输入版本保存，跨短进程复用。

| 逻辑记录 | 必要内容 |
| --- | --- |
| 文件分析 | blob 标识、词序列摘要、版面树、单元及首行名字、结构置信度 |
| 仓库统计 | 扩展名分组、词频与 idf、字符串定界符、注释记号、关键字、调用写法比例、测试词汇、约定入口模式、统计所用的 tree |
| 变更簇 | 所含 hunk 及类别、新词、依赖关系、来源（Agent 编辑、工作区更新或混合）、合并原因 |
| 需求相关区 | 需求修订、种子及权重、精度参数、得分、相关区成员、各变更簇的最强路径 |
| 对外新增项 | 种类、识别方式及是否经探针确认、名字与取值、需求对应关系的级别及对应来源或实现位置、探针输出摘要 |
| 结构信号 | 间接层的变化数与代价、近似重复的对象与相似度、没人使用的新词 |
| 撤回试验 | 候选集合、每次运行的撤回集合与结果、合并的变更簇、确认运行及失败后逐个加入的结果、撤回补丁 |
| 变异与发现矩阵 | 变异位置与算子、是否有效、抽样与停止估计、每个变异的运行结果、发现关系、冗余变异、保留集合、确认运行、测试缺口 |
| 验证输入记录 | 验证输入哈希及其组成、结果、输出、不稳定标记、注释敏感性计数、范围包含与通过规律的计数、两次运行之间修改环境变量的命令 |
| 合并信号 | 每个候选的信号取值、可信度、所用权重的版本 |
| 反馈与校准 | 展示的条目、是否拦截及所依据的事实、Agent 的处理及理由、之后的恢复或失败、标签、拟合的权重及样本数 |

内容或需求变化时复用未变化的文件分析，并重新计算对应输入的变更簇、相关区和信号。发布时核对任务、内容、需求与决定；输入已经变化的结果保留其输入版本，不用于当前拦截。

Agent 将验收标准写入 `requirement_save.acceptance`，对应需求的修订时间就是验收标准的登记时间；如何处理反馈、决定保留哪些内容以及重跑理由，用 `note_add` 记录。校准标签按项目保存，没有本项目标签时采用本机其他项目的标签，不随单个任务到期删除。

## 保留期限

schema 14 在原有索引页目录之外记录构建代次、删除标记和页发布修订。撤下索引后按其实际编号续删目录和引用全文。每个账本事务和 MCP 调用核对支持版本。结构迁移失败整体回滚，下次打开可重试。

`Full=true`、`Complete=true` 表示已取得完整 tree；观察的文件正文只记录本次核对的路径，以 `files_set_id` 引用去重内容表，保留原始 blob、删除标记和合法空映射。部分观察仍内联保存。具体路径按观察编号从路径版本表读取，检查元数据保留在 `checks_v12.data`，完整报告单独压缩。读取正文时校验长度与摘要，损坏或缺失正文返回带记录编号的错误。正文整理只在短事务复核原文后发布，压缩不省空间或超过准备时间时保存原文，总预算耗尽则不改记录。

- 进行中、待交付和暂停任务的记录、起点及恢复快照保留至任务结束。
- 完成或中止后，任务记录、方案和需要回读的快照继续保留三十天，便于重新打开和查看问题的依据。
- session、hook、MCP 调用身份和验证记录保留三十天；仍被活跃任务引用的记录随任务保留。
- 超期时一并清理记录、方案文件和 TaskBelay 自己的快照引用。

维护使用独立的 200 ms 总预算，先筛选各类到期记录。每轮最多处理八个任务，每个任务在单独事务中删除其独有记录，并登记需要释放的资源；独立记录每类最多处理 256 条。仍被保留任务的任何修订、来源引用、起点或恢复点、当前文件、编辑前后观察及验证关联引用的记录，都不能删除。

恢复事务先提交时，清理流程不再删除该任务；删除事务先提交时，恢复请求返回任务不存在。超时会回滚当前事务，不会留下只删除了一部分的任务。

只要仍有观察记录引用共享文件表中的内容，就保留该内容；最后一个引用消失后，才在写事务中回收，不另外维护引用计数。创建新的 Git tree 引用前，先登记工作区、完整名称、对象与三十天的保留期限；提交观察记录时核对并撤销这项登记。未成功保存到观察记录中的引用，仍可在到期后回收。只有账本事务提交后，才核对资源的归属并释放。日常维护腾出的页由 SQLite 复用；空闲页超过文件一半且不少于 64 MiB 时，MCP 后台在清理分析数据后收缩一次文件。用户执行 `taskbelay compact` 时，程序整理旧索引和分析正文，再运行 `VACUUM` 并回写 WAL，将空闲页归还文件系统。实现见 [系统架构](product-architecture.md)。

## 会话动作记录

会话文件保存用户可以直接阅读的运行记录，不为此新增账本表、索引或迁移。需求、决定、下一步、方案及任务状态实际保存成功后，才追加简述和能够取得的编号、修订。全自动模式下，方案接口只返回模式提示时，不能记作方案已保存。`task_finish` 记录申请交付，不能写成任务完成。读取记录和重复调用返回原结果时，不再记录一次新的保存动作。

只采用当前处理过程中的事实，不为记录另查账本、扫描工作区或追溯历史。后续验证结果另写新条目，未知或未完成不当作通过。记录文件的位置、追加及保留规则见 [系统架构](product-architecture.md#会话动作记录)。
