# TaskBelay 产品需求

TaskBelay 是一个在本机运行的命令行程序，接在 Claude Code 和 Codex 上，帮助开发者减少 Agent 多做的功能、抽象和测试，减少重复验证，并在切换 Agent 或 session 后接着工作。

用户照常提需求、改代码、提交和切换分支。TaskBelay 记录任务，检查 Agent 的工作，把有依据的问题交给 Agent 处理。用户直接修改 Agent 写出的代码，也是开发过程的一部分：接下来的工作以当前代码为准。

文档的分工和术语见 [文档说明](README.md)。本文算法相关功能是语言无关的目标需求，现有程序尚未实现；当前命令、安装和数据规则保持原义。

## 要解决的问题

### Agent 容易做多

用户只要 CSV 导出，Agent 可能同时加上只有一种实现的接口、没人需要的分隔符选项和几处顺手重构。TaskBelay 把改动与本次需求对应起来，指出可以省掉的部分，让 Agent 交回够用、容易维护的实现。

### Agent 容易测多

Agent 可能为同一行为写很多相近用例，反复运行全量测试、构建和 lint。TaskBelay 分别检查测试代码和验证过程。保留测试的标准是它守住了什么行为；运行验证的标准是这次运行能提供什么新信息。

### 工作难以接续

额度用完、上下文压缩、隔天重开 session 或临时插入另一件事后，Agent 容易丢失需求、决定和进度。TaskBelay 保存任务账本，按当前工作区生成摘要。

## 正常的开发过程

下面这些操作都按正常开发处理，用户不需要为 TaskBelay 提前登记：

| 用户在做什么 | TaskBelay 怎样处理 |
| --- | --- |
| 一个需求分多次提交，部分文件暂存、部分不暂存 | 始终相对任务起点计算累计 diff，提交不结束任务，也不清空记录 |
| 自己改了 Agent 写得不好的代码，没有告诉 Agent | 下次观察工作区时记录更新，刷新相关检查；Agent 从当前内容继续，保留这部分修改 |
| 删除、改名、移动 Agent 写出的文件或函数 | 更新实现位置，旧位置保留在任务记录里；对应不明确时让 Agent 补位置 |
| 追加、修改或撤销需求 | 更新同一任务的需求，保留之前的版本和变更依据 |
| 临时处理另一件事，再回来继续 | 暂停原任务，之后恢复原来的需求、快照和进度 |
| 切分支、stash、pull、rebase 或 amend | 重新核对工作区与任务的关系；新出现的内容先作为工作区更新处理 |
| 明确要求再跑一次测试，或暂时保留某处实现 | 按这次要求执行，记录适用范围，后续接续能看到 |

任务范围、工作区更新和需求变更的规则见 [任务和需求](requirements.md)。

## 功能

### 防止过度设计

TaskBelay 把累计改动分成必须一起保留或撤回的变更簇，用局部图聚类找出每条需求的相关区，再指出与需求无关的改动、原话里找不到对应的对外新增项、背后没有变化的间接层、重复实现和没人使用的代码。每处反馈写明具体动作：撤回哪个变更簇、怎样内联、复用哪个已有单元。代码行数、接口数和实现个数都不单独构成结论。

动态检查开启时，TaskBelay 在副本中撤回候选改动、运行验收依据，用分组检验以接近对数级的运行次数确认哪些可以撤回，并给出确认过的撤回补丁。原话里找不到对应、全部来自 Agent 编辑的对外新增项，以及确认可以撤回又与需求无关的改动，交付时可以拦截一次；其余都是排好序的建议。规则见 [过度设计判定](over-design.md)。

各项信号的权重和拦截所需的置信水平按项目中反馈的实际结果校准。处理是否完成、依据覆盖了什么、得出什么结论和采取什么动作分别记录；信息不足时结论是未知。共享算法和问题身份见 [算法核心](algorithm.md)。

### 防止过度测试

TaskBelay 用被测代码中的比较常量划分等价类和边界，找出落在同一等价类的重复用例。动态检查开启时，再用变异和分组检验求出每条用例发现的变异，以贪心集合覆盖选出能维持同样发现能力的保留用例，其余用例作为删除或合并候选。确有变异没被任何用例发现时，才提示补测试。

运行命令前，TaskBelay 按验证输入判断这次运行能否提供新信息：验证输入与上次通过时相同，就拦截一次并交回上次的输出；用户要求重跑、上次失败或结果未知、命令会写入时照常运行。运行后按 Young 公式估计的最优验证间隔，提示合并验证或尽快验证。规则见 [过度测试判定](over-testing.md)。

动态测试检查由项目设置开启，也可由 Agent 主动请求。默认的交付检查先做静态分析，不额外启动项目测试。

### 跨 Agent、跨 session 接续

同一工作区的两个 Agent 共用任务账本。摘要包含当前需求、方案、进度、决定、工作区更新和最新检查结果。用户中途手改代码时，摘要提醒 Agent 先读更新后的内容；不会把旧的下一步当成必须恢复的实现。见 [任务接续](handoff.md)。

### 两种工作模式

- **全自动**：用户给出需求后，Agent 直接开发，TaskBelay 在过程中检查。
- **半自动**：Agent 先提交方案，用户确认后开发。方案约定行为、涉及的范围、新入口和新依赖；范围内的实现调整由 Agent 完成，扩大约定范围时再确认。

用户可以在任务中途调整工作模式，已经完成的工作保留。半自动模式只约束 Agent 接下来的开发，用户随时可以自己改文件。见 [半自动模式](semi-auto.md)。

### 安装与日常管理

用户通过一条安装命令把程序装到自己的用户目录，无需管理员权限。安装后运行 `taskbelay`，在终端菜单中完成 Agent 接入、移除接入、常用设置、状态查看、检查、程序更新和卸载。上下方向键移动，右方向键或回车进入，左方向键返回，空格勾选 Agent；卸载和开启动态检查需要在菜单中确认。

已有子命令继续用于脚本。非交互环境无参数运行时显示帮助，不等待键盘输入。安装、更新和卸载保留任务账本及用户原有的配置；程序自更新和自卸载只处理安装脚本标记的程序。具体入口和发布包要求见 [Agent 接入](product-agent-integration.md)。

### 调试与过程复盘

用户可开启 debug 模式，详细记录 TaskBelay 接收到的任务事件、MCP 调用、处理阶段、检查依据、返回结果、错误和耗时。记录保存在用户目录 `.taskbelay/debug/`，按日期分组，文件以任务唯一标识命名。任务结束后记录继续保留，用户需要时再让 Agent 分析这些记录，查找接入、判断、接续和性能上的不足。开关默认关闭，不自动分析或上传记录。记录格式、范围和查看方式见 [系统架构](product-architecture.md#调试记录)。

## 一个完整的例子

1. 用户在 Claude Code 里说：“给 export 命令加一个导出 CSV 的选项。”
2. Claude Code 记录需求，开发 CSV 导出，用户中途提交了一次。
3. 用户觉得错误处理写得不好，自己修改了函数，没有发消息。Claude Code 下次编辑时，TaskBelay 告诉它该文件有更新；它先读当前函数，再继续开发。
4. Claude Code 申请交付。TaskBelay 拦截原话中找不到对应的 `--delimiter`，并建议把只有一种实现的接口改为直接使用实现类型；项目开启了动态检查时，还附上撤回后验收用例仍然通过的补丁。Claude Code 撤回这两处，保留用户修改的错误处理。
5. 用户又提交一次，任务完成报告仍然覆盖这次需求的全部改动。
6. 下一项任务做到一半，用户临时让 Agent 修一个小问题。原任务暂停，小问题完成后恢复原任务；如果换成 Codex，Codex 会拿到同一本账本和当前代码的摘要。

## 支持范围

- **Agent**：Claude Code、Codex，通过各自的 hook 和 MCP 接入。
- **语言**：目标算法对任何开发语言使用同一套词法、版面和统计方法，不按语言分级；判断所需的语言知识从仓库自身统计得到。文本结构信息少的文件结论更少，不会因此下错结论。当前实现尚有语言适配限制，见 [输入与执行协议](languages.md)。
- **平台**：Windows、macOS、Linux。WSL 按 Linux 安装和运行，同一环境里的 Agent 共用账本。
- **工作区**：git 仓库及其 worktree，各工作区分别管理任务。不在 git 工作区时直接结束 hook。
- **数据**：保存在本机。安装、配置和存储位置见 [Agent 接入](product-agent-integration.md) 和 [系统架构](product-architecture.md)。

## 默认行为

- 默认全自动，拦截强度为拦截一次；用户可改为只提示。
- 拦截按具体问题记账。修复其他文件、补充笔记或需求状态，不会让同一问题重新拦截；同一问题每个 session 最多拦一次，每轮合计最多三次。
- 普通停顿、分析和等待用户回复时，检查结果作为提示。Agent 申请交付后，Stop 才执行交付拦截。
- 工作区更新自动记录。来源无法核对的内容按现状分析，作为提示交给 Agent，不要求用户补充声明。
- 设置按用户、项目、当前任务依次覆盖。用户在当前对话里的明确要求即时适用于当前任务。
- TaskBelay 自己出错时，Agent 继续工作；本次检查的完成情况显示在报告里。

## 成功标准

效果按 [算法评估](product-evaluation.md) 的方法，在另行授权的专项验证中衡量。以下为目标与采用条件，不是已测得的效果；不能用代码或测试数量下降替代正确性。

| 方面 | 标准 |
| --- | --- |
| 精简效果 | 减少确认多余的改动和不提供新信息的验证，报告成本变化及不确定性；不强求每项数量下降 |
| 正确性 | 比较行为验收与有效回归结果，逐项调查新失败；精简收益不能抵消行为退步 |
| 接续 | 切换 Agent 后继续满足同一需求，保留有效结果、未知范围与用户决定 |
| 用户修改 | 保留场景中用户最后一次修改的行为，用户无需补原话、登记文件或暂停手动开发 |
| 开发习惯 | 多次提交、暂存、分支操作、暂停恢复和需求变更场景均完成任务，账本连续 |
| 误判与漏判 | 拦截中经核对为错误的比例不超过一成；建议的采纳与恢复、漏判分别统计，并报告样本数与不确定性；不能靠全部放行获得低误判率 |
| 普适性 | 扩展名和工具名一致改名后结果不变；语言之间的差异只体现为统计结果和结构置信度 |
| 半自动 | 用户确认前拦下 Agent 的编辑；确认后按有效方案和后续授权工作，用户修改照常保留 |
| 速度与总成本 | 静态部分的耗时随改动规模而不是仓库规模增长；动态部分的运行次数随候选数对数增长；计入 TaskBelay 自己的运行，报告冷启动、增量、缓存命中及退化场景，不宣称未测得的时延 |

## 会话动作记录

TaskBelay 自动将新发生的需求、决定、下一步和方案保存，任务开始或恢复、申请交付，已输出的接续信息、检查反馈、验证拒绝、过期编辑拒绝，以及已观察到的检查或验证结果追加为简短中文 Markdown。普通读取和没有干预的工具放行不机械记录；记录不依赖 debug。

用户直接打开用户数据目录的 `session-records/` 查看，无需发起查询。记录只写当时可确认的事实，区分保存成功、输出成功、检查复用、运行中及未知结果；申请交付不代表完成任务。没有查询或汇总入口，不扫描或补写历史。路径与保留方式见 [系统架构](product-architecture.md#会话动作记录)。
