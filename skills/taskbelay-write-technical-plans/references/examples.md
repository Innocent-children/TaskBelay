# 范例

[example-sliding-window.md](example-sliding-window.md) 和 [example-token-bucket.md](example-token-bucket.md) 是用户认可的两份方案。它们针对同一个问题（企微机器人每分钟最多 20 条），给出了两种设计：前者是限流加合并补发，后者是排队加令牌桶。

读它们是为了看到：一份好方案写得多具体、读起来多顺。不要搬走它们的主题、组件、章节名和图的形状，这些都是"给一个发送出口加限流"这个问题的产物。换一个问题，好的结构自然会不一样。动笔时可以问自己：写这两份方案的人，面对我手上这个问题，会怎么写？

下面的点评表里，"为什么有效"那一列可以用到别的方案上；"做法"那一列只属于这两份方案。

## 方案一做对了什么

| 位置 | 做法 | 为什么有效 |
| --- | --- | --- |
| 背景 | 一句话：压测期间告警多，多个入口同时发给同一个机器人，超过每分钟 20 条，部分通知被拒 | 场景、机制、约束、后果都在，读者马上明白为什么要改 |
| 目标 | 四条，粗体关键词开头；"不超频"写明 18 次和理由；最后一条是"平时无感知" | 每条都能验收；"不变"的目标打消了"平时会不会受影响"的顾虑 |
| 思路 | 点名"精确滑动窗口算法"，链到 Redis 官方教程；几句话讲完计数、超额暂存合并、延迟唤醒补发、清空后恢复 | 只读这一段就能复述方案；链接带来可信度 |
| 流程解析开头 | "现有所有企微告警都会汇集到一个出口，所以，只改动这个出口即可" | 一句话回答了改动范围、工作量和风险 |
| 全景图 | 列出全部真实入口：三类来源先经 MQ 汇到同一个监听器，再和 HTTP 接口、积压检查一起汇到唯一出口；改造部分注明"详细过程见下图" | 读者看到新机制在系统里的位置，也相信没有漏掉的入口 |
| 细节图 | 有判断（额度够不够）、等待（延迟队列）、回路（额度不够回去等，还有积压继续取）、出口（积压清空恢复逐条发送） | 异常和恢复都画了，不留"然后呢"的疑问 |
| 分步说明 | 五步，每步一句加粗结论，再补具体规则：同模板 ID 合并、模板 ID 为 0 时按正文开头固定字数合并、唤醒时间 = 最近 18 次中最早一次 + 60 秒 | 加粗部分串起流程；规则补齐了图上放不下的细节 |

## 方案二多了什么

方案二的设计更朴素，写法也跟着变简单：目标换成"超额排队""按序发送"，思路换成 FIFO 队列加令牌桶，细节图更短。它展示了同一种写法怎样适配不同复杂度的设计。几处细节值得注意：

- "每 3335 毫秒补充一个令牌（约每分钟 18 个）"：给出精确值和换算，读者不用自己算。
- "同一个机器人在所有服务实例中保持串行发送"：主动回答了多实例并发这个工程师一定会问的问题。
- 入口节点用描述代替了类名，不熟悉代码的读者更容易懂；方案一保留类名，方便熟悉代码的人定位。两种都可以，看读者是谁。

## 它们没写什么

没有开场白，没有成本排期表，没有风险表，没有待决策清单，也没有被否掉的备选方案。因为这次读者要的是看懂并认可这个设计，这些内容不影响他的判断。

读者需要批资源、选方向或者承担风险时，就要把这些补上。范例没写，不代表永远不写。
